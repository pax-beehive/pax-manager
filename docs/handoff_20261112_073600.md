# Native harness account identity

## Change and boundaries

Issue #083 is resolved for the current node user API. Harness auth views now
include optional `account` metadata:

```json
{"email":"person@example.com","display_name":"Person","organization":"Workspace","plan":"Pro"}
```

Every field is optional. A missing account means the daemon did not report an
identity; callers must not infer an email from API keys or other credentials.
No new route, request argument, database field, or credential access is added.

`internal/manager/domain/harness_auth.go` defines the public account whitelist.
`internal/manager/userapi/harness_auth_account.go` sanitizes strings before the
existing status/command response path returns them. `decodeHarnessAuthView`
omits account metadata unless state is `logged_in` or `succeeded`, preventing
stale identity on pending, failed, expired, cancelled, or logged-out views.

## Request and data flow

The existing principal, exact node ownership, ephemeral attempt ownership,
node-control transport, and `Cache-Control: no-store` checks still apply. Updated
paxd sends account metadata through `harness_auth.status` or successful login
ACKs. Manager decodes only the four public account fields and drops provider
extras, including token fields. It trims surrounding whitespace, requires valid
UTF-8, rejects Unicode control/format characters, and applies byte limits:

- Email: 254 bytes.
- Display name and organization: 256 bytes each.
- Plan: 128 bytes.

An invalid field is omitted while other valid metadata is retained. An empty
account object is omitted. Account metadata is response-only and is not added
to the ownership map, durable command journal, logs, or other persistence.

## Generated artifacts

`api/pax_manager.thrift` remains the source of truth. It defines the optional
`HarnessAuthAccount` struct and account field. Hertz and OpenAPI artifacts were
regenerated with the exact cached mockery module used by the previous login
change:

```sh
PATH=/Users/gengcongkai/go/bin:$PATH GOWORK=off make generate MOCKERY=/tmp/pax-manager-mockery
```

The binary was built from cached `github.com/vektra/mockery/v2@v2.53.5`; its

were edited manually. Existing interface mocks are unchanged.

## Development and deployment

Use `GOWORK=off` for this isolated worktree. Existing local commands remain
`GOWORK=off make run-memory` or normal PostgreSQL configuration. Deployment uses
the existing `make cloud-build-vm` workflow. No deploy, merge, commit, or push was
performed as part of this implementation.

The new field is optional in both directions. Old daemons return no identity;
old clients ignore the extra field. Complete account display requires the
matching paxd extraction and Console display changes. The OS account and native
credential context remain those of the paxd process. Identity is metadata from
the native CLI, not an additional provider request or ownership verification.

Tests were written first and failed because the previous API dropped account
metadata. Unit coverage exercises Claude/Codex status, successful login ACKs,
older responses, stale states, unknown token/provider fields, malicious control
characters, oversized values, exact limits, and Unicode display names. A real
local HTTP/WebSocket route test verifies account passthrough, no-store, and token
field exclusion using synthetic replies. No real provider credentials, files,
logs, or tokens are accessed by these tests.

All required checks passed:

```sh

GOWORK=off GOCACHE=/tmp/pax-manager-go-cache go test -count=1 ./...

```

New account sanitization code has 14/15 covered statements (93.3%), exceeding
the 80% requirement. Both branches added to the existing view decoder are
exercised by active and stale account tests. Lint passed for normal and
integration-tag packages. Local HTTP/WebSocket tests required network sandbox
escalation; they use synthetic account data only. Docker-backed integration and
real provider authentication were not run for this optional metadata passthrough.

Read-only review found no account safety blocker. A malformed non-string
account scalar causes the typed daemon response to fail, consistently with the
existing invalid daemon response handling; it is not treated as logged out.
