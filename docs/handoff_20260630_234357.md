# Handoff: Team User Envelope Authorization

## Summary

Envelope creation with `from_agent_id` and `to_agent_id` now authorizes by
shared active team membership between the sender user and the target agent owner
user. The target and source agent ids still need to be valid identities, and the
source agent must belong to the sender.

This relaxes the previous rule that both agents had to be active entries in the
same `team_agents` set.

A small unrelated lint cleanup in `internal/manager/conversation.go` was also
needed so the PR can pass the repository merge gate.

## Module Boundaries

- `internal/manager/userapi/envelope.go` keeps transport-facing envelope
  validation and maps authorization misses to a 403.
- `internal/manager/storage/envelope.go` owns the Postgres authorization query.
- `internal/manager/storage/memory_envelope.go` mirrors the Postgres rule for
  in-memory tests and local service behavior.
- `internal/manager/conversation.go` had request parsing extracted from
  `handleConversation` and an unused helper removed to satisfy lint.

## Request Flow

1. `CreateEnvelope` normalizes `from_agent_id` and `to_agent_id`.
2. If both agent ids are present, `resolveEnvelopeRecipient` calls
   `GetEnvelopeAgentRecipient`.
3. Storage verifies:
   - `from_agent_id` exists and is owned by the sender user.
   - `to_agent_id` exists and resolves the recipient user.
   - sender user and recipient user share at least one active team.
4. The envelope still stores the original `from_agent_id` and `to_agent_id`.

Friend-based envelope creation without agent ids is unchanged.

## Generated Artifacts

No generated artifacts were changed. The store interface signature stayed the
same, so `make generate` was not required.

## Risks And Notes

- The authorization is intentionally relaxed only for team-agent membership.
  Sender ownership of `from_agent_id` is still enforced.
- Existing clients that already add agents to teams continue to work.
- Legacy friend-based envelope sends are not changed.
