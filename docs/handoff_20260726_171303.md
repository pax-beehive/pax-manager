# Session artifact GCS deployment configuration handoff

## Summary

The VM deployment now injects the session artifact bucket and artifact signing
service account into the pax-manager container. This fixes the attachment API
returning `session artifact gcs bucket is not configured` after the attachment
routes were deployed.

## Deployment configuration

`cloudbuild.vm.yaml` defines these non-secret substitutions:

- `_SESSION_ARTIFACT_GCS_BUCKET=pax-tech-bucket`
- `_PAXD_ARTIFACT_SIGNING_SERVICE_ACCOUNT=548727007198-compute@developer.gserviceaccount.com`

The deploy step passes both values to `deploy/vm/deploy.sh`. The script requires
them and injects them into the manager container as:

- `SESSION_ARTIFACT_GCS_BUCKET`
- `PAXD_ARTIFACT_SIGNING_SERVICE_ACCOUNT`

The VM service account signs GCS URLs through its existing self-scoped
`roles/iam.serviceAccountTokenCreator` binding. No human account receives
service account impersonation permissions.

## Verification

- `bash -n deploy/vm/deploy.sh`
- Cloud Build YAML parsing and deployment argument assertions
- The triggered Cloud Build and a production attachment API request provide
  end-to-end verification.

## Operational notes

The browser still requires a GCS CORS policy that permits the PAX Console
origins and exposes the resumable upload `Location` header.
