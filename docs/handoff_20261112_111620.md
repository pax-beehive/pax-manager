# Native harness plan usage

## Change and boundaries

Issue #084 is partial: the current node user API can now return subscription
plan usage for a node harness. Manager adds one read-only route and forwards a
new paxd control query. It never reads native credentials, persists usage, or
caches responses. The legacy agent API is unchanged.

```text
GET /api/v1/user/:user_id/nodes/:node_id/harnesses/:harness/usage
200 {"data":{"harness_usage":<HarnessUsageView>}}   Cache-Control: no-store
```

Files:

- `api/pax_manager.thrift`: `GetNodeHarnessUsage`, `GetNodeHarnessUsageRequest`,
  `HarnessUsageView`, `HarnessUsageWindow`, `HarnessUsageExtra`,
  `HarnessUsageData`, `HarnessUsageResponse`.
- `internal/manager/domain/harness_usage.go`: response types.
- `internal/manager/userapi/harness_usage.go`: ownership, control query,
  daemon error mapping, and sanitization (business logic).
- `internal/manager/node_harness_usage.go`: thin HTTP binding that sets
  `Cache-Control: no-store` and delegates; registered in
  `generatedNodeDaemonHandlerBridge` in `internal/manager/idl_handlers.go`.

## Request and data flow

1. Principal resolution, then `validHarnessAuthTarget` (harness `claude` or
   `codex`, trimmed node id). Invalid input returns 400 before any node call.
2. `harnessAuthRemote` requires exact node ownership (404 otherwise) and a
   connected control tunnel with a reported remote id (503 otherwise).
3. Manager sends, with a 15 second bound:
   `{"type":"harness_usage.status","harness_usage_status":{"harness":"claude"}}`.
   Node control requests are serialized per tunnel (one pending request), so
   the bound limits how long a slow native read can block other control
   requests to the same node.
4. paxd replies `{"harness_usage":<view>}` or `{"error":{"code":...}}`.

View contract (paxd output is untrusted and re-validated here):

| Field | Rule |
| --- | --- |
| `harness` | must equal the requested harness, else 502 |
| `state` | `available`, `unsupported`, or `unavailable`, else 502 |
| `observed_at` | RFC3339, re-emitted as RFC3339 UTC; dropped if unparsable |
| `plan` | account-field sanitizer, 128 bytes |
| `windows` | `available` only; first 12 valid windows; duplicate ids dropped (first valid wins) |
| `windows[].id` | `^[a-z0-9_]{1,64}$`, else the window is dropped |
| `windows[].window_minutes` | integer 1..44640, else the window is dropped |
| `windows[].used_percent` | finite number 0..100 (JSON null rejected), else the window is dropped |
| `windows[].scope` | account-field sanitizer, 64 bytes; only the scope is dropped |
| `windows[].resets_at` | RFC3339, normalized to UTC; only the field is dropped |
| `extra_usage` | `available` only; `{"enabled": bool}` |
| `error_code` | `unavailable` only; `cli_unsupported`, `read_failed`, `timeout`, or `daemon_unsupported`; anything else, including missing, becomes `read_failed` |

Optional fields are decoded from raw JSON so one malformed value drops only that
value. Unknown fields (tokens, raw native output, provider extras) are never
copied.

Error mapping:

- Daemon `invalid_argument`: the harness was already validated, so this means the
  node runs a paxd that predates the query. Manager returns 200 with
  `{"harness":h,"state":"unavailable","error_code":"daemon_unsupported"}`.
- Daemon `not_found` 404, `conflict` 409, anything else 502 with a safe code
  (`harness usage failed: node_error`); daemon messages are never echoed.
- Transport: 504 on timeout, 503 when the tunnel is unavailable (existing
  `queryNodeControl` behavior).

## Development and deployment

Use `GOWORK=off` in a worktree under the pax workspace `go.work`. Local run and
deployment commands are unchanged (`GOWORK=off make run-memory`,
`make cloud-build-vm`).

Usage needs a paxd with the `harness_usage.status` query and the pax-console
Plan usage panel, both shipped in companion pull requests. An older paxd answers
the unknown query with `invalid_argument`, which Manager maps to `unavailable` /
`daemon_unsupported`; older clients do not call the route.

## Risks and assumptions

- paxd reads Claude usage through the Claude Code `get_usage` stream-json
  control request, which Claude Code marks EXPERIMENTAL. A CLI change can turn
  the state into `unavailable` with `cli_unsupported`; Manager passes that through
  and needs no change.
- paxd caches each harness view for 60 seconds (15 seconds when unavailable), and
  the Claude CLI caches usage for about a minute on its own. `observed_at` is
  when paxd completed its native read, so Claude data can be up to about two
  minutes old.
- Control requests are serialized per node tunnel. A paxd cache miss holds the
  tunnel for the native read, measured at about 1-4 seconds for Claude and
  1.5-2.5 seconds for Codex, at most once per minute per harness and only while
  someone views usage. paxd bounds the read at 10 seconds (Claude) and 5
  seconds (Codex).
- `unsupported` covers both API-key style credentials and a signed-out CLI;
  clients should combine it with `harness_auth.status`.
- The 15 second bound must stay above paxd's own native read timeout so paxd can
  report `timeout` itself instead of Manager returning 504.
