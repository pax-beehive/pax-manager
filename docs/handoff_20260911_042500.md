# KEV-37 registration-start edge baseline

## Applied configuration

Cloudflare Free permits one rate-limiting rule with a 10-second counting period.
The dashboard shows its managed ruleset as Always active; no WAF challenge,
Access policy, Tunnel route or paid entitlement was changed.

Rule `668a294c41b84a6d9a9622d5180bd092`, PAX registration start burst protection,
limits the exact `/api/v1/node/registration/start` path to 3 requests per
10 seconds per IP, then blocks for 10 seconds. The expression applies across
proxied hostnames in the zone; it does not include the Console proxy prefix,
registration poll, control or ACP paths. All methods on the exact path count.
The dashboard values are recorded in
[the rule manifest](../deploy/edge/registration-rate-limit.json).

This is burst protection, not the issue's original 5/minute token-bucket target.
Cloudflare counters are distributed; do not treat them as an exact global quota.
Several simultaneous setups behind one NAT can share a limit.

## Verification

A bounded burst of missing-hostname requests creates no registration records.
Both API hosts produced Cloudflare 429 / error 1015, Retry-After: 10, and a
text/plain response without a challenge. Subsequent registration requests
recovered after waiting 12 seconds. During the block, poll returned its normal
validation error, unauthenticated ACP returned 401, and the user API retained
its Access redirect. Security Analytics sampled logs showed Block events from
Rate limiting rules filtered to this rule, confirming edge enforcement.

Run `python3 deploy/edge/check_registration_rate_limit.py` to repeat the bounded
check against the two production API hosts. It uses at most nine invalid starts
per burst and records only response metadata in `/tmp/kev37-edge-results.json`.
It temporarily limits registration starts from the probe's own IP. Do not run it
concurrently with normal setups from that IP. This is not a load benchmark.

Normal registration-start plus three two-second polls succeeded on each API
host. Only the test pending registrations were removed. The existing daemon
remained connected with auth none; full browser approval/new-client setup was
not repeated in this step.

## Client behavior and operations

Normal Manager registration responses advertise a two-second polling interval.
Polling is deliberately outside this rule. The current paxd client reports a
non-200 registration-start response as an error; it does not automatically
retry using Retry-After. After a 429, wait at least the advertised delay and
rerun login. No CAPTCHA or JavaScript challenge was added.

Find this rule under Security > Security rules > Rate limiting rules. Open its
sampled events through the rule's event-count link. To roll back only this
change, disable this exact rule; leave managed WAF, Access and other rules intact.
No application deployment, database migration or daemon restart was required.

## Remaining KEV-37 acceptance

Local issue 018 is partial and Linear KEV-37 remains In Progress. This completes
only the initial registration burst-protection step. Free cannot implement all
four independent edge limits as originally specified. Poll/session protection,
invalid-credential limits, handshake limits, exact per-minute registration
policy, client retry improvements and broader flood/load evidence remain.
Application limiters do not substitute for the missing edge acceptance criteria.
