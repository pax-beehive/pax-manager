# Secretary session list and progress fixes

## Changes and boundaries

- Resolve issue 055 by excluding internal Secretary work sessions in storage
  list predicates before COUNT and pagination. Source, reserved ID prefix, and
  the agent/session registry each identify internal work. User and agent lists
  agree; authorized direct session/history access remains available.
- Resolve issue 056 by replacing the wide coverage scan with early canonical
  type filtering, ordered SQL text hashing, compact metadata, and an eight-second
  request/statement budget. Domain helpers keep message type and hidden-envelope
  rules shared with canonical search reads.
- No schema/API generation changes, migration, new index, checkpoint changes,
  or deployment operation are required by this patch.

## Data flow

Normal session list requests apply ownership/team predicates and the internal
session predicate, then count and paginate. MemoryStore applies equivalent
visibility before sorting and pagination.

Secretary progress checks current owner/node/session visibility and replacement
message rules. PostgreSQL aggregates parts without adding separators, rejects
invalid indexes and blank canonical text, and computes SHA256. Go applies the
existing metadata-envelope visibility rules and compares current hashes with
published owner/canonicalization checkpoints. It accumulates message and turn
counts, then paginates session rows using the existing owner-bound cursor.

## Operational evidence and limitations

At 09:48 UTC, seven progress SELECTs were active for up to 19 minutes. They were
cancelled using the exact query prefix and pg_cancel_backend; no records were
modified. The queue continued progressing from 116 to 114 pending sources by
09:51 UTC. Some independent jobs had evidence/read-receipt or interrupted-turn
errors. This fix does not change durable execution retries or repair those jobs.

A bounded read-only EXPLAIN ANALYZE of the new query on the affected owner's
data returned 13,052 compact rows in 7,023 ms on its first run and 4,018 ms on a
repeat run, with no wide result sort. This is database execution time, not an end-to-end browser latency
guarantee. The live application still needs normal release deployment to use
the code change.
