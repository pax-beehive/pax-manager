# Secretary startup queue preservation

## Problem and scope

Issue [066](../issues/066-secretary-startup-requeues-completed-sessions.md)
tracks ordinary Manager restarts marking previously processed sessions pending.
The worker's startup call reused unconditional reconciliation: every source
advanced its desired revision and every tracked message received a new change
revision. Existing summaries and processed hashes survived, but the queue and
scheduling state changed unnecessarily.

The fix belongs to storage bootstrap and reconciliation. Search indexing,
Elasticsearch group projection, Secretary input views, model prompts, and board
behavior are separate. No API or generated artifacts need regeneration.

## Implementation and flow

`secretary_bootstrap_postgres.go` separates worker startup from explicit owner
reconciliation. The worker still calls `BackfillSecretaryJobs` once at startup.
That method opens a READ COMMITTED transaction, acquires a database/schema-scoped
advisory lock, and then selects repair work with a fresh statement snapshot.
Concurrent startups therefore see the first transaction's seeded state.

Ordinary sources only enqueue missing message state or older canonicalization
metadata. Missing jobs, ownership mismatches, and completed legacy sources
without the exact canonical rolling head receive a full source reconciliation.
The stable head SQL hash matches the domain identity, including UTF-8 owners and
the zero-byte separator. Pending first summaries do not trigger legacy repair.
Startup reads source metadata, not message bodies or model input.

Settings enable and manual retry use the same selector with full reconciliation
enabled for that owner. They retain their existing transaction lock order and
do not take the startup advisory lock. Processed messages absent from the current
source are included as tombstones, including deletion of the final message while
Secretary was disabled. Claim/publication can then replace the current head with
an empty, accurately covered summary.

## Preserved invariants

- Repeated startup preserves existing summaries, checkpoints, job revisions,
  active leases, retry deadlines, and retry budgets when no repair is needed.
- Startup may seed missing work and perform targeted compatibility repair.
- Explicit enable and manual retry reconcile changes made while disabled,
  including deleted source messages.
- Claims and publication retain current permission, version, and lease checks.
- Production queue rows are not manually acknowledged or reset by this branch.

## Verification

The old SQL failed real PostgreSQL regressions for all four scheduling states,
missing state, and disabled final-message deletion. The fixed PostgreSQL suite
passed those cases plus missing jobs, unused empty sessions, overlapping startup
transactions, owner transfer with an active lease, canonicalization repair,
SQL/domain identity parity, and existing legacy rolling-head migration.

Memory regressions cover ordinary restart scheduling and seed-once behavior.
Scripted transaction tests cover explicit reconciliation mode, isolation level,
transaction ownership, begin/lock/statement/commit failures, and rollback fences.
The new bootstrap Go functions have 100% unit statement coverage; SQL semantics
are verified separately against real PostgreSQL.

Passed commands, with `GOWORK=off` and the shared temporary Go cache:

- `make fmt-check`
- `make lint` (normal and integration tags)
- `go test -count=1 ./...`
- `go build -o /private/tmp/pax-manager-secretary-startup ./cmd/manager`
- `make secretary-acceptance`: 448 checks, no skips, including real HTTP/ACP/PG
- Targeted bootstrap tests with a coverage profile for the new Go functions

## Deployment and operational limits

No schema migration, input-policy bump, new environment variable, API change, or
generated artifact is required. Build and deploy the Manager normally. The fix
takes effect at the next startup; existing pending work continues through the
normal claim/hash/checkpoint path. This branch does not clear production queues,
rewrite old summaries, or acknowledge work without processing it.

Explicit enable/manual retry can still enqueue broad reconciliation on purpose.
Existing model/validation failures and historical status errors are separate;
this fix does not promise that every pending task will immediately complete.
Issue 066 is resolved by this change. No other issue changes status.
