# User attachment localization handoff

## Summary

This change adds the first user attachment slice across pax-manager and paxd.
An attachment belongs to a user and may optionally record a conversation ID. It
does not belong to an agent or node. The same attachment UUID can therefore be
localized again after the user changes the selected agent.

The first version deliberately does not delete attachments or localized files.
Agent-produced artifacts, artifact preview, and artifact download are outside
this slice.

## Module boundaries

- pax-manager owns attachment metadata, authorization, GCS upload tickets, and
  the decision to localize an attachment on the node selected for a prompt.
- GCS owns the uploaded source object. Browser uploads use a resumable upload
  initiation URL.
- The existing node-control tunnel carries ensure commands, status queries, and
  progress reports. No new transport is introduced.
- paxd owns the local partial file, verification, atomic ready manifest, and
  final `file://` URI.
- ACP only receives composed prompt blocks after every attachment is ready on
  the selected node.

## Persistence

pax-manager adds `user_attachments`.

Important columns are:

- `attachment_id`
- `owner_user_id`
- optional `conversation_id`
- filename, content type, size, and optional SHA-256
- GCS bucket, object, and generation
- upload status and timestamps

There is intentionally no agent ID or node ID. paxd adds no SQLite table. Its
filesystem manifest is the authoritative local state after restart.

## User upload API

Create:

```text
POST /api/v1/user/:user_id/attachments
```

Request:

```json
{
  "conversation_id": "",
  "filename": "notes.txt",
  "content_type": "text/plain",
  "size_bytes": 12,
  "sha256": ""
}
```

The response contains an attachment UUID, a `gcs_resumable` initiation ticket,
required headers, 256 KiB chunk alignment, and the completion URL. The client
POSTs to the initiation URL with `x-goog-resumable: start`, reads the resumable
session URL from the `Location` response header, and uploads chunks to that
session URL.

Complete:

```text
POST /api/v1/user/:user_id/attachments/:attachment_id/complete
```

Completion verifies GCS object attributes and is idempotent. Cross-user access
returns not found.

## Node-control contract

Ensure command:

```json
{
  "command_id": "cmdatt_...",
  "type": "attachment.ensure_local",
  "ensure_attachment_local": {
    "attachment": {
      "attachment_id": "att_...",
      "filename": "notes.txt",
      "content_type": "text/plain",
      "size_bytes": 12,
      "sha256": "",
      "generation": 7
    },
    "download": {
      "url": "https://signed-gcs-download",
      "expires_at": "2026-07-26T10:00:00Z"
    }
  }
}
```

The command ACK means accepted, not ready. paxd downloads in the background.

Status query:

```json
{
  "type": "attachment.local_status",
  "get_attachment_local_status": {
    "attachment_ids": ["att_..."]
  }
}
```

The response returns an item per requested UUID. States are `unknown`,
`queued`, `downloading`, `verifying`, `ready`, `failed`, and `paused`.

Progress report:

```json
{
  "type": "attachment.local_state",
  "attachment_local_state": {
    "attachment_id": "att_...",
    "state": "ready",
    "local_uri": "file:///.../notes.txt"
  }
}
```

pax-manager treats reports as an optimization. It polls the status query if a
ready report is lost. Ephemeral manager state is cleared when the node-control
connection is replaced or removed.

## paxd local layout

The default root is `~/.paxd/attachments`, configurable with
`daemon.attachment_dir` or `PAXD_ATTACHMENT_DIR`.

Each attachment uses:

```text
<root>/<attachment_id>/content.part
<root>/<attachment_id>/<safe filename>
<root>/<attachment_id>/ready.json
```

An existing partial file resumes with an HTTP Range request. paxd verifies the
declared size and optional SHA-256, renames the content atomically, then writes
the ready manifest through a temporary file and rename. After restart, the
manifest and final file are authoritative. There is no cleanup in this version.

## Conversation flow

The conversation request remains backward compatible with `input` and also
accepts ordered content blocks:

```json
{
  "content": [
    {"type": "text", "text": "Read this file"},
    {"type": "attachment", "attachment_id": "att_..."}
  ]
}
```

Before claiming or creating an ACP session, pax-manager:

1. verifies every UUID belongs to the caller and upload is completed;
2. queries local status on the node selected by the route;
3. sends ensure commands for missing attachments;
4. consumes pushed progress and polls status until ready;
5. converts attachment blocks to ACP `resource_link` blocks using the local
   `file://` URI;
6. sends the composed prompt.

The attachment record is never rewritten when the user changes agents.

## Generated artifacts

No Thrift or generated Hertz artifact changed. These endpoints follow the
existing manually registered artifact endpoint pattern. Store mocks did not
require regeneration.

Passing checks:

```bash

go test -count=1 ./...
go build -o /tmp/pax-manager-attachment-build ./cmd/manager

```

The attachment BDD coverage includes owner isolation, idempotent completion,
resumable partial download, restart manifest recovery, progress reports,
lost-ready-report polling, unsafe filename rejection, and reuse of one UUID on
different nodes.

`make lint` has no issue in the new attachment code. It remains non-zero on
pre-existing generated handler import formatting and five pre-existing unused
functions. `make fmt-check` also reports the pre-existing
`internal/manager/acp_history_test.go` import order before reaching later
format checks.

## Operational risks and assumptions

- The ACP peer is assumed to accept `resource_link` prompt blocks with
  `file://` URIs. This must be verified against each harness.
- GCS bucket CORS must allow the browser initiation request and expose the
  `Location` header.
- paxd begins downloading only after GCS finalizes the object in this version.
  Streaming paxd download while browser chunks are still uploading is not
  implemented.
- Download tickets expire after 15 minutes. Retrying the conversation issues a
  fresh ticket and resumes the partial file.
- Attachment cleanup, quotas, malware scanning, and artifact handling remain
  future work.
