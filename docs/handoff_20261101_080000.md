# Search source and FIFO queue indexes

## Scope

ISSUE-051 persists two partial indexes for the current FIFO search worker on
main a7c479a. Query text, owner checks, replacement semantics, durable revisions,
leases and acknowledgements remain unchanged. There are no generated artifacts
or production Go changes. PR 207's proposed priority lanes are independent; if
ClaimSearchBatch ordering changes, its index and plan verification must change
with it.

`db/init.sql` defines idx_messages_search_display_agent_session on
messages(agent_id, session_id), restricted to pax:invocation,
pax:invocation_pending and pax:artifact. The existing replacement query still
applies its agent/session scope and JSON list or parent fallback checks; the
index narrows the candidate display rows.

`db/search.sql` defines idx_search_sync_pending_fifo on
search_sync_state(available_at, kind, source_id), restricted to
desired_revision > indexed_revision. This matches the current claim order and
avoids sorting a large tied timestamp group. Availability, lease expiry and row
lock skipping continue to apply. All existing indexes are retained.

## Existing database rollout

Build both indexes online before deploying the fresh-schema definitions to a
busy database. Otherwise the normal startup IF NOT EXISTS definitions can build
missing indexes while writes are blocked. The online builds can improve plans
for the already-running Manager; a restart is not needed to use them.

Use the same approved PG connection environment and search_path as Manager.
Inspect existing names first:

```sql
SELECT n.nspname AS schema_name, c.relname AS index_name,
       t.relname AS table_name, i.indisvalid, i.indisready,
       pg_get_indexdef(i.indexrelid) AS definition
FROM pg_index i
JOIN pg_class c ON c.oid = i.indexrelid
JOIN pg_class t ON t.oid = i.indrelid
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = current_schema()
  AND c.relname IN ('idx_messages_search_display_agent_session',
                   'idx_search_sync_pending_fifo')
ORDER BY c.relname;
```

For an absent name, run its single-statement file using psql autocommit. Run and
verify each file independently, with ON_ERROR_STOP and without -1, BEGIN or a
migration tool that wraps the statement in a transaction. These per-connection
options preserve existing PGOPTIONS and append a 3-second lock timeout and a
120-second statement timeout, matching the bounded online operation:

```sh
PGOPTIONS="${PGOPTIONS:-} -c lock_timeout=3000 -c statement_timeout=120000" \
  psql -X -v ON_ERROR_STOP=1 -f db/migrations/20261101_search_display_index.sql
```

```sh
PGOPTIONS="${PGOPTIONS:-} -c lock_timeout=3000 -c statement_timeout=120000" \
  psql -X -v ON_ERROR_STOP=1 -f db/migrations/20261101_search_pending_fifo_index.sql
```

These files intentionally omit IF NOT EXISTS. An existing name is an error,
including an invalid leftover from an interrupted build. Skip that file only
after verifying the table, complete definition, indisvalid and indisready match
the intended index. A wrong or invalid index needs a separately reviewed repair;
the files never drop or silently replace it. Recheck the catalog after success.
Keep credentials in the approved private connection environment, not command
arguments or logs.

PostgreSQL's [CREATE INDEX documentation](https://www.postgresql.org/docs/current/sql-createindex.html)
explains why concurrent builds cannot run in a transaction block and why
IF NOT EXISTS does not verify an existing definition. Concurrent builds can
wait for existing transactions and briefly contend for metadata locks; they do
not remove the CPU/I/O cost of building an index.

## Verification

The new real-PG tests first failed against the old schema: the two catalog names
were absent, a 10,000-row tied queue used Incremental Sort over the old
availability index, and the replacement lookup scanned unrelated messages.
Replacement semantic cases already passed before the index change.

The green tests verify valid/ready catalog entries and exact key order, both
partial predicates, the exact captured ClaimSearchBatch UPDATE plan without Sort or Incremental Sort
(EXPLAIN without ANALYZE inside READ ONLY), and
a display lookup that selects the new partial index. Standalone concurrent files
succeed outside transactions and reject a second run with duplicate-relation
SQLSTATE 42P07. All three display types retain explicit replacement list behavior,
invalid/empty/missing-list parent fallback, agent/session scope and restoration
when the display is deleted. Fixtures use isolated schemas in a disposable local
PG instance. No new production Go statements were added, so ordinary unit
coverage has no new runtime-code denominator.

Passed checks:

- `GOWORK=off make fmt-check`.
- `GOWORK=off make lint`, including the integration build tag.
- `GOWORK=off GOCACHE=/tmp/pax-manager-go-cache go test -count=1 ./...`.
- `GOWORK=off GOCACHE=/tmp/pax-manager-go-cache go build -o /private/tmp/pax-manager-search-indexes-build ./cmd/manager`.
- Focused real PG: `go test ./internal/manager/storage -run '^TestSearchIndexesPostgres' -count=1`,
  with PAX_MANAGER_SEARCH_TEST_DATABASE_URL pointing to the disposable loopback PG.
- After strengthening the exact-claim plan test: formatting, affected storage
  tests/type checks, targeted storage lint and focused real-PG checks were repeated.

Validation logs are retained under `/private/tmp/pax-search-indexes-*.log`.

## Separate approved production operation

Both indexes were built online and their exact definitions, indisvalid and
indisready were verified. The display index took 1.038 seconds and occupied
16kB; FIFO took 4.281 seconds and occupied 18MB. Manager and ES were not restarted,
and no extra worker or temporary runner was started.

For one sampled source query, server execution fell from 335.584ms to 1.365ms;
broad bitmap candidates fell from 144,625 to 122 display records examined. The
same FIFO candidate sample fell from 190.602ms to 0.554ms, examining 20 rows
instead of 196,470, without sorting. These are sampled server execution times,
excluding planning, rather than end-to-end latency guarantees. The exact claim
UPDATE was also inspected using EXPLAIN without ANALYZE inside READ ONLY; the
probe executed no claim mutation and showed LockRows plus the FIFO index.

Between 2026-11-01 08:09:03.942 UTC and 08:12:04.191 UTC, current message-queue
acknowledgements rose from 34,179 to 37,059 over 180.249 seconds: 15.98 per second,
about 4.9 times the earlier 3.25 per second. At the final sample there were
231,243 message queue rows, 194,184 pending and two existing errors, unchanged.
Current acknowledgements represented 16.03 percent of that queue. Session-title
queue rows were current at 219/219. Queue acknowledgements include filtered or
tombstone work and do not measure searchable hits.

At that sampled rate the remaining message queue implied about 3.38 hours
(roughly three to four hours); new writes, retries and load can change it.
Historical backfill was still running. This patch does not change the worker's
20-record default batch or its one-second pause.
