# Remove remaining legacy journal startup backfills

The US release failed its 60-second health window while Manager was applying
db/init.sql. The restored Manager became ready after about 82 seconds, so the
release agent also recorded failed rollback and kept the target blocked even
though later local health probes returned the expected 200 and unauthenticated
401. SEARCH_URL was unset, and no ES process was involved in startup.

The earlier fix removed only the two historical queue watermark aggregations.
This change finishes removing automatic journal data conversion from schema
application: queue_id, direction, error_message and stream UPDATEs are deleted.
The modern table definitions, additive DDL, NOT NULL constraints and indexes
remain. No Go runtime code, API or generated artifacts change.

## Evidence and boundary

Read-only US plans showed sequential scans for direction and error conversion.
The journal heap was 2,681 MB; its total size including indexes and TOAST was
6,656 MB. A bounded read-only error-predicate query exceeded five seconds; this
does not establish an exact duration for the historical UPDATE or the whole
startup. Other diagnostic queries used two- or five-second statement limits and
read-only transactions. No production UPDATE, migration, vacuum, configuration
change, container restart or release recovery was performed.

Current normal and legacy write adapters already persist canonical journal
fields. Startup no longer repairs ancient rows or derives replay state from
history. Unsupported old layouts with missing required values need a deliberate
legacy data migration before upgrading. Constraints are not relaxed.

Background bounded journal retention is unchanged and still starts after the
store is opened. It intentionally deletes eligible completed history according
to the existing watermark and diagnostic-tail policy. Other application schema
migrations remain; this patch does not promise a universal startup time.
