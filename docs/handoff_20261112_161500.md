# Handoff: generic usage items and agent type ids

## Summary

The node user API for harness plan usage and native login now works with PAX
agent type ids instead of a fixed `claude|codex` pair, and plan usage is
returned as a generic `items` list so clients render it without per-harness
code. Issue 084 stays `partial`; see its current note.

## Module boundaries

- `internal/manager/userapi/harness_ids.go`: id format
  (`^[a-z0-9][a-z0-9_-]{0,31}$`), the `claude-code` -> `claude` native name
  mapping, and fallback display labels for Claude Code and Codex.
- `internal/manager/userapi/harness_auth.go`: auth status and login use the
  native name internally (claims, pending starts, paxd queries) and report the
  id the caller requested.
- `internal/manager/userapi/harness_usage.go` and `harness_usage_items.go`:
  usage query, item sanitization, and item synthesis for older paxd.
- `api/pax_manager.thrift`: `HarnessUsageItem`, `HarnessUsageView.items` and
  `harness_label`, and updated path parameter docs.

## Request flow

1. `GET /api/v1/user/:user_id/nodes/:node_id/harnesses/:harness/usage` and the
   `auth/status` and `auth/login` routes validate the id format, then the node
   owner and control tunnel as before.
2. Manager sends paxd the native name: `claude-code` and `claude` become
   `claude`; other ids are unchanged. The paxd response must name that native
   harness; Manager then rewrites `harness` to the requested id.
3. Usage: paxd `items` are sanitized per kind. When paxd sends no items (paxd
   before usage v2), Manager derives them from `windows` (`5-hour`, `Weekly`,
   `N-day`, `N-hour`, `N-minute`, plus ` middle-dot scope`) and `extra_usage`
   (`status` item `on`/`off`). Sanitized `windows` and `extra_usage` are still
   returned for older clients.
4. Agent types without native support: newer paxd returns state `unsupported`;
   older paxd returns `invalid_argument`, which Manager maps to `unsupported`
   for every id except Claude Code and Codex (where it stays
   `daemon_unsupported` for usage and a 400 for auth). Login starts for such
   agent types are forwarded and the paxd rejection is returned as 400.

## Item rules

- Common: `id` `[a-z0-9_]{1,64}` (first duplicate wins), `label` required
  (account field sanitizer, 64 bytes), `kind` `percent|amount|status` (others
  dropped), optional `severity` `normal|warning|critical`. At most 20 items,
  only when `state` is `available`.
- `percent`: `used_percent` 0..100 required; optional `window_minutes`
  1..44640 and RFC 3339 `resets_at`.
- `amount`: `used` >= 0 required; optional `limit` > 0, `unit`
  `usd|eur|cny|credits|tokens|requests`, `resets_at`.
- `status`: `value` required (64 bytes).
- An invalid optional field is dropped alone; an invalid required field drops
  the item. `harness_label` (64 bytes) is kept in every state.

## Risks and assumptions

- Clients should render `items`; `windows` and `extra_usage` will be removed
  once all nodes run paxd with items.
- Labels are English text chosen by paxd adapters; a client may override known
  item ids for translation.
- An older paxd answering `invalid_argument` for a supported harness with a bad
  session id would be reported as an error, not `unsupported`, because Claude
  Code and Codex are excluded from that mapping.
