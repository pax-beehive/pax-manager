# Capability Injection and Runtime State Design

## Summary

Pax needs a capability injection foundation that can support session knowledge
transfer, handoff skills, MCP tools, local tools, and future agent-to-agent
delegation. The capability layer should not be implemented as prompt string
concatenation or one-off mailbox commands. It should be modeled as control-plane
state with explicit assignment, runtime installation, activation boundaries, and
auditability.

The runtime state layer is a prerequisite. Capability activation must happen at
well-defined session and turn boundaries. A capability revision should never
change in the middle of a running turn.

## Design Goals

- Keep pax-manager as the control plane for capability definitions,
  assignments, approval policy, and runtime state projection.
- Keep paxd as the node runtime that installs capability packages, reports
  installation state, and freezes effective capability revisions before turns.
- Treat mailbox and WebSocket messages as notification and delivery paths, not
  as the source of truth for installed capabilities.
- Make ACP, Hermes, Codex, and future agent backends adapters into the same Pax
  runtime state model.
- Keep WebSocket transport logic thin by moving frame handling into
  middleware-like hooks.
- Preserve concurrent correctness when downstream agent frames and upstream user
  frames arrive at the same time.

## Terms

- Capability package: A versioned ability that can be injected into an agent
  runtime. Examples include a skill bundle, MCP server config, local tool,
  A2A agent card, or handoff bundle.
- Capability assignment: A policy binding that says which node, agent, session,
  message, or handoff scope should receive a package.
- Capability installation: paxd local state describing whether a package was
  fetched, verified, installed, failed, or removed.
- Capability activation: The point where an installed package becomes part of
  the effective runtime context for a turn.
- Capability revision: A monotonic revision for the effective capability set.
  A turn must record the revision it used.
- Runtime state: Pax's canonical projection of a session or turn state, derived
  from backend events such as ACP frames, Hermes session polling, and paxd
  executor events.

## Source Of Truth

The source of truth should be capability registry and assignment storage in
pax-manager:

```text
capability_packages
- package_id
- owner_user_id
- kind
- name
- version
- digest
- manifest
- artifact_ref
- inline_content
- created_at
- deleted_at

capability_assignments
- assignment_id
- package_id
- owner_user_id
- scope_type
- node_id
- agent_id
- session_id
- message_id
- policy
- activation
- priority
- expires_at
- created_at
- revoked_at
```

The mailbox should only poke paxd that capabilities changed:

```json
{
  "entity_type": "capability",
  "event_type": "sync",
  "revision": 17
}
```

paxd should then fetch the full desired state from a node API, apply it locally,
and report installation status.

## Runtime State Model

Pax should own a canonical state model instead of exposing raw ACP or Hermes
state directly:

```text
SessionRuntimeState
- owner_user_id
- node_id
- agent_id
- session_id
- lifecycle
- active_turn_id
- active_prompt_request_id
- blocked_reason
- blocked_ref
- active_tool_calls
- pending_approval_id
- last_stop_reason
- last_error
- capability_revision_active
- capability_revision_pending
- updated_at
```

Recommended lifecycle values:

```text
idle
running
waiting_approval
blocked
cancelling
errored
```

Recommended blocked reasons:

```text
tool_approval
secret_approval
capability_install
user_input
agent_unavailable
unknown
```

Runtime state should be generated by events rather than direct frame-specific
mutation:

```text
RuntimeEvent
- prompt_started
- prompt_completed
- prompt_failed
- tool_call_pending
- tool_call_started
- tool_call_completed
- permission_requested
- permission_resolved
- capability_install_started
- capability_install_completed
- capability_install_failed
- session_cancelled
```

The reducer that applies these events should be the only place that decides the
final lifecycle. This keeps ACP, Hermes, and other backend adapters small.

## ACP Frame Pipeline

The ACP tunnel should become a frame pipeline. The tunnel owns transport,
pairing, and socket writes. Middleware owns protocol-aware behavior.

Proposed package shape:

```text
internal/manager/acp/
  tunnel.go
  frame.go
  pipeline.go
  approval_middleware.go
  runtime_state_middleware.go
  capability_prompt_middleware.go

internal/manager/runtime/
  state.go
  events.go
  reducer.go
  store.go
```

The pipeline should look like HTTP middleware:

```go
type FrameDirection string

const (
	DirectionAgentToUser FrameDirection = "agent_to_user"
	DirectionUserToAgent FrameDirection = "user_to_agent"
)

type FrameContext struct {
	OwnerUserID string
	NodeID      string
	AgentID     string
	SessionID   string
	Direction   FrameDirection
	MessageType int
	Frame       JSONRPCFrame
	Raw         []byte
}

type FrameHandler func(context.Context, *FrameContext) error

type FrameMiddleware interface {
	HandleFrame(context.Context, *FrameContext, FrameHandler) error
}
```

Middleware examples:

- Approval middleware handles `session/request_permission`, reusable grants,
  and allow-always option injection.
- Runtime state middleware observes prompt, update, permission, and response
  frames, then emits runtime events.
- Capability prompt middleware injects effective skill context into
  `session/prompt` only before the prompt reaches the agent.
- Audit middleware records important normalized events without requiring the UI
  to understand backend-specific frames.

## ACP State Projection

ACP has useful event granularity, but it does not provide a complete standard
session snapshot with fields like `blocked_reason`,
`capability_revision_active`, or `capability_revision_pending`. Pax should infer
canonical state from the ACP JSON-RPC stream.

Mapping rules:

```text
user -> agent session/prompt
  RuntimeEvent: prompt_started
  lifecycle: running

agent -> user session/update tool_call status=pending
  RuntimeEvent: tool_call_pending
  lifecycle: running

agent -> user session/request_permission
  RuntimeEvent: permission_requested
  lifecycle: waiting_approval
  blocked_reason: tool_approval

user -> agent response to session/request_permission
  RuntimeEvent: permission_resolved
  lifecycle: running

agent -> user session/update tool_call status=in_progress
  RuntimeEvent: tool_call_started

agent -> user session/update tool_call status=completed|failed
  RuntimeEvent: tool_call_completed

agent -> user response to session/prompt
  RuntimeEvent: prompt_completed or prompt_failed
  lifecycle: idle or errored
```

The ACP observer should track outstanding JSON-RPC request ids so responses can
be correlated with `session/prompt` or `session/request_permission`.

## Concurrency Safety

The WebSocket tunnel has two independent directions. Runtime state projection
must be correct when frames from both directions arrive concurrently.

Required rules:

- The transport layer should continue to use independent write locks per
  downstream and upstream socket.
- Runtime state updates must be serialized per session. Use a per-session lock,
  a single reducer goroutine per active session, or transactional compare and
  swap in storage.
- Middleware must not hold socket write locks while calling storage or other
  middleware that can block.
- Middleware may mutate the frame payload only before it is forwarded.
- Observer middleware should be idempotent where possible. Replayed or duplicate
  frames should not corrupt state.
- JSON-RPC request id correlation must be scoped by connection and session.
- A prompt turn should freeze `capability_revision_active` before forwarding
  the prompt to the agent.
- If a new assignment arrives while a turn is running, it should set
  `capability_revision_pending`; it must not alter the active revision.
- Runtime state should prefer monotonic transitions, for example a completed
  prompt response should close outstanding tool calls for that turn.

## Capability Activation Rules

```text
session idle
  Safe to activate immediately after package installation succeeds.

session running
  Do not change active capability set. Record pending revision for next turn.

session waiting_approval
  Do not change executable tools for the current turn. Non-executable context
  may be queued, but default behavior should still be next_turn.

session blocked on capability_install
  Resume activation only after paxd reports installation success.

session errored or cancelled
  Activation may proceed, but should record activation_reason for audit.
```

Each turn result should record:

```text
capability_revision_used
capability_packages_used
```

This is required for reproducibility and audit.

## User-Facing Display

User APIs should expose normalized runtime state on session reads and lists.
The UI should not need to parse ACP directly.

Example:

```json
{
  "status": "waiting_approval",
  "current_task": "Run shell command",
  "blocked_reason": "tool_approval",
  "active_tool_calls": [
    {
      "tool_call_id": "call_001",
      "kind": "execute",
      "title": "go test ./...",
      "status": "pending"
    }
  ],
  "capability_revision_active": 12,
  "capability_revision_pending": 13
}
```

The external WebSocket should publish normalized events:

```json
{
  "entity_type": "session_runtime",
  "event_type": "state_changed",
  "agent_id": "agent_123",
  "session_id": "sess_123",
  "state": {
    "lifecycle": "waiting_approval",
    "blocked_reason": "tool_approval"
  }
}
```

Suggested display labels:

```text
idle: Ready
running: Working
waiting_approval: Waiting for approval
blocked: Blocked
cancelling: Cancelling
errored: Error
```

## Implementation Sequence

1. Extract ACP frame parsing and forwarding into a pipeline without changing
   external behavior.
2. Move the current ACP approval grant logic into approval middleware.
3. Add runtime event and state reducer with in-memory store support.
4. Add runtime state middleware that observes ACP frames and emits events.
5. Persist runtime state into `agent_sessions.metadata.runtime_state` or typed
   columns after the state shape stabilizes.
6. Expose normalized runtime state on session list/get responses.
7. Add capability registry and assignment tables.
8. Add paxd capability sync and installation status reporting.
9. Add capability activation hooks around prompt start and prompt completion.
10. Add backend-specific adapters for skill bundles, MCP servers, local tools,
    and A2A agent cards.

## Testing Requirements

Code changes in this area must include unit tests and integration tests.

Unit tests:

- Frame parser accepts valid JSON-RPC requests, responses, notifications, and
  preserves unknown extension fields.
- Pipeline preserves frame order within one direction.
- Pipeline allows middleware to mutate frames before forwarding.
- Approval middleware keeps existing reusable grant behavior.
- Runtime state middleware emits correct events for prompt start, tool call
  updates, permission requests, permission responses, prompt completion, prompt
  errors, and cancellation.
- Runtime reducer handles duplicate events idempotently.
- Runtime reducer closes a running turn when the prompt response arrives.
- Capability activation freezes active revision at prompt start.
- New assignments during running turns become pending revisions, not active
  revisions.
- Per-session concurrent event application is race-safe under `go test -race`
  where practical.

Integration tests:

- ACP user tunnel and agent tunnel still relay transparent frames end to end.
- `session/request_permission` still supports reusable approval grant auto-allow.
- ACP prompt flow updates session runtime state from idle to running to idle.
- ACP permission flow updates runtime state to `waiting_approval` and back to
  running after decision.
- A capability assignment created while a session is idle activates immediately
  after paxd reports installation success.
- A capability assignment created while a session is running is reported as
  pending and activates on the next prompt.
- Session list/get responses include normalized runtime state.
- External WebSocket emits normalized `session_runtime.state_changed` events.

## Notes

- ACP supports `_meta` fields and custom methods for extension, but Pax should
  not rely on backend-specific `_meta` fields for core runtime safety.
- The capability design should treat MCP and A2A as package kinds or adapters,
  not as the internal source of truth.
- The current paxd Hermes collector reports coarse session status. ACP runtime
  projection should augment, not replace, collector reports.
- Capability package installation may require approval for executable or remote
  tool kinds. Reuse the existing `agent_approvals` model with a new
  `domain=capability`.
