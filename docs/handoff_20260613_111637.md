# pax-manager Handoff

Timestamp: 20260613_111637

This document captures the current design intent, module boundaries, request
flows, generated-code workflow, and local/deployment practices for pax-manager.

## Purpose

pax-manager is the cloud control plane for paxd agents. It stores tenant users,
agents, session snapshots, mailbox messages, offsets, registration tokens, and
platform API keys in PostgreSQL. The production paxd path is websocket-based
after agent registration, while HTTP agent endpoints remain available for
compatibility and integration testing.

Core data flow:

```text
Browser user -> Cloudflare Access -> pax-manager -> PostgreSQL
paxd         -> pax-manager websocket -> PostgreSQL
paxd         -> pax-manager HTTP agent endpoints -> PostgreSQL
paxd         -> local Hermes API on the user machine
```

The cloud service does not initiate inbound connections to machines running
paxd. Agents connect outbound to Cloud Run.

## Module Layout

```text
cmd/manager
  Thin production entrypoint.

  Local mock paxd client for exercising the HTTP agent path.

  - internal/manager/openapi_generated.json

  API contract source of truth for Hertz models, generated route handlers, and
  OpenAPI metadata.

  Application assembly, Hertz handlers, transport adapters, websocket handling,
  OpenAPI serving, and compatibility aliases.

internal/manager/auth
  User identity resolution, admin policy, registration token ownership, secret
  generation and hashing, and Cloudflare Access JWT verification.

internal/manager/config
  Environment-driven configuration and built-in admin merge logic.

internal/manager/domain
  Core domain structs, errors, store interface, mailbox helpers, token usage
  parsing, and tenant ownership helpers.

internal/manager/paxd
  paxd-facing business service. Handles agent registration, status reports,
  mailbox pulls, offset updates, and message results.

internal/manager/userapi
  user-facing business service. Handles tenant-scoped user views, mailbox
  creation, user API key records, and agent registration token creation.

internal/manager/storage
  PostgreSQL and in-memory store implementations.

internal/transport/http
  Hertz generated model, route, and handler scaffolding.

integration
  Build-tagged end-to-end tests that run against Docker Compose.
```

## Deep Module Boundaries

Business modules are intentionally deeper than transport packages.

The `paxd` package depends on interfaces for storage, registration ownership,
and secrets. It does not know about Hertz request contexts.

The `userapi` package depends on interfaces for storage, principal resolution,
and secrets. It does not know about Hertz request contexts.

The `auth` package owns identity resolution rules. It does not own the transport
or storage implementation, only the interfaces needed to ensure users and
resolve registration tokens.

The `storage` package owns SQL and in-memory persistence details. Business
packages should not construct SQL queries or inspect database-specific errors.

The top-level `internal/manager` package wires dependencies and adapts Hertz,
OpenAPI, websocket, and HTTP concerns into the deeper modules.

## Authentication

### User-Facing APIs

User-facing APIs are protected by Cloudflare Access JWT assertions in
production. The trusted header is:

```text
Cf-Access-Jwt-Assertion
```

The verifier checks:

- JWT signature against Cloudflare Access JWKS
- issuer
- audience
- expiry
- not-before
- email claim

Cloudflare validation is enabled by default. Local development must explicitly
disable it:

```text
CLOUDFLARE_ACCESS_DISABLED=true
ALLOW_LOCAL_USER_HEADER=true
```

When local fallback is enabled, `X-User-Email` is accepted and missing users are
registered automatically through `EnsureUser`.

Production must not set:

```text
CLOUDFLARE_ACCESS_DISABLED=true
ALLOW_LOCAL_USER_HEADER=true
```

### Admins

There are built-in admin emails in code. `ADMIN_EMAILS` extends that set; it
does not replace it.

Admin status is derived from the current config on each request. It is not
trusted from the persisted user role alone. This prevents stale admin rows from
keeping cross-tenant access after config removal.

### paxd Registration

Preferred registration flow:

1. A user calls `POST /api/user/agent-registration-tokens`.
2. pax-manager stores a hash of the one-time registration token.
3. paxd calls `POST /api/agent/register` with `X-Registration-Token`.
4. pax-manager creates the agent under the token owner and returns an agent API
   key once.

`REGISTRATION_TOKEN` exists as a bootstrap escape hatch. Prefer owner-bound
user-minted registration tokens.

### paxd Runtime Auth

paxd uses the agent API key returned by registration.

HTTP agent endpoints use:

```text
Authorization: Bearer <agent_api_key>
```

The websocket path uses:

```text
X-Pax-Key: <agent_api_key>
```

`/api/agent/ws` accepts optional `agent_id` and `session_id` during handshake.
If `agent_id` is present, it must match the authenticated agent key.

## Tenancy Model

`users` is the tenant identity table.

`agents.owner_user_id` is the primary tenant boundary.

`mailbox.owner_user_id` duplicates ownership for direct filtering and query
simplicity.

`agent_sessions` inherits ownership through `agent_id`.

Normal users only see owned data. Admins can list and act across tenants.
Cross-tenant access should return not found where that avoids exposing another
tenant's object existence.

## Core Request Flows

### User Registration and Agent Registration

```text
GET /api/user/agents
  -> auth.Principal
  -> EnsureUser(email)
  -> userapi.ListAgents

POST /api/user/agent-registration-tokens
  -> auth.Principal
  -> userapi.CreateRegistrationToken
  -> storage.CreateRegistrationToken(hash)

POST /api/agent/register
  -> auth.RegistrationOwner
  -> paxd.RegisterAgent
  -> storage.RegisterAgent(owner, hashed agent key)
```

### paxd Status

```text
POST /api/agent/status
  -> AgentAuth middleware
  -> storage.AuthenticateAgent(hash)
  -> paxd.ReportStatus
  -> storage.UpsertAgentStatus
  -> agents and agent_sessions are upserted
```

Session input follows paxd field names, using snake case and string timestamps.
`token_usage` accepts object or numeric forms through domain parsing.

### Mailbox Over HTTP

This older flat user route example is superseded by the nested REST routes:
`POST /api/user/agents/{agentId}/sessions/{sessionId}/messages` for
session-scoped messages and `POST /api/user/agents/{agentId}/messages` for
bootstrap or agent-level messages.

```text
POST /api/user/message
  -> auth.Principal
  -> userapi.CreateMailboxMessage
  -> storage.CreateMailboxMessage

GET /api/agent/mailbox?offset=0&limit=10
  -> AgentAuth
  -> paxd.PullMailbox
  -> storage.PullMailbox
  -> pending messages are marked delivered

POST /api/agent/messages/{messageId}/result
  -> AgentAuth
  -> paxd.ReportMessageResult
  -> storage.MarkMessageResult

POST /api/agent/messages/offset
  -> AgentAuth
  -> paxd.UpdateOffset
  -> storage.UpdateOffset
```

### Mailbox Over Websocket

Handshake:

```text
GET /api/agent/ws?agent_id=<agent_id>&session_id=<session_id>
X-Pax-Key: <agent_api_key>
```

The server sends:

```json
{
  "type": "connected",
  "code": 200,
  "message": "ok",
  "data": {
    "agent_id": "agent_...",
    "owner_user_id": "usr_...",
    "session_id": "sess-..."
  }
}
```

Supported request frame types:

```text
status
report_status
pull_mailbox
update_offset
message_result
report_message_result
```

All websocket responses use:

```json
{
  "type": "<type>_result",
  "request_id": "...",
  "data": {},
  "code": 200,
  "message": "ok"
}
```

## API Contract and Generated Artifacts

The IDL source of truth is:

```text
api/pax_manager.thrift
```

Hertz generated code lives under:

```text
internal/transport/http
```

The in-repo OpenAPI generator writes:

```text
internal/manager/openapi_generated.go
internal/manager/openapi_generated.json
```

`openapi_generated.go` currently contains IDL route registration helpers.
`openapi_generated.json` is embedded by `internal/manager/openapi.go` through
`go:embed`.

`/openapi.json` serves the embedded JSON after patching `servers[0].url` from
the current request host and forwarded protocol.

`/openapi` serves a lightweight UI that fetches `openapi.json` with a relative
URL so path-prefixed deployments do not accidentally fetch from the wrong root.

Regenerate derived artifacts with:

```bash
make generate
```

Do not manually edit generated files unless a generator migration is in
progress and the generated state is intentionally being corrected.

## Persistence

DDL is in:

```text
db/init.sql
```

The production store uses pgx through `database/sql`. The application runs
`EnsureSchema` on startup, which applies `db/init.sql`.

Tables:

```text
users
agents
agent_sessions
mailbox
message_offsets
agent_registration_tokens
user_api_keys
```

Secrets are stored only as hashes. Plain registration tokens, agent keys, and
user platform API keys are returned once.

## Local Development

Run with in-memory storage:

```bash
make run-memory
```

Run with local Postgres:

```bash
make db-up
make run
```

Local run targets set:

```text
CLOUDFLARE_ACCESS_DISABLED=true
ALLOW_LOCAL_USER_HEADER=true
```

Docker Compose:

```bash
make up
make down
```

The normal compose stack uses port 9879 and a persistent local Postgres volume.

## Integration Tests

Integration tests are behind the `integration` build tag:

```bash
go test -tags=integration -count=1 ./integration
```

Preferred command:

```bash
make integration-test
```

That command uses:

```text
docker-compose.integration.yml
project: pax-manager-integration
port: 19879 -> 9879
```

It creates an isolated volume and intentionally resets it on each run. This
avoids stale local development database state.

Stop the integration stack with:

```bash
make integration-down
```

The integration flow covers:

- health
- OpenAPI JSON
- user auto-registration
- user platform API key create/list/revoke
- agent registration token minting
- paxd registration
- paxd HTTP status report
- user agent/session reads
- user mailbox create
- paxd HTTP mailbox pull/result/offset
- paxd websocket status/pull/result/offset
- tenant isolation

## Deployment

Cloud Build config:

```text
cloudbuild.yaml
```

Defaults:

```text
region: us-west1
repository: pax-manager
service: pax-manager
max instances: 5
timeout: 30s
```

Cloudflare Access values are non-secret env vars in Cloud Run:

```text
CLOUDFLARE_ACCESS_ISSUER
CLOUDFLARE_ACCESS_AUD
CLOUDFLARE_ACCESS_JWKS_URL
```

`DATABASE_URL` contains credentials and should come from Secret Manager.

Cloud SQL with Cloud Run should use the Cloud SQL connection configured on the
Cloud Run revision and a Unix socket style `DATABASE_URL`.

Do not set Cloud Run's reserved `PORT` env var manually. Cloud Run injects it.
The deploy command uses `--port 9879` for the container port.

## Security Notes

Cloud Run is deployed with `--allow-unauthenticated` because Cloudflare Access
is expected to sit in front of user-facing routes and paxd must connect from
outside the private network.

Application-level protections:

- Cloudflare Access JWT validation for user APIs
- agent key auth for paxd HTTP routes
- `X-Pax-Key` auth before websocket upgrade
- per-client in-memory API rate limits
- request body size cap
- tenant filtering in storage
- generated OpenAPI exposes the expected security headers

Cloudflare and Cloud Run ingress rules are still important. Use Cloud Armor or
equivalent edge controls for large traffic attacks and path-level edge rules.

## Current Operational Gotchas

The normal local Docker volume can become stale if it was initialized before
`POSTGRES_DB=paxdb`. Use `make db-reset` only when it is acceptable to recreate
that local volume.

The integration stack is isolated and safe to reset.

Some sandboxed local commands emit:

```text
go: writing stat cache: mkdir ... operation not permitted
```

The command can still be successful if the exit code is 0.

## Handoff Practice

For substantial architecture, deployment, generated-code, authentication, or
test workflow changes, add a handoff document:

```text
docs/handoff_<YYYYMMDD_HHMMSS>.md
```

The handoff should explain:

- what changed
- why the design is shaped that way
- core request flows
- module boundaries
- generated artifacts
- local/deployment commands
- validation already run
- known risks or gotchas

Keep handoff documents in English and ASCII only.
