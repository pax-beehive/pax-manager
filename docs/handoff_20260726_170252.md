# Cloud Build VM SSH key reuse handoff

## Summary

The VM deployment pipeline now generates one short-lived SSH key under
`/workspace` and reuses it across every `gcloud compute ssh` and `scp` step.
The first VM connection retries while the OS Login key propagates.

This fixes deployments that successfully built and pushed an image but failed
at `prepare-vm` with `Permission denied (publickey)`.

## Deployment flow

`cloudbuild.vm.yaml` performs these steps:

1. Build and push the commit-addressed manager image.
2. Remove stale Cloud Build OS Login keys.
3. Generate one build-scoped key at
   `/workspace/.ssh/pax-manager-cloud-build`.
4. Retry the first VM connection up to six times with a five-second delay.
5. Reuse the same key to copy scripts, bootstrap the VM, and deploy the image.

The key still expires through `_SSH_KEY_TTL`, which defaults to 30 minutes.
No production authentication defaults or VM IAM roles changed.

## Verification

The YAML parses successfully with Ruby's standard YAML parser. The completed
Cloud Build is the end-to-end verification because OS Login propagation and VM
access cannot be reproduced by local unit tests.

## Operational notes

- A failed first SSH attempt is expected while OS Login propagates.
- If all six attempts fail, inspect the Cloud Build service account's OS Login
  role and the VM's OS Login configuration.
- The build-scoped private key exists only in the ephemeral Cloud Build
  workspace.
