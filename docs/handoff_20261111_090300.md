# Incremental Secretary progress

## Goal and scope

Issue 079's first replacement-query optimization still hashed all visible history
on every progress refresh. This follow-up persists progress independently of
summary execution so caught-up reads do not access messages or parts. Existing
global counts, current visibility, completion hashes and source cursors remain
authoritative. Summary generation, ES indexing, job recovery and retry budgets
are unchanged. The earlier status-scope correction remains in the same PR.

## Projection and lifecycle

`db/secretary.sql` adds owner bootstrap/version state, per-message hash/completion
rows, per-session counters and a coalescing generation queue. No new table stores
body text, evidence or summary payloads. Source changes feed from transactional
`search_sync_state` desired revisions; indexing acknowledgements do not enqueue.
Checkpoint changes and internal-session registration have separate triggers.
Enqueue retains owners from the current source, cached projection and committed
dirty rows, with reverse indexes for each message lookup. Tables intentionally
have no source FKs so tombstones survive deletion.

The Manager starts an optional projection worker regardless of ES configuration,
Secretary enabled state or agent availability. Each step handles at most 128
committed dirty messages. Live changes precede backfill; remaining capacity stages
one bounded historical page. Successful steps wait 100 ms. Errors back off from
100 ms to 10 seconds, each step has a five-second context, and shutdown cancels
and waits before storage closes.

Existing inactive owners are initialized on their first progress read. Source
changes also discover owners. Bootstrap captures a message-ID upper bound and
persists its keyset cursor. Raw pages are limited before owner/type filtering,
so a sparse owner cannot cause an unbounded scan in one step. This may require
several metadata pages across other owners' history; it exposes none of their
data. Deployment performs no historical DML or all-user bootstrap. Policy version
changes clear that owner's projection and rebuild; visibility/count-rule changes
must bump the projection policy in addition to canonicalization version changes.

## Concurrency and reads

Writers take a database/schema-scoped advisory transaction try-lock. Dirty rows
are locked through canonicalization, affected-session counter recomputation and
acknowledgement of their exact generation. Source state/checkpoints are never
locked or changed by progress. Counters rebuild only from cached message rows
for affected sessions. Current source hashes use the existing canonical visible
parts/metadata and replacement rules, limited to changed message IDs.

Historical staging and first canonicalization MUST use separate committed
transactions. Otherwise a concurrent deletion/owner move can see neither the
uncommitted queue nor the first projection, losing its old-owner cleanup event.
Committing discovery first lets enqueue's dirty-owner union serialize every such
change against an in-flight projection, even before any cached message exists.

A clean read uses one read-only repeatable-read snapshot: owner policy/bootstrap
ready, no owner dirty rows, current source scope checks on both global counters
and SQL-paginated session rows. Neither original-content table is queried.
If not ready, bounded request preparation stages up to 256 rows, commits, then
refreshes up to 256 previously committed dirty messages in a fresh transaction.
Remaining work, writer contention or serialization/deadlock races return the
preparing sentinel. The existing eight-second request ceiling remains in place.
No unbounded full-history fallback exists. MemoryStore retains its in-memory
implementation and does not start a projection worker.

User API maps preparing to HTTP 503 with the fixed safe message
`Secretary progress is updating. Please try again shortly.` Successful response
shape, count meaning, lexical source ordering and owner-bound cursors are intact.
Console companion PR 248 recognizes this specific response, hides old counts and
rows, and displays updating while retaining the existing refresh/polling behavior.
Other errors keep their ordinary unavailable treatment.

## Verification and operational boundary

New PostgreSQL acceptance compares projected pages with the full canonical SQL
oracle across parts, grouping, source moves, deletion, publication, disabled state,
ACL/node/archive/internal changes, policy rebuild and pagination. Tests hold both
original-content tables and the writer lock while a clean read succeeds, prove
bounded restartable bootstrap with live traffic, and deterministically fence
concurrent parts, deletion and first-projection cross-owner moves using advisory
barriers and `pg_blocking_pids`. Driver tests cover rollback and failure paths;
worker/API tests cover backoff, cancellation and safe preparing responses.

Validation passed:

- Exact `make secretary-acceptance`: 1565 named checks, no skips; storage
  completed in 86.796 seconds, within the existing 300-second CI limit.
- Full `GOWORK=off GOCACHE=/tmp/pax-manager-go-cache go test -count=1 ./...`.
- New projection storage: 215/223 statements, 96.4% coverage; public progress
  read and existing canonical SQL builders/scanner: 100%.
- Worker/API targeted race tests; worker functions have 80/100/100/100% coverage.
- Nine new real-PG projection tests and ten schema/feed tests, including the
  deterministic deletion and initial cross-owner move races.

- Normal/integration lint, formatting/diff checks and Manager build passed.
- Console: 170 relevant tests, TypeScript, changed-file ESLint and Prettier passed.

No production mutation or deployment was performed. Deployment must include both
Manager and Console;
existing history can briefly show updating while its progress projection warms.
Old unknown executions and exhausted invalid-output budgets still require their
existing owner-controlled recovery, as documented in issue 074. This projection
does not claim to repair unrelated summary-execution failures.
