# Secretary owner controls

## Scope

Adds persistent owner defaults, persistent per-session requirements, frozen
one-operation requirements, guided reprocessing, human completion of exact
message selections, and human edits as immutable summary revisions. It also
includes the recurring-activity prompt improvements from PR #246.

Issue 085 is partial until deployment and actual long-session outcomes are
verified. No production data, model tasks, or deployment configuration were
changed during implementation. Cross-session relations and board maintenance
remain out of scope.

## Boundaries and flow

- Domain contracts: `secretary_guidance.go`, `secretary_operations.go`, and the
  optional snapshot/operation fields on `SecretaryJob`.
- User API: `userapi.SecretaryControlService` derives owner identity from the
  authenticated principal. It validates bounded input and returns fixed safe
  error messages. HTTP handlers reject duplicate, unknown, null, incorrectly
  cased, and malformed fields. Body input cannot specify an owner.
- Storage: both MemoryStore and PostgresStore implement guidance and operation
  stores. The only new tables are `secretary_guidance` and
  `secretary_operations`. Existing summary versions gain authorship metadata;
  existing message state gains an exact acknowledged change revision.
- Guidance writes use independent scope revisions. Empty text clears a scope.
  They do not alter settings, leases, retry epochs, or existing progress.
- Preparation freezes complete visible message identities, previews, applicable
  guidance and baseline summary revisions. Submission verifies source identity
  and baseline heads again, and uses an owner-scoped idempotency key.
  Canonical identity is the message ID, canonicalization version, content hash,
  role and source ownership. A scan change revision is a processing locator,
  not a new content version: reconciliation can reassign it to identical text.
- Guided operations reuse existing model batches, attempts, recovery, and
  bounded retry behavior. The same instructions persist across batches and
  retries. An explicit replacement supersedes earlier unsuccessful operations.
  An explicit selected batch only requires stale-node repairs whose entire
  unresolved source set is present in that batch. Other repairs remain pending
  and do not expand the selected operation's scope.
- Human completion publishes and acknowledges selected exact message changes in
  one transaction. Provenance is a separate subset. The contiguous source
  cursor only advances across acknowledged work, preserving earlier holes.
- Manual completion acknowledges the selected current messages' same-origin
  repair notifications in the existing invalidation table. Older summaries
  remain stale and unchanged, but do not force another model retry for that
  manually completed change. Later source changes reset the notification
  acknowledgement. Unselected or cross-origin repairs remain pending.
- Human edit inherits sources on the server and publishes a new revision;
  it adds no message progress. Both human paths fence old execution before it
  can publish stale output. They require no model or enabled Secretary.
- Task/status readers include explicit unfinished operations even if the
  original message cursor was complete. `operation_id` allows the Console to
  reopen that operation after a page reload. Completed-message counts are not
  reset for reprocessing.
- Summary contents and sources remain in PG; current versions use existing
  asynchronous ES indexing. ES is not required to view or manually save a
  summary. No new search or model engine is introduced.

## HTTP contract

All paths are under `/api/v1/user/:user_id/secretary`:

- `GET /guidance?scope=user|session&source_id=...`
- `PUT /guidance?scope=user|session&source_id=...`
- `POST /operations/prepare`
- `GET /operations/:operation_id`
- `POST /operations/:operation_id/submit`

The canonical source ID is the Manager agent_sessions primary key, not an ACP
native session ID. Operation kinds are `guided_summary`, `human_summary`, and
`human_edit`; selection scopes are `pending`, `all`, and `selected`.

Guidance caps at 8192 UTF-8 bytes and 4096 Unicode characters per scope.
Preparation caps at 4096 target messages without silent truncation. Advanced
selected-ID input permits a bounded subset of a larger source. Representative
provenance caps at 512 references. Title/body input and the final bound summary
state have separate capacity validation.

## Release and operational notes

- Deploy Manager before Console controls are used. Manager applies the additive
  schemas through existing EnsureSchema; there is no startup full-table data
  rewrite or global progress reset for this feature.
- Keep a single compatible worker version for a queue while switching releases.
  Optional omitted snapshot fields retain compatibility with already frozen
  legacy job JSON and batch identities.
- Guided work requires enabled Secretary scheduling and an owned selected
  agent. Paused source tasks must be resumed explicitly. Human writes preserve
  the pause setting and work with Secretary off.
- Replacing unknown work fences publication; it is not proof that a native
  runtime stopped. The UI requires an explicit replacement choice.
- Revision conflicts preserve drafts in the Console. A network failure after
  submission is unconfirmed, not proof of failure; retry the unchanged payload
  with the same request ID or read its operation status.
- User-written content is labeled as such. Historical generic writes use
  `legacy_unknown` instead of being retroactively attributed to an agent.
- Passing deterministic ACP fixtures verifies data and lifecycle semantics,
  not real-model summary quality. Deployment does not automatically regenerate
  all historical sessions or resolve unrelated existing quote-validation bugs.
