# Direct regional gateway and replicated account directory

## Change and boundaries

Issue 040 is partial: implementation is ready for review; production migration is
not performed. All work is based on manager main 459a49a and the paired Console
main 36202da, on `feat/regional-account-directory` in isolated worktrees. Original
checkouts and their local changes are untouched.

`workers/region-directory/src/account-directory.ts` abstracts the existing D1
lookup/binding entrypoints. The Worker still uses its original D1 implementation.
`src/regional/store.ts` provides PostgreSQL transactions, immutable inserts and
durable change pages. `directory.ts` handles local reads, authority writes and
HMAC-authenticated replication. `gateway.ts` reuses WorkOS browser/native auth,
provisioning and origin assertions. `server.ts` proxies local HTTP, SSE and
WebSockets without buffering business uploads. `main.ts` is the executable and
import entrypoint; `config.ts` fails closed on incomplete deployment configuration.
`migration.ts` converts explicit D1 query exports while keeping original IDs.

No Go protocol or generated artifact changed. Existing Manager regional HMAC
identity validation and provisioning APIs are reused; no regeneration is needed.
The separate Node bundle and Dockerfile are intentionally outside the Worker
entrypoint, so Node/PostgreSQL modules do not enter the Worker deployment bundle.

## Data flow

Both regions persist the complete minimal directory, not business data. New
bindings and region assignments go to one authority. Journal sequence allocation
is serialized with commit. A replica applies changes and cursor in one database
transaction and catches up after restart. Local misses recover only the requested
record without advancing the global cursor; a failed authority lookup cannot
create a duplicate account. Region choice is immutable. Bootstrap provisions only
the home Manager. Ordinary foreign requests return a destination rather than proxy.

Console validates configured origins, blocks account queries until bootstrap and
navigates to the fixed home URL. Region hints never carry identity or credentials.
A navigation-only return flag avoids a loop from stale hints after switching
accounts. Local REST and WebSockets use the regional gateway. Direct mode has no
periodic region probes/bootstrap. Legacy Worker mode remains separately available.

## Deployment and verification

Use `workers/region-directory/regional/README.md`, its environment example and
Caddy example. Build with `npm run build:regional`; run the bundle with Node 24+.
The authority-only import command accepts D1 exports or a validated snapshot.
Freeze every legacy directory writer, import preserved IDs, start private regional
services, compare all rows and replication cursor, then enable public traffic.
Only one directory may accept new identities. Do not roll back to stale D1 after
new registrations without reconciling its new rows.

## Limits and operational notes

No live deployment, DNS/TLS change, WorkOS app update or production database import
was performed. Android source is outside these repositories; its persisted
bootstrap `api_url` behavior must be checked before native cutover. Host-only
cookies can require WorkOS sign-in when moving to a new regional hostname.

Replication is asynchronous with miss recovery, not active-active writes.
Authority outages block new identities; cached local accounts keep working.
No automatic region migration, deletion, authority failover or journal pruning is
implemented. Do not promote a stale replica. Native bootstrap/logout rate limits
are bounded per process; this change does not provide a distributed rate limiter.
CLI confirmation targets the home region; foreign admin aggregation/approvals
remain on the separate administrative entrypoints. The gateway's local upstreams
and PostgreSQL must stay private. Use backups and monitor replication failures.
