# Team Memex Repair Loop Handoff

## Summary

This change adds persisted run attempts for team memex maintenance runs and
turns `CreateTeamMemexRun` into a repair loop. The hosted memex executor now
receives the previous invalid manifest and structured validation report on each
repair attempt, so an LLM provider can correct its own output before the run is
finally published or marked failed.

## Module Boundaries

- `internal/manager/domain/team_memex.go` owns the run attempt domain type and
  attempt statuses.
- `internal/manager/userapi/team_memex.go` owns the executor loop, validation
  feedback, workspace construction, and response shape.
- `internal/manager/storage/team_memex.go` owns persistence for runs,
  attempts, and document operations.
- `db/init.sql` owns the Postgres schema for `team_memex_run_attempts`.

Generated Hertz handlers are unchanged. The `TeamMemexStore` method signatures
are unchanged, so store mocks did not need regeneration.

## Request Flow

1. `POST /api/v1/user/:user_id/teams/:team_id/memex/runs` authorizes the
   principal as an owner or operator.
2. The service lists active documents and reserved paths, renders the generated
   `index.md`, and creates a run ID.
3. The executor is called with `TeamMemexExecutorInput`.
4. If the executor returns a provider error, the run is stored as
   `provider_failed` with one failed attempt.
5. If manifest validation fails and the validation report is retryable, the
   next attempt receives:
   - `AttemptNumber`
   - `PreviousManifest`
   - `ValidationReport`
   - a fresh limited `TeamMemexWorkspace`
6. If validation eventually succeeds, `PublishTeamMemexRun` stores the run,
   stores attempts, and applies document operations in the same transaction.
7. If repairs are exhausted, `CreateTeamMemexRun` stores the final
   `validation_failed` run and all attempts without publishing documents.

`MaxRepairAttempts` remains part of `TeamMemexRunConstraints`; default behavior
is one initial attempt plus two repair attempts.

## Data Model

`team_memex_run_attempts` stores:

- `attempt_id`
- `run_id`
- `team_id`
- `attempt_number`
- `executor_type`
- `status`
- `manifest_json`
- `validation_report_json`
- `error`
- `started_at`
- `completed_at`

The run response now includes an `attempts` array with manifest and validation
report details for observability and future provider debugging.

## Tests Added

- Repair succeeds after an invalid first manifest and publishes the corrected
  document update.
- Repair attempts are exhausted and no document is published.
- Storage model conversion round-trips run attempts.
- Memory store cloning keeps run attempt manifests immutable from callers.

## Known Risks

- The executor type is still `dry_run`; DeepSeek wiring is intentionally left
  for the next slice.
- Session selection and incremental cursors are still not implemented.
- The response includes full attempt manifests. Current output limits make this
  bounded, but future provider output limits should stay aligned with response
  size expectations.
