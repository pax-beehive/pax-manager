# Transport journal retention implementation

## Change and boundaries

Issue #044 is implemented in code; merge and production rollout remain pending.
The original pax-manager checkout has unrelated uncommitted changes, so this work
uses the isolated `pax-manager-journal-gc` worktree based on main commit `526c749`.

- `internal/manager/journalgc` owns bounded scheduling, policy defaults, timeout,
  retry, cancellation, and joining the worker.
- `internal/manager/storage/transport_journal_gc.go` owns one-statement PostgreSQL
  deletion with persisted watermark and diagnostic tail checks.
- `internal/manager/journal_gc.go` wires PostgreSQL storage and structured batch
  logs into the process lifecycle; `app.go` stops GC before closing storage.
- Config exposes retention, batch interval, batch size, and an explicit disable
  switch. Defaults require no environment changes.

No API or generated artifact changes are required. The legacy deletion API and
in-memory implementation are unchanged. The worker uses a narrow optional storage
interface; no generated mocks or domain Store interface were expanded. Current
node traffic and legacy agent traffic share the same retention path.

## Safety and rollout

See `transport-journal-retention.md` for exact defaults and environment variables.
Recent, unfinished, failed/rejected, missing-state, and beyond-watermark records
remain intact. Persistent queue state is never deleted. Concurrent batches skip
rows locked by other transactions. Timeouts cancel the statement atomically and
retry on later ticks; the worker never drains the entire backlog in one call.

The initial startup migration still precedes the worker. The observed US failure
hit a 60-second deployment health timeout; its restored old Manager took about
104 seconds to listen. This patch does not change release-agent timeouts or remove
the startup historical aggregations. Account for that first-start limitation at
rollout. No production data was deleted, no Manager was restarted, and no release
platform changes were made as part of implementation.

Deleting retained history is irreversible; an application rollback cannot restore
it. PostgreSQL autovacuum allows space reuse without necessarily shrinking files.
