# Secret Vault With Agent Approval

## Summary

Implemented an owner-scoped secret vault in pax-manager with encrypted secret
versions, node/agent resolve and write APIs, approval-gated plaintext access,
optimistic locking for current-version promotion, idempotent node writes, access
events, OpenAPI route generation, and integration coverage.

Also added lightweight paxd support for `api_key_secret_ref`, persisted cloud
agent secret refs, and cloud client methods for resolving and writing secret
versions.

## Module Boundaries

- `internal/manager/secrets` owns local AEAD encryption helpers. It reads
  `SECRET_VAULT_MASTER_KEY`, falling back to a deterministic dev key for tests.
- `internal/manager/userapi` owns user-facing secret creation/list/get.
- `internal/manager/paxd` owns node-facing secret resolve/write behavior and
  creates `agent_approvals` records when an agent wants plaintext access or
  wants to write a new secret version.
- `internal/manager/storage` owns Postgres and memory persistence for secrets,
  secret versions, and access events.
- Existing `agent_approvals` remains the grant store for agent-visible
  plaintext reads and agent writes.

## Core Flows

User creates a secret through:

```text
POST /api/v1/user/:user_id/secrets
```

The request includes plaintext `value`, but responses only return secret
metadata and version metadata. The database stores only ciphertext, nonce, and
key id.

Agent read flow:

```text
POST /api/v1/node/secrets/resolve
```

If no reusable `agent_approvals` grant exists for
`domain=secret_vault`, `operation=read_value`, and the stable action
fingerprint, pax-manager returns `202 approval_required`. After the user
approves, the same request returns plaintext value and records a
`secret_access_events` row.

Agent write flow:

```text
POST /api/v1/node/secrets/:secret_id/versions
```

If no reusable grant exists for `operation=write_value`, pax-manager returns
`202 approval_required`. After approval, the request appends a new version. If
`make_current=true`, the request must include
`expected_current_version_id`; promotion uses a CAS update and returns conflict
when stale.

## Notes

- Approval request bodies intentionally do not include secret plaintext.
- `allow_once` is not offered for secret actions because the existing reusable
  grant lookup excludes `decision_scope=once`; current options are agent, node,
  or deny.
- paxd now has config/store/client support for secret refs, but the current
  daemon bootstrap path does not clearly instantiate Hermes clients from
  `RuntimeAgentConfig`, so full runtime injection should be wired in a follow-up
  once that lifecycle is clarified.
