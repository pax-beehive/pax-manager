# Secretary source completion waiting and native execution investigation

## Result and scope

An incomplete source batch now persists the existing source-incomplete reason.
The task API can therefore distinguish waiting_source from queued and explain
that it is waiting for the source turn to finish. Successful preparation clears
only that specific reason. No new schema or API representation is needed.

This fixes [issue 071](../issues/071-secretary-source-wait-reason-not-persisted.md).
The deployed Pax MCP approval change was independently validated and
[issue 069](../issues/069-pax-mcp-manual-approval-blocks-secretary.md) is resolved.
[Issue 070](../issues/070-pax-mcp-origin-binding.md) remains open as previously
agreed. [Issue 072](../issues/072-dscode-long-pty-command-blocks-secretary.md)
tracks a separate native terminal problem; that runtime compatibility work is
not part of this Manager code change.

## Storage and request flow

Claiming still requires a visible owned source, an enabled selected agent,
source idle, the quiet period, and a valid lease. PrepareSecretaryBatch still
checks reliable completed-message or matching-turn evidence before creating
a new batch.

When that check is false, MemoryStore and PostgresStore release the lease,
defer the next check by 30 seconds, and persist
ErrSecretarySourceIncomplete.Error(). The existing task projection maps it to
waiting_source / source_incomplete. Waiting creates no batch or attempt and
does not advance the checkpoint, change the retry epoch, or consume a model
attempt.

After preparation succeeds, the exact waiting reason is cleared under the
same transaction or memory lock. Other failure reasons are preserved. In PG,
commitPreparedSecretaryBatchTx combines that conditional clear with commit;
a clear failure rolls back the new batch. Fenced preparation cannot clear the
reason.

There are no generated artifacts or regeneration steps for this change.

## Operational findings

The Manager image was confirmed to contain merged PR 224. Two older native
Secretary runs were still waiting on approvals from before that deployment.
The selected DSCODE connection was restarted only after verifying that no
ordinary conversation was active. Old unknown tasks were individually retried
with owner, settings, epoch, control revision, attempt and lease checks. Existing
summaries and processed revisions were retained.

Fresh workspace_summaries and workspace_read requests received audited
allow_once decisions with approval_policy=pax_owned_mcp, successful responses,
and committed summary output. Seven of the retried tasks subsequently completed.
One long execution later timed out while running native bash; its MCP approvals
had already passed. It was not repeatedly resubmitted.

Some pending history genuinely lacks a complete message or matching reliable
turn terminal. Its stored visible messages are sent/received, not complete.
This change exposes that waiting reason; it does not manufacture completion
proof. User prompt completion and canceled/failed turn handling remain separate
ingestion and lifecycle questions.

## Native terminal compatibility candidate

The installed DSCODE tool wraps a whole shell command into a single ANSI-C
quoted eval input. An independent synthetic PTY reproduced a length-related
failure: a 1 KiB command finished promptly, while a roughly 27 KiB JSON command
did not reach its end marker before the bounded test timeout. The real failed
run waited in that tool until cancellation. The exact low-level cause has not
been established.

A separate local candidate stages bounded input lines, sending the next only
after stdin_read readiness, and evaluates the reconstructed command in the
same persistent shell. Independent review and 21 tests passed, including
Unicode, quotes, CR/LF, cwd/env, exit status, stdin, autoexport, cancellation and
timeout boundaries. Raw PTY tests also passed. A complete 26,849-byte command
then passed against the actual installed BashTerminalBackend and
LocalSubprocessRuntime: 16 input lines returned stdin_read, output hashes and
exit status matched, and cleanup left no processes or terminals. This took
8.49 seconds; the initial three-second synthetic deadline had been too short.

The compatibility file was applied after checking the exact original SHA256,
creating and verifying a same-directory backup, and atomically replacing the
file with its original mode. The selected connection was restarted after its
active execution finished. This is a local DSCODE runtime hotfix, not a Manager
image change or upstream release. A DSCODE upgrade may overwrite it.

The local compatibility artifact has original SHA256
71f0d8162bac4bcf0755dda5058bb4a24fa99f346223b617b0eca74b0977e253 and
patched SHA256
2946e896dadcda593084b5167fab7791fc46e591365ae3604785e9826c276016.
Restore only after checking both the current patched file and original backup;
do not overwrite a later native upgrade. The backup is named
index.js.pax-longline-backup-20261106T054718Z-71f0d8162bac4bcf beside the
installed dsh-tool-bash-persistent/lib/index.js.

The current DSCODE ACP adapter has no per-session tool allowlist. Its coding
preset includes bash. The Secretary prompt already forbids command execution,
but that does not provide a hard native tool restriction.
