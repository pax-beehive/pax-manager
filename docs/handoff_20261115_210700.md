# Tunnel replay and session locking recovery

## Incident and scope

The US Manager based on `d162dc62295bea983f5e19d39d1386a9bf521c72`
experienced repeated session snapshot deadlocks, queue replay errors, and severe
PostgreSQL CPU/lock-manager contention. One agent had 1,299 session rows. One
queue retained 1,010 failed command-list updates, exceeding the 1,000-frame
replay batch. A subsequent audit across all queues found 1,013 stale received
frames below applied cursors, all `available_commands_update`, with no approval
or content message types in that set.

## Changes and module boundaries

- `domain.SessionAliasStore` is an optional internal routing capability. Memory
  and PostgreSQL resolve IDs across hidden and archived sessions using existing
  agent access checks. PostgreSQL prefers exact manager IDs, then authoritative
  native bindings, then unbound native lookup. Public session lists stay filtered.
- ACP alias caching, history canonicalization, worker responses, and tunnel
  handshakes use that lookup instead of listing user-visible sessions.
- Paxkit commit `27bf3c835b5f88208fd3129a3d61c294454c5724` preserves dispatch
  errors and exposes the sink's optional inbound cursor through producer
  write-behind. Manager replay filters stale rows before pagination. Original
  journal records are retained; no production data deletion is needed.
- Runtime snapshots share the node fence read lock and lock only current or
  previously active/unknown sessions, ordered by session ID. Dedicated batch
  reports acquire the same agent guard before touching sessions.
- Reliable transport mutations acquire queue guards before journal rows.
  Batches acquire sorted, deduplicated queue guards to avoid interqueue inversion.
- The application pool permits at most 16 open and 4 idle PostgreSQL connections.
- User relay prepares the history boundary before making a request available to
  the agent, avoiding immediate-response fragment splitting. Outgoing prompt
  persistence still occurs after successful acceptance.

No IDL, generated handler, generated mock, schema, auth configuration, or
Cloudflare policy change is required.

## Verification

The new tests reproduced the replay loop, hidden-session `not found`, duplicate
native routing error, actual PostgreSQL `40P01` cycles, idle-history blocking,
and immediate-response history fragmentation before the fixes.

Checks use `GOWORK=off` because the parent workspace excludes this worktree:

```sh
GOWORK=off GOCACHE=/tmp/pax-manager-go-cache make fmt-check
GOWORK=off GOCACHE=/tmp/pax-manager-go-cache make lint
GOWORK=off GOCACHE=/tmp/pax-manager-go-cache go test -count=1 ./...
GOWORK=off GOCACHE=/tmp/pax-manager-go-cache go build -o /tmp/pax-manager-build-check ./cmd/manager
```

Actual lock regressions additionally set `PAX_MANAGER_LOCK_TEST_DATABASE_URL`
to the disposable local database at port 25432. Internal alias PostgreSQL tests
use `PAX_MANAGER_SECRETARY_TEST_DATABASE_URL` and isolated fixture schemas.
Relevant tests also run with `-race`. New lookup and queue-guard methods have
100% statement coverage. Changed snapshot methods have 80.0%-86.7% coverage;
final changed-statement coverage is 96.2% (127 of 132 changed statements).
Paxkit's full suite passed with 80.1% overall coverage.

The standard `make integration-test` image build hit registry metadata timeouts.
The fallback uses the same cross-compiled candidate binary, current `db` and
`static` files, and a locally cached runtime image. It runs the existing
`docker-compose.integration.yml` under the exact isolated project
`pax-tunnel-fix-20261115`, with Manager port 29879 and MinIO port 29000, then
executes `go test -tags=integration -count=1 ./integration`. Docker DNS was
intermittently timing out, so the isolated Manager endpoints were pinned to the
existing test-container IPs in a temporary Compose override. The final suite
passed in 2.633 seconds; the optional sibling-paxd-container fixture was skipped
because that repository is not adjacent to the worktree.

## Build and production operation

Build the Linux candidate with the pinned Paxkit dependency:

```sh
GOWORK=off GOCACHE=/tmp/pax-manager-go-cache CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \
  go build -trimpath -ldflags='-s -w' -o /tmp/pax-manager-tunnel-linux-amd64 ./cmd/manager
```

The incident target is `home_dev` (US). Use its deployment runbook. Derive the
candidate image from the exact running image and replace only `/app/pax-manager`.
Do not commit a running production container into an image: its container config
contains runtime credentials. Image preparation must start from the original
image configuration, with no protected runtime env injected.

The switch retains the complete existing environment, loopback port, non-root
user, restart policy, and all three networks: `pax-manager_default` (dynamic),
`pax-cloudflare-origin` (172.30.36.3), and `pax-search-private` (dynamic).
Keep the previous container stopped and disconnected as a rollback target.
Protected inspect backups remain on the server with mode 0600. Do not print them.

Do not start a second Manager against production. PostgreSQL, Console, search,
and tunnels do not need restarts. Preserve the existing protected env file.
