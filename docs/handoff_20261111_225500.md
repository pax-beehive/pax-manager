# Native harness login user API

## Change and boundaries

Issue #081 is resolved for the current node API. New user endpoints forward the
existing ephemeral paxd native login protocol:

- GET `/api/v1/user/:user_id/nodes/:node_id/harnesses/:harness/auth/status`
- POST `/api/v1/user/:user_id/nodes/:node_id/harnesses/:harness/auth/login`

GET accepts optional `session_id`. POST accepts `command_id`, `operation`, and
optional `session_id`, `method`, `code`. Operation is start, submit, or cancel.
Supported methods are Claude subscription/console and Codex
device/api-key/access-token. Claude submit requires the complete authorization
code; Codex key/token login sends the secret on start. Secret input is a single
line of at most 4096 bytes. Request JSON is strictly decoded and bounded to 32 KiB.

`internal/manager/node_harness_auth.go` binds transport data, forces route IDs,
sets `Cache-Control: no-store`, and delegates. `userapi/harness_auth.go` resolves
the authenticated principal, checks GetNode and exact ownership, validates the
native operation, and forwards via the existing NodeControlClient. Domain types
whitelist the public view fields. The regular durable node command path is not
used. No database schema or paxd changes are required.

## Request and data flow

Start first queries the harness state. Unknown active sessions are rejected
without returning the authorization challenge. A per-node mutex serializes the
ownership check and mutation. Only nonsecret ownership metadata (user, node,
remote ID, harness, method, command ID, previous session ID, deadline) is retained
in process memory. Codes, API keys, access tokens, and URLs are never retained by
the ownership map or persisted to the command journal.

Before dispatch, a pending-start reservation records ownership. If the daemon
accepts login but the ACK is lost, a later status query may adopt only a new
session with the same remote ID, harness, and canonical method. The previous
terminal session and unrelated methods cannot be adopted. Definite rejection
clears the pending reservation. Successful ACKs validate command ID and session
identity. Polling does not extend the original five-minute ownership deadline.

Responses use the normal Manager envelope: HTTP/code 200 for status, 202 for an
accepted operation, and `data.harness_auth` for the normalized native view. An
accepted ACK does not prove provider login completion. Stable native error codes
map to 400, 404, 409, or 502; daemon messages/raw output are not returned. Tunnel
unavailability maps to 503 and timeout to 504. Existing processes may require an
explicit restart to consume new native credentials.

## Generation

Source of truth is `api/pax_manager.thrift`. Generated Hertz models/routes and
Manager OpenAPI output were regenerated using `make generate`. Network metadata
lookup for `go run mockery@v2.53.5` was unavailable in this environment, so the
exact cached v2.53.5 module was compiled locally to `/tmp/pax-manager-mockery`:

```sh
GOWORK=off GOCACHE=/tmp/pax-manager-go-cache go build -o /tmp/pax-manager-mockery .
# Run the above in the cached github.com/vektra/mockery/v2@v2.53.5 module.
PATH=/Users/gengcongkai/go/bin:$PATH GOWORK=off make generate MOCKERY=/tmp/pax-manager-mockery
```

No generated files were edited manually; existing interface mocks were unchanged.

## Development, verification, and deployment

Use `GOWORK=off` for this isolated worktree. Local development remains
`GOWORK=off make run-memory` or the normal PostgreSQL configuration. Deployment
continues through the existing `make cloud-build-vm` workflow; no deploy was run.
Deploy the compatible Manager before exposing the new Console login controls.

Targeted tests exercise the actual HTTP routes and authenticated node control
WebSocket with fake native views for all five methods, polling, submit/cancel,
malformed JSON, owner isolation, journal exclusion, and lost start ACK recovery.
No real native login or credential mutation is performed. Local loopback
listeners require running these tests outside the filesystem/network sandbox.

Lint passed for normal and integration-tag packages. The full Go suite passed;

route integration tests instead use actual local HTTP/WebSocket transports and
fake daemon replies without changing native credentials.

## Risks and assumptions

The existing node control hub is process local. Requests must route to the
Manager holding the node WebSocket and login ownership; a database alone cannot
provide that affinity. The checked-in VM deployment targets one
`pax-manager-monolithic` VM. This change does not establish distributed routing.
After Manager restart, transferred ownership, or a changed remote ID, unknown
attempts fail closed and may need to expire before another login starts. The API
returns an explicit conflict message for this case.

The native CLI remains responsible for tokens, refresh, and credential storage
under the OS account/environment running paxd. This API does not authenticate
an arbitrary credential context, prove model-request success, or interrupt
existing conversations. Reverse proxies and callers must also avoid logging
bodies/challenge URLs and respect no-store.
