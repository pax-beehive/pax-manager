## Summary

Added the first approval-recording layer for normalized agent approvals.
The change introduces a shared `agent_approvals` table, approval IDL models and
routes, Postgres and in-memory DAL methods, and ACP tunnel handling for
`session/request_permission`.

## Module Boundaries

- `api/pax_manager.thrift` is the source of truth for the new approval routes
  and response models.
- `db/init.sql` owns the `agent_approvals` schema and indexes.
- `internal/manager/domain` owns approval models and store interface methods.
- `internal/manager/storage` implements approval persistence for Postgres and
  memory stores.
- `internal/manager/node_idl_handlers.go` currently wires approval routes to
  the store. A future `internal/manager/approval` module can move policy and
  orchestration out of handlers.
- `internal/manager/acp_tunnel.go` handles ACP `session/request_permission`
  interception.

## Request And Data Flow

Node-authenticated agents can create and read approval records:

- `POST /api/v1/node/agents/:agent_id/approvals`
- `GET /api/v1/node/agents/:agent_id/approvals/:approval_id`

Users can inspect, decide, list grants, and revoke reusable grants:

- `GET /api/v1/user/:user_id/approvals`
- `GET /api/v1/user/:user_id/approvals/:approval_id`
- `POST /api/v1/user/:user_id/approvals/:approval_id/decision`
- `GET /api/v1/user/:user_id/approval-grants`
- `POST /api/v1/user/:user_id/approval-grants/:grant_id/revoke`

Approval records keep concrete request origin fields:

- `request_node_id`
- `request_agent_id`
- `request_session_id`

Reusable grants use match fields that may contain `*`:

- `grant_node_id`
- `grant_agent_id`
- `grant_session_id`

`allow_always_on_all_agents` maps to:

- `decision = allow`
- `decision_scope = across_all_agents`
- `grant_node_id = *`
- `grant_agent_id = *`
- `grant_session_id = *`

## ACP Permission Flow

The ACP tunnel now inspects agent-to-user JSON-RPC frames. If the method is
`session/request_permission`, pax-manager computes an action fingerprint from
`params.action_fingerprint`, `params.actionFingerprint`, or a stable hash of
the params excluding `options`.

If a reusable approval grant exists for the owner, agent, session, domain,
operation, and fingerprint, pax-manager does not forward the frame to the user.
It writes a JSON-RPC result back to the agent using the existing `allow_once`
option from `params.options`.

If no reusable grant exists, pax-manager appends
`allow_always_on_all_agents` to `params.options` and forwards the request.

The ACP behavior is covered by integration-style websocket tests:

- `TestACPTunnelRequestPermissionAddsAllowAlwaysOption`
- `TestACPTunnelRequestPermissionUsesReusableApprovalGrant`

## Risks And Follow-Ups

- The approval route handlers currently call the store directly. A follow-up
  should add `internal/manager/approval` for normalization, policy, and option
  construction.
- ACP auto-approval response shape uses the existing `allow_once` option object
  as the JSON-RPC result. Confirm this shape against the ACP client contract.
- Secret vault CRUD approvals must not place plaintext secret values in
  `agent_approvals`; store only secret or pending-version references.
- The reusable grant lookup depends on consistent domain, operation, and action
  fingerprint generation between stored approval records and ACP frames.
