## Scope and boundaries

`workers/region-directory/src/hosting.ts` is integrated into the existing
browser Worker's outer dispatcher before browser login. It accepts only four
exact service POST paths and never falls through to user/node authentication.
Only explicit `HOSTING_SERVICE_REGION=us` enables it. It reuses the existing
`PUBLIC_ORIGIN`, `US_MANAGER_URL`, `US_ACCESS_CLIENT_ID` and
`US_ACCESS_CLIENT_SECRET` bindings. No new service secret is required.

Service flow: caller's own gateway/host Bearer -> exact Worker service path ->
fixed HTTPS US Manager with the existing CF Access pair -> Manager's independent
role-key check and authoritative ledger. The Worker has no copy of the Manager
gateway/host keys, does not read D1 or provision an account, and emits no user
identity assertion. Fresh headers remove caller cookies, assertions, identities,
node keys and incoming CF credentials. Limits are64KiB input,2MiB JSON output
and15seconds across the full request. Redirects, retries and CORS grants are
absent; output is no-store. Cleanup failures cannot produce raw transport logs.

`starter-routes.ts` supplies one exact method/path predicate used by browser,
native WorkOS and existing native API-key routing. Allowed owner operations are
GET/POST `/api/v1/starter` and POST `/api/v1/starter/wake`. Existing `/api/pax/*`
and native CF prefixes cover them, so no direct Starter prefix was added.
WorkOS session/JWT validation, same-origin checks, D1 home-region authority,
owner resolution and HMAC method/path signing are unchanged. The regional Node
gateway passes the method into the same browser predicate.

No Go, Thrift, SQL or generated artifacts changed. No regeneration is required.
Legacy agent/node routes and Manager inference were not opened.
