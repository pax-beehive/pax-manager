# Secretary task controls

## Scope and boundaries

Each task follows one original source session (`secretary_jobs.source_id`). A batch
is immutable input; an attempt is one actual agent execution. The Console now
lists pending tasks and exposes bounded attempt history, a source link, and an
execution link when that execution remains readable by the owner.

The existing connection-backoff change remains required. This change does not
deploy services, restart agents, invoke a production model, or reset production
checkpoints. Native execution cancellation is outside this version.

## User actions

- Pause/resume changes future scheduling for one source. Pause survives source
  updates, service restarts, and bulk retry. An already running execution may
  finish and publish while paused; pause does not cancel it.
- Check existing result acquires a short lease on the same batch and attempt,
  reads an existing completion or saved output, and validates/publishes it. It
  never prepares new input, begins another attempt, or calls `Executor.Execute`.
  If no completion is confirmed, the original failure remains visible.
- Retry this task advances only the selected source's retry epoch and queues its
  current source input with a fresh retry budget. Existing summaries and progress
  remain. Late results from the previous epoch cannot publish. Unknown outcomes
  require explicit restart confirmation because the old model request may have
  run. Retry/check are rejected while an operation owns an active lease.
- The existing bulk retry endpoint remains compatible. The Console now confirms
  bulk scope and possible duplicate executions, and paused sources are excluded.

## API and persistence

Owner-authenticated routes under `/api/v1/user/self/secretary` (and the existing
explicit-user aliases):

```text
GET  /tasks?limit=20&cursor=...
GET  /tasks/:task_id?limit=20&cursor=...
POST /tasks/:task_id/actions
```

List returns pending source tasks; detail returns the task and paginated attempt
history. The default limit is 20, capped at 100. Cursors are bounded and tied to
the owner and list/detail scope. Completed tasks leave the pending list but remain
available through detail.

Actions carry `action`, `expected_revision`, `batch_id`, `attempt_id`,
`retry_epoch`, `settings_revision`, and optional `confirm_restart`. The backend
checks the observed revision and execution identity atomically. Stale requests
return 409; the client refreshes state and never automatically repeats a POST.

`secretary_jobs` gains additive `paused` and `control_revision` columns; attempt
history gains an index on batch, creation time and attempt ID. Memory
and PostgreSQL implement the optional `domain.SecretaryTaskStore`; the general
store interface is unchanged. PostgreSQL actions use short transactions and row
locks. No transaction remains open while reading an execution result.

The user API resolves the current owner. Storage checks current source agent,
session and node visibility, archive/delete state, and internal-session exclusion.
Foreign or inaccessible sources return 404. Execution links are independently
authorized. Responses use fixed safe error codes/messages and never include raw
prompts, model output, read receipts, capability tokens, or arbitrary errors.

## Recovery flow

`userapi.SecretaryTaskService` validates requests and delegates a recovery callback
to the Manager service. The service claims the original attempt for one minute,
calls `secretary.Worker.RecoverJob` with a 20-second request timeout, and always
releases its lease with a separate bounded cleanup context.

Recovery validates source identity, permissions, input versions and summary
baselines. Changes or publication races return a conflict instead of automatically
superseding the batch or scheduling another model request. Unresolved/invalid
checks remain blocked for an explicit user decision. Successful publication lets
later deltas proceed, while preserving the source's pause flag.

The task service is wired from `configureSecretary`; transport handlers remain
thin. The source of truth for generated HTTP models/routes/OpenAPI remains
`api/pax_manager.thrift`. Regenerate with `make generate`; generated files are
committed together with the IDL.

## Rollout and checks

Deploy Manager before the paired Console so the task routes exist. Normal schema
bootstrap adds the two columns; no destructive migration or data backfill is
needed. No paxd update or ES rebuild is required for task controls. Existing
unknown executions are retained for an explicit check or confirmed retry.

Verification uses testify-style BDD tests, Memory/isolated PostgreSQL contracts,
actual authenticated HTTP recovery, worker no-dispatch checks, ACL/CAS and lease
races, and responsive Console tests. Required commands:

```sh
make fmt-check
make lint
GOWORK=off GOCACHE=/tmp/pax-manager-go-cache go test -count=1 ./...
GOWORK=off GOCACHE=/tmp/pax-manager-go-cache go build -o /tmp/pax-manager-build-check ./cmd/manager
PAX_SECRETARY_TEST_PAXD_BINARY=/tmp/pax-summary-nodes-daemon GOWORK=off make secretary-acceptance
```

Local coverage and complete verification results are recorded in the PR. These
checks use isolated test data and do not establish production summary quality.

issue 064 (upstream source runtime snapshots) and the separate legacy integration
fixture limitation in issue 068 are not resolved by task controls.
