# Machine identity runtime snapshot handoff

## Summary

paxd runtime snapshots now carry a friendly machine name, operating system,
and architecture. pax-manager persists those fields on the authenticated node.
This lets existing nodes replace registration-time `unknown` values without
pairing again.

The machine name is descriptive hardware information only. The implementation
does not collect serial numbers, machine IDs, boot IDs, or hardware UUIDs.

## Module boundaries

- paxd detects the machine name in `internal/machineinfo`.
- paxd includes host identity in `control.HostMetricsReport` and the existing
  node-control `runtime.snapshot` report.
- pax-manager decodes host identity in `internal/manager/node_control_tunnel.go`.
- pax-manager storage implementations update the existing node profile during
  `UpsertNodeStatus`.

## Request and data flow

1. paxd resolves an explicit configured machine name or detects one locally.
2. The host metrics sampler includes `machine_name`, `os`, and `arch` in its
   runtime snapshot.
3. The existing authenticated node-control WebSocket sends the snapshot.
4. pax-manager maps the host identity onto `domain.NodeStatusReport`.
5. Memory and PostgreSQL stores update non-empty node identity fields.

Older paxd versions omit these fields, so pax-manager preserves the stored
values. Older pax-manager versions ignore the additional JSON fields.

## Detection behavior

- macOS uses the `machine_name` returned by `system_profiler
  SPHardwareDataType -json`, with `hw.model` as a fallback.
- Linux uses valid DMI product data, device-tree model data, or valid board
  data. Firmware placeholders are ignored. It does not infer a physical form
  factor from SMBIOS chassis type because that value is often inaccurate.
- Windows uses `Win32_ComputerSystem` through non-interactive PowerShell CIM.
- An explicit `PAX_MACHINE_TYPE` or YAML `agent.machine_type` value wins.
- When no reliable name exists, the value is `Computer`.

## Generated artifacts

No generated Hertz or Thrift artifacts changed. The additional fields are on
the existing internal node-control runtime snapshot JSON contract.

## Deployment

Deploy pax-manager first, then release paxd. After the updated paxd connects,
its initial runtime snapshot should update the node machine name, OS, and
architecture automatically.

## Risks and operational notes

- Vendor firmware data can be absent or contain placeholders. Detection must
  stay conservative and must not guess a laptop, desktop, or server category.
- `machine_type` now contains a friendly machine name for paxd nodes. Consumers
  must continue treating it as an opaque display string rather than an enum.
- Users can override incorrect firmware data with `PAX_MACHINE_TYPE` or
  `agent.machine_type`.
