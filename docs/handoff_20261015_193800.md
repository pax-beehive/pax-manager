# Mobile home-directory browsing and daemon maintenance

## Scope and boundaries

Added a user-authorized `GET /api/v1/user/:user_id/nodes/:node_id/daemon/directories`
endpoint. Thrift is the contract source; generated Hertz models/router and
manager-owned OpenAPI routes were regenerated with `make generate`. The runtime
uses `registerIDLRoutes`, with the thin manager handler delegating to userapi.
Userapi resolves the principal and checks node visibility before forwarding the
`directories.list` query. No directory data is stored by the manager.

Paxd in the sibling checkout implements the query using `os.Root` rooted at its
service user's home. It lists one directory at a time, never file contents or
recursive descendants. Hidden folders are opt-in; replies contain at most 100
folders and an after-name cursor. Bounded enumeration retains only one page and
lookahead. Symlinks outside home and parent traversal are rejected by the daemon.

Native gateway additions are narrowly limited to GET current-user node detail,
daemon directories/status/command result, POST daemon upgrade, and authenticated
GET public/paxd/download. The user explicitly approved this exact security-boundary
change after automatic review requested per-exception authorization. Existing
login/subject binding and manager node checks remain intact. No broad catch-all
route or unauthenticated upgrade route was added.

The sibling pax-clients Android/iOS clients display existing heartbeat versions,
select folders on demand, and reuse idle-mode upgrade commands. They persist the
command identity before dispatch and require a confirmed new boot and matching
version. Request acknowledgment is not upgrade success.

## Integration and deployment

This handoff records implementation validation. The new directory and daemon
maintenance routes have not been deployed. Backend and native gateway changes
are integrated in this worktree, including the earlier mobile project/session
creation routes documented in the adjacent handoffs. Client changes remain in
the sibling pax-clients repository. The daemon changes were pushed separately
as pax-beehive/paxd PR #95 and still require review before merging.

Deployment sequence: integrate/release the manager endpoint and approved native
Worker routes, publish/install a paxd build containing the directory query, then
distribute updated clients. Use the repository's configured manager release flow;
Worker `npm run deploy` is the existing deployment command but was NOT run.
No real remote node was upgraded during validation.

The home boundary is the paxd process user's home, not necessarily the current
interactive desktop user's home. Old daemons will return an unsupported-query
error; the clients retain manual session-path entry. No database migration or
new periodic reporting protocol is needed; existing 10-second heartbeat version
persistence and maintenance confirmation are reused.
