# E2EE attachment download tickets

Encrypted attachments use the ordinary upload-ticket, direct object PUT, and
completion paths with ciphertext only. Their public filename is a random ID
with .paxe suffix; content type is application/octet-stream, and size is the
ciphertext size. Original file metadata and decryption context remain in the
browser-to-paxd E2EE command. Manager never receives a decryption key.

GET /api/v1/user/{user_id}/attachments/{attachment_id}/content?ticket=1 returns
an ordinary JSON API envelope with data.url instead of a redirect. It performs
the existing owner, completed-upload, and configured-bucket checks, and uses
the same signed download URL and private/no-store cache policy. Existing
content requests without ticket=1 keep their redirect behavior.

This is an extension of the existing handwritten attachment content route;
no generated handlers, Thrift endpoints, database schema, or models changed.
Console fetches a fresh ticket before each encrypted prompt, and paxd downloads
and authenticates the ciphertext before exposing a local resource_link to ACP.

Deploy Manager and paxd before Console. There are no new configuration values
or migrations. Local development continues to use the existing Manager and
object-storage configuration. The encrypted paxd downloader requires HTTPS
signed URLs. See paxd/docs/e2ee_attachments.md for the cross-language format.

Validation: repository fmt-check, lint (including integration-tag lint), full
Go tests, and Manager build. Attachment content tests exercise both redirect
and JSON-ticket modes for owners, other users, pending uploads and wrong
buckets. No local legacy issue was marked resolved. KEV-25 covers the combined
Console/Manager/paxd feature; deployment smoke validation remains outstanding.
