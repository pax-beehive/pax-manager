# Handoff: S3-Compatible Object Storage

## Summary

This change replaces the pax-manager runtime dependency on Google Cloud
Storage, Google IAM ID tokens, and `gs://` object identities with an
S3-compatible object storage backend. AWS S3 and the pinned MinIO version are
supported through AWS SDK for Go v2 and its standard credential chain. Other
S3-compatible implementations must be verified for conditional PutObject with
`If-None-Match: *` and `x-amz-checksum-sha256` validation before use.

No old GCS objects or database rows are migrated. Existing bucket, object, and
generation columns remain to avoid an unrelated database migration, but new
storage URIs use `s3://`. Operators must republish or re-upload legacy objects.

## Configuration and endpoint split

The storage configuration is:

- `OBJECT_STORAGE_BUCKET` is required and is the only accepted bucket.
- `OBJECT_STORAGE_REGION` defaults to `us-east-1`.
- `OBJECT_STORAGE_ENDPOINT` is optional and is used for server-side HEAD calls.
- `OBJECT_STORAGE_PUBLIC_ENDPOINT` defaults to the internal endpoint and is
  used to create client-reachable presigned URLs.
- `OBJECT_STORAGE_FORCE_PATH_STYLE` defaults to false.
- Credentials come from the AWS standard credential chain.

The public endpoint host is part of the SigV4 signature. A proxy must preserve
the original Host header, and the endpoint must not redirect to an interactive
login. In particular, a Cloudflare Access 302 response breaks presigned PUT and
GET requests. The public installer and updater routes under `/api/v1/public/*`
also require an Access bypass or non-interactive service-auth policy.

## Upload and download protocol

All attachment, generic session artifact, and node publication upload tickets
use protocol `s3_presigned_put` and HTTP PUT. Clients must send every header in
the ticket, including `Content-Type`, `If-None-Match: *`, and optional
`x-amz-meta-sha256` and `x-amz-checksum-sha256`. When the API receives a valid
64-character hex SHA-256, it signs the base64 S3 checksum header so supporting
object stores validate the body during upload. Empty SHA values omit both checksum
validation and metadata.

`If-None-Match: *` is included in both the PutObject signature and the returned
ticket headers. This prevents a ticket from overwriting an existing key. A
client that loses the response after an upload should use the completion API;
blindly repeating the PUT may receive a precondition failure. Specifically, HTTP
412 is ambiguous already-exists: clients continue to completion and let manager's
HEAD integrity validation decide. Other 4xx responses remain upload failures.

Completion calls issue HeadObject and validate declared size, content type,
and SHA-256 metadata. Upload size is always compared exactly, including zero;
declaring `size_bytes: 0` therefore requires an empty object. Expected content
type is enforced after preserving the old `application/octet-stream` fallback.

Single-request PutObject is limited to 5 GiB. Prepare requests above that limit
are rejected with an explicit message that multipart upload is not supported.

Download URLs are presigned GET requests. The only supported response query
overrides are `response-content-type` and `response-content-disposition`, which
are included in the signature. If a caller supplies a positive synthetic
generation, pax-manager first issues HeadObject and rejects a mismatch before
signing. When HeadObject returns an S3 VersionId, pax-manager binds that exact
version into the presigned GET, closing the verification-to-download overwrite
window. The bundled MinIO Compose stacks enable bucket versioning; an
unversioned compatible store can only enforce generation at signing time.

## Publication authentication

Admin publication endpoints now use an existing platform user API key:

```text
Authorization: Bearer <user-api-key>
```

The API key owner must be an admin. Google ID token audience and service account
allowlist checks have been removed. Publication accepts only the configured
bucket, verifies the object with HeadObject, and fills `generation: 0` with a
stable positive fingerprint. The fingerprint includes available version, ETag,
last-modified, and size attributes; it is not passed to SigV4 as a version ID.

## Deployment

The main Compose stack includes pinned single-node MinIO and MinIO Client image
tags. It requires operator-provided `MINIO_ROOT_USER`, `MINIO_ROOT_PASSWORD`,
and a client-reachable `OBJECT_STORAGE_PUBLIC_ENDPOINT`. Its init container
creates `OBJECT_STORAGE_BUCKET` (with a `pax-artifacts` development fallback).
The MinIO server receives `PAX_CONSOLE_ORIGIN` through the server-wide
`MINIO_API_CORS_ALLOW_ORIGIN` setting; open-source MinIO does not implement the
paid per-bucket CORS API. The pinned image is checked with an OPTIONS preflight
for the signed PUT method and headers.

Compose lets `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` override the MinIO
root credentials used by manager. Production deployments should provision a
separate service account restricted to GetObject, GetObjectVersion, and PutObject
on the one configured bucket. The root fallback is for the bundled home/development
stack.

Bundled MinIO is intended for self-hosted or development use. Keep an off-host
backup. Use AWS S3 or another verified replicated service when single-host loss
is unacceptable.

`make db-reset` stops manager and recreates only the PostgreSQL database. It does
not run `docker compose down -v` and therefore does not delete the MinIO artifact
volume.

The VM deploy path now reads AWS access key, secret key, and optional session
token from Secret Manager before starting the container. The integration
Compose files use fixed test-only MinIO credentials and no longer claim to use
a fake GCS service.

The legacy `cloudbuild.yaml` Cloud Run deploy step is removed. It remains an
archived build/push pipeline only because the old rollback service has no
required object-storage configuration or AWS credential source.

## Consumer rollout

The companion paxd and pax-console changes implement `s3_presigned_put` as one
direct PUT to the returned URL with all returned headers. They treat HTTP 412 as
ambiguous already-exists and continue to completion so manager can validate the
stored object. Installer and updater callers use the public presigned GET flow.

Old GCS-backed rows are outside this migration. Do not expose them as if they
were S3 objects; republish releases and re-upload user/session content instead.

## Verification

Unit tests use testify and cover the production S3 backend, real static-
credential presigning, endpoint separation, checksum behavior, metadata, query
signing, write-once headers, and stale-generation rejection. The S3 backend has
tests for binding a matched S3 VersionId into the final download request.

The following checks pass:

```bash
GOCACHE=/private/tmp/pax-manager-go-cache go test -p 1 -count=1 ./...
GOCACHE=/private/tmp/pax-manager-go-cache go build -o /private/tmp/pax-manager-build-check ./cmd/manager
go test -tags=integration ./integration -run '^$'
go test -tags=integration ./integration -run '^TestObjectStorageGivenWriteOnce'
docker compose -f docker-compose.yml config --quiet
docker compose -f docker-compose.integration.yml config --quiet
docker compose -f docker-compose.paxd-integration.yml config --quiet
golangci-lint run --new-from-rev=HEAD
make -n db-reset
```

The overall task also ran both release-download and installer-redirect
integration tests against a locally started manager and the pinned MinIO image;
both passed and the temporary containers and volumes were removed. The Docker
pax-manager image build itself still needs `PAX_BEEHIVE_READ_TOKEN` to download
the private paxkit dependency, so that build path was not rerun here.

A focused live test against the pinned MinIO image also passed: MinIO rejected
an incorrect `ChecksumSHA256` and rejected a second conditional PutObject for
the same key. Its isolated containers, network, and test-only volume were
removed afterward.

Repository-wide `make fmt-check` and `make lint` remain red on pre-existing
unrelated formatting, errcheck, cyclomatic-complexity, and unused-code findings.
The changed lines pass the new-from-HEAD lint check.
