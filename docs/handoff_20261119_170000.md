# Agent deletion reconciled with paxd

## Scope and boundaries

Issue 095 is resolved in Manager. An agent is a Manager `agents` row plus the
paxd agent connection that runs it. paxd owns the connection, so Manager now
follows what paxd reports, and removes connections that paxd still keeps for
agents deleted in Manager.

No route, IDL, schema, environment variable or paxd change is involved. paxd
has reported `desired_state` per connection, including removed ones, since its
first control contract, so every deployed paxd version takes part. The legacy
agent API has no connections and is unchanged.

Module boundaries:

- `internal/manager/node_control_tunnel.go` reads the runtime snapshot, decides
  which agents paxd removed, and asks for cleanup after the status is stored.
- `internal/manager/storage` deletes reported agents inside `UpsertNodeStatus`
  and answers `ListDeletedNodeAgentIDs`. Both stores implement both.
- `internal/manager/userapi/agent_connection_cleanup.go` sends
  `agent_connection.delete` to paxd in the background and owns the retry
  policy. `DeleteAgent` and `DeleteNodeAgent` call it after the store delete.
- `internal/manager/domain/node_agent_connection.go` holds the shared command
  shape and its idempotency key.

## Data flow

paxd removed a connection:

1. The runtime snapshot lists the connection with `desired_state` `deleted`.
2. `runtimeSnapshotConnections` collects the bound agent, unless the same
   snapshot has another connection for that agent that paxd still keeps.
3. `UpsertNodeStatus` tombstones those agents in the status transaction, after
   the runtime fence check. Only agents of the reporting node and its owner are
   touched. `deleted_by_user_id` stays NULL.

The owner deleted an agent:

1. The store tombstones the row at once. This never waits for the node.
2. `removeDeletedAgentRuntimeConnection` reads `runtime.connection_id` from the
   agent metadata that the last runtime snapshot wrote, and sends
   `agent_connection.delete` in the background.
3. When the node is offline, or paxd never reported the connection, nothing is
   sent. After the node reconnects, its snapshot still lists the connection as
   kept. `removeDeletedAgentConnections` asks the store which of the kept
   agents are tombstoned and sends the removal.
4. paxd removes the connection and reports it as `deleted`. That report is a
   no-op because the agent is already tombstoned.

Status reports never write to a tombstoned row. Before this change a snapshot
overwrote `status`, `last_heartbeat` and `metadata` of tombstones.

## Removal command and retries

The command id is `agentdel_` plus a hash of the agent and connection ids. paxd
deduplicates by command id and stores a command only when it was applied, so
repeated attempts replay one record.

Manager attempts a removal at most once a minute per node and connection. A
command that did not reach paxd releases that claim, so the next snapshot
retries at once. A timeout keeps the claim because the command may still be
running, and so does a rejected or malformed acknowledgement. Each attempt has
a 15 second timeout because the control connection handles one request at a
time. The attempt state is in memory; after a Manager restart the next snapshot
starts over, which is safe because of the stable command id.

The removal is sent from a background task, not from the control tunnel read
loop: the loop is what delivers the acknowledgement.

## Rollout notes

- The first runtime snapshot of each node after deployment deletes agents whose
  connections were removed on that node earlier. Sessions of those agents are
  hidden with them, as for any deleted agent. Tombstones can be restored by
  hand.
- The same snapshot removes connections that nodes still run for agents deleted
  earlier. Their harness processes stop.
- Console copy for removing a daemon connection said that the cloud record is
  retained. The matching Console change updates it; deploy Manager first.

## Known gaps

- `CreateNodeDaemonAgentConnection` creates the Manager row before paxd accepts
  the connection. A rejected or undelivered create leaves a row that paxd never
  reports.
- Deleting a node tombstones its agents and revokes its key. While its control
  tunnel is still open, the next snapshot removes its connections like those
  of any deleted agent. Once the tunnel drops, paxd cannot be reached and keeps
  them. Nothing sends the removal at the moment the node is deleted.
- Removing a connection and later creating a new one for the same cloud agent
  no longer works, because the agent is deleted in between.
- paxd leaves `agent_connection.*` commands at `received` and never marks them
  `applied`. Manager therefore learns the outcome from the next snapshot, not
  from the command.
