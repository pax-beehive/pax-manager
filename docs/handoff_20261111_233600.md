# Durable Secretary bulk retry acknowledgement

## Problem and scope

Issue 080 records a production request that committed retry state for 155 jobs
but appeared failed in Console. The former run endpoint read pending status,
reconciled all history, reset retries, then read pending status again before
acknowledging. The browser's 12-second header deadline could expire after commit.
This fix separates command acceptance, bounded metadata updates and status reads.
It does not rerun any production task or alter historical execution records.

## Request contract

The existing POST `/api/v1/user/self/secretary/run` accepts optional JSON
`{"request_id":"..."}`. IDs allow 1-128 ASCII letters, digits, underscore,
dash, dot and colon. Extra fields, malformed JSON and invalid IDs are rejected.
Empty legacy bodies receive a generated ID; only clients that supply and retain
their own ID can deduplicate a lost response.

The API resolves the authenticated owner and calls `SecretaryRunStore` directly.
It never calls `GetSecretaryStatus`, `RetrySecretaryJobs` or backfill. The durable
owner/request pair returns HTTP 202 with immutable `request_id`, `state: accepted`
and `accepted_at`. Acceptance means the command was persisted, not that a model
finished. Replaying a receipt returns it even if settings were later disabled.
There is no fallible status computation after the acceptance commit.

`api/pax_manager.thrift` remains the request source of truth. Generated model
and OpenAPI JSON changes come from `make hz-update` and `go generate
./internal/manager`; they were not hand edited. The generic response envelope
continues to carry runtime data. New domain capabilities are optional interfaces
so existing execution stores and mocks do not gain unrelated maintenance methods.

## Persistence and processing

`secretary_run_commands` stores owner/request identity, accepted time, configuration
revision, command version, source upper bound/cursor, internal completion state
and affected-job count. It has no raw source content. The owner/source jobs index
supports bounded keyset pages. The upper bound is captured using the jobs primary
key; the request does not scan or update all owner jobs. Receipts currently have
no expiration. Future cleanup must explicitly define an idempotency retention
window rather than silently allowing an old ID to execute again.

An independent Manager maintenance worker runs even without a connected agent or
ES. Each step visits at most 128 job metadata rows. A schema/owner advisory
try-lock serializes owner commands; a settings share lock fences reconfiguration;
the command and ordered page rows are locked until cursor and retry changes
commit together. Locked jobs wait briefly or roll back the page, never get skipped
past a committed cursor. Settings/policy mismatch cancels remaining command work.

Only currently owned, visible, unpaused pending jobs with no live lease and no
unresolved source execution are reset. Any pending/running/output_received/unknown
batch remains protected, including old settings/epochs: previous epoch increments
are not terminal proof. Completed jobs and message coverage remain unchanged.
The worker does not read original messages, parts, snapshots or summary evidence,
nor increase desired revisions or mark historical messages dirty.

Request transactions have a three-second context, 250 ms lock wait and two-second
statement limit. Worker steps have a five-second context and the same bounded SQL
limits. The existing maintenance scheduler is shared with progress: backlog steps
wait 100 ms, idle steps one second, errors back off exponentially to ten seconds.
Shutdown cancels and waits before storage closes. Legacy `RetrySecretaryJobs`
definitions remain for internal compatibility; the production run endpoint no
longer calls them.

## Console and rollout

The companion Console retains the pending ID per actual authenticated owner,
including reload and uncertain transport failure. The route may use `self`, but
that alias is not used as the persistence identity. A validated receipt succeeds
independently of later settings/task refreshes and never replaces settings cache.
Legacy successful status responses are recognized during rollout. No automatic
mutation retry or model call is added.

Deploy Console first, then Manager. Old Console clients expect a status-shaped
response; the new Console understands both response forms. The older Manager
ignores request IDs and cannot guarantee deduplication during the transition.
Full guarantees apply after both changes are deployed. Existing unknown tasks
still use explicit per-task recovery (issue 074). Already dirty history from an
earlier bulk run is not rewritten or cleared by this deployment.

## Verification

Tests exercise status failure isolation, legacy and malformed requests, stable
receipts, duplicate/concurrent delivery, configuration changes, owner isolation,
bounded pages, rollback, raw-table locks, current permissions, pauses, leases and
unknown executions. Validation passed:

- Full `make secretary-acceptance`: 1657 named checks, no skips. Storage completed
  in 146.863 seconds under the existing 300-second package limit.
- Full `GOWORK=off GOCACHE=/tmp/pax-manager-go-cache go test -count=1 ./...`.
- Targeted worker/HTTP/API race tests and final request-validation regression.
- New storage unit coverage: 178/183 statements, 97.3 percent. API Run, request-ID
  validation, HTTP handler, new worker and shared scheduler: 100 percent.
- Eight real-PG bulk command tests; eight concurrent requests and eight workers
  for one ID repeated three times without duplicate effects.
- Console: 92 targeted tests, TypeScript, changed-file ESLint and Prettier.

Formatting, normal/integration lint and build results are recorded in the PR.
The test PostgreSQL instance is isolated and disposable. No production data was
changed, tasks retried, or application deployed during implementation.
