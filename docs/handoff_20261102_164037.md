# Refreshed browser session preservation

## Change and boundaries

Issue [060](../issues/060-refreshed-session-cookie-loss.md) covers replacement
WorkOS cookies lost after token refresh succeeds but a later dependency fails.
The implementation stays in `workers/region-directory`; Manager's Go auth and
permission checks, generated APIs, and browser cookie format are unchanged.

`authenticateSession` now carries replacement cookies in a retryable
`SessionFailure` when identity lookup fails. Auth routes and the Worker wrapper
retain cookies after later failures. The opt-in regional Node gateway retains
them on directory failures and HTTP or WebSocket proxy connection failures.
Authentication failures retain their existing 401 and cookie-clearing behavior.

## Request flow

1. The SDK validates the sealed browser session and refreshes an expired token.
2. The SDK returns replacement sealed session data; the previous refresh token
   has already been rotated.
3. Directory or upstream errors still return 503 or 502, respectively, together
   with the replacement cookies. A later request can use the new token.

The configured public Worker routes in `wrangler.browser.jsonc` handle
`paxworkspace.net/auth/*`, `/api/pax/*`, and browser `/api/v1/user/*` requests.
Its normal caught origin-fetch 503 already retained refresh cookies. The
regional Node HTTP proxy is a separate opt-in deployment; do not infer that it is
running because its implementation is present in this repository.

## Verification and deployment

From `workers/region-directory`, run:

```sh
npm run typecheck
DIRECTORY_TEST_DATABASE_URL=postgresql://postgres:password@127.0.0.1:5432/directory_test npm test
npm run build:regional
```

The focused regression suite first reproduced five cookie-loss failures on the
unchanged implementation. The final full suite passes all 264 tests with real
PostgreSQL, including rejected WebSocket handshakes. Coverage is 94.67% lines,
94.27% statements, 92.95% branches and 96.89% functions, above every 80% gate.
Type checking, Worker dry-run build, regional build, Worker formatting and the
repository `make fmt-check` also pass. No Go implementation changed.

The Worker is deployed separately using `npm run deploy`, which selects
`wrangler.browser.jsonc --keep-vars`. This change does not require a database
migration or generated API updates. No production deployment was performed as
part of this fix.

## Operational limits

WorkOS documents a 30-second replay grace period for rotated refresh tokens:
<https://workos.com/docs/authkit/session-resilience>.

The fix covers error responses that can reach the browser. It cannot deliver a
cookie after a client disconnects or a response has already been sent. It does
not add a cache that bypasses session validation or change refresh-token
revocation rules. Do not report this demonstrated failure mode as the proven
cause of a production incident without matching observations.

## Separate production incident diagnosis

Read-only investigation on 2026-11-02 found a stronger candidate for the current
repeated sign-in prompts: the US host's clock was behind real time and its NTP
client was not synchronized. This is separate from the latent cookie-loss bug
fixed by this PR.

- `timedatectl` reported `NTPSynchronized=no`. The DHCP-provided link NTP server
  was `139.78.100.163`; its requests timed out throughout the preceding ten hours,
  at a polling interval of approximately 34 minutes. The NTP packet count was 0.
- Direct UDP probes to reachable Cloudflare, Google and Ubuntu time servers each
  measured the host approximately 5.38 seconds behind. An earlier independent
  SSH timing estimate measured 5.203 seconds behind.
- Two short Worker observations counted 18 HTTP 401 responses out of 53 and 45
  requests, respectively, with no Worker exceptions. Counts were reduced during
  collection without retaining raw request headers, cookies or tokens.
- The actual serving path is the existing Cloudflare Worker, not the opt-in
  regional Node gateway. The active Worker deployment has served 100% of traffic
  since 2026-10-16; no Worker deploy on November 1 or 2 explained the onset.

The Worker signs `Math.floor(Date.now() / 1000)`. Manager accepts a signed browser
assertion only when its timestamp is at most `time.Now().Unix() + 5`. Therefore a
host approximately 5.2 seconds behind can intermittently reject a freshly signed
assertion depending on fractional seconds. A deterministic temporary Go overlay
test called the real `browserIdentity.valid` implementation: a 5.203-second skew
rejected edge time `1000.100` but accepted `1000.700`. Both cases passed without
changing the authentication window or adding Go source to the repository.

Clock skew is the strongest operational candidate, but the incident is not
verified as resolved. Attempts to run the repair with non-interactive sudo and
to inspect sudo grants both returned `a password is required`. No NTP
configuration was written, the time service was not restarted, and no production
application deployment was performed.

### Administrator action still required

An administrator on the US host can configure the reachable time servers and
restart the existing time service:

```sh
sudo install -d -m 0755 /etc/systemd/timesyncd.conf.d
sudo tee /etc/systemd/timesyncd.conf.d/90-pax-ntp.conf >/dev/null <<'EOF'
[Time]
NTP=
NTP=time.cloudflare.com time.google.com
EOF
sudo systemctl restart systemd-timesyncd
timedatectl show -p NTPSynchronized --value
timedatectl timesync-status
```

The explicit `NTP=` list adds reachable servers alongside per-interface servers;
setting only `FallbackNTP=` would not override the known DHCP NTP source. This
matches the [systemd timesyncd configuration reference](https://www.freedesktop.org/software/systemd/man/latest/timesyncd.conf.html).

After the service reports synchronized status, remeasure the clock offset and
collect another 45-second Worker trace reduced to route/status counts while an
authenticated browser exercises the application. Verify that spurious 401s and
repeated sign-in prompts cease before declaring the incident fixed. The
administrator clock repair does not require relaxing assertion validation or
deploying this cookie-preservation PR.
