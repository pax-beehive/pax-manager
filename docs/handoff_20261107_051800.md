# Secretary stable-source recovery and meaningful queue counts

## Problem and result

Old idle sessions can have stable `sent`/`received` text without a retained normal
terminal event. The previous completion gate waited forever and consumed no model
attempt, while the status counter counted all raw dirty revisions as queued
conversations. A manual Run amplified that misleading count by reconciling history.

The source gate now accepts either the existing reliable completion proof or
settled canonical text. The pending counter reports genuine content, removal,
dependency repair and unfinished current execution work, excluding raw-only
unchanged events. This extends the source-wait reason change in PR 225; no second
stacked PR is needed. Issues 071 and 073 describe the code fix. Deployment remains
separate from code validation.

## Boundaries and data flow

- `storage/secretary_completed_sources.go`: original success-proof predicate plus
  a fallback requiring explicit idle, no contradictory active/unknown lifecycle,
  non-streaming input, and real message/text-part writes at least 30 seconds old.
  PostgreSQL selects a reliable terminal, rather than only the first terminal.
- Prepare and publication reuse eligibility. Publication also checks every input's
  current canonical hash/version, including `no_summary` inputs. Existing related
  frozen references retain immutable version and current ACL checks.
- Existing message/part dirty triggers, invalidations and immutable snapshots
  handle late parts. Original states and checkpoints are not rewritten as a repair.
- `storage/secretary_pending_*`: read-only union of visible owned dirty content,
  removal of processed input, current dependency repair and current execution work.
  Paused, active or deferred work is not falsely reported as complete.
- The pending query hashes dirty identities and dependency references. It expands
  display replacement relationships once per relevant session, preserving existing
  array validation and parent fallback semantics. It avoids repeating that JSON
  check for each candidate. The status read has an eight-second context deadline.
- Search source/replacement predicates are factored into constants; ordinary search
  and unscoped progress keep their existing predicates and result shapes.

No schema, generated API, Console, MCP approval policy, model or deployment
configuration changes are required. Summaries still use full canonical source
versions while assistant prompt input retains its last-paragraph view.

## Concurrency semantics

Eligibility is checked against the publication transaction snapshot. It does not
mean a native execution succeeded. Runtime-only changes racing that snapshot are
not fenced by a new session lock; this avoids introducing a reversed job/session
lock order. A resume already visible to the transaction blocks the quiet fallback.

Late text writes serialize through the job dirty trigger. A write committed first
is caught by hash/version checks or transaction retry; a write waiting behind
publication commits afterward and leaves subsequent work pending. Old snapshots
remain exact and readable subject to current access/deletion rules.

## Verification and rollout

Focused Memory and real PostgreSQL contracts reproduce the historical failure,
and cover fresh/split parts even after manual Run, explicit streaming, runtime
resumption and contradictory unknown lifecycle, cancellation/error text, terminal
ordering, late-part version rejection and subsequent summary revision with exact
old source retrieval. Queue contracts cover ownership, hidden/replaced content,
raw-only changes, deletion, nested invalidations and unknown execution recovery.

Production verification was read-only with five-second statement and one-second
lock limits. Three known old idle sources also had idle/absent runtime lifecycle
and quiet actual source text, so they satisfy the new fallback without data edits.
An initial pending-query plan exceeded five seconds. The final replacement
precomputation plan ran in 1,987.7 ms on 65,030 current dirty candidates (42.2 ms
planning); this is a point-in-time measurement, not a fixed latency guarantee.
An additional read-only simulation treating all existing owned jobs/message state
as dirty returned 199,349 candidates in 6,933.5 ms (42.7 ms planning), close to the
eight-second status budget. Transport, Go scanning, cold caches and future growth
can add latency. Full reconciliation remains an explicit repair operation; it is
not changed to incremental retry in this patch. Large reconciliation statistics
remain a candidate for a separately refreshed, explicitly stale-aware projection.

Final local verification passed:

```sh
GOWORK=off make fmt-check
GOWORK=off make lint
GOWORK=off GOCACHE=/tmp/pax-manager-go-cache go test -count=1 ./...
GOWORK=off GOCACHE=/tmp/pax-manager-go-cache go build -o /tmp/pax-manager-finalization-build-check ./cmd/manager
```

The full Go suite used an isolated PostgreSQL 16 database through
`PAX_MANAGER_SECRETARY_TEST_DATABASE_URL`; its storage package passed in 165.767s.
Changed production statement blocks versus main have 95.8% focused Memory/real-PG
coverage (136/142). New settled-source helpers have 100% statement coverage; new
pending-count helpers have 96.8% (61/63).

The two tagged Secretary HTTP/ACP/PostgreSQL integration scenarios passed all four
cases, including rejected-output recovery. The isolated Docker API suite passed
22 tests with one existing optional skip: the worktree has no sibling `paxd` for
`TestPaxdContainerMockHermesIntegration`. Docker used the current source's cached
Linux/arm64 build with the production distroless runtime, plus PG/ES/MinIO on
unique loopback ports and tmpfs. CI additionally exercises the standard Dockerfile.

The first test PostgreSQL tmpfs exhausted space during DDL-heavy full
tests; a fresh isolated tmpfs with bounded WAL and test-only durability settings
replaced it. No production storage or credentials were used by these tests.

Deploy the normal Manager image after merging. Existing queued sources are checked
automatically; no message-state backfill, fabricated terminal events, global retry,
native agent restart or manual checkpoint reset is part of this fix. Active or
still-changing sources continue to wait. Existing output-capacity/validation limits
and unknown-execution recovery policy remain unchanged (issue 067).
