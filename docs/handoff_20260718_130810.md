# Handoff: Cross-Tenancy Security Fixes (ISSUE-009 through ISSUE-013)

## Summary

A cross-tenancy audit of pax-manager found five authorization gaps. All five
are fixed in the storage layer (postgres + memory stores) with regression
tests. Issues are tracked under `issues/009` through `issues/013` and all are
marked resolved.

## Issues fixed

- **009 (blocker)** - Node status reports could re-home any agent by ID.
  `UpsertNodeStatus` now only updates a conflicting agent when its `node_id`
  and `owner_user_id` match the reporting node; foreign agents and their
  reported sessions are skipped. The memory store no longer rewrites
  `OwnerUserID` (`postgres_store.go` `UpsertNodeStatus`,
  `memory_store.go` `upsertNodeAgentLocked`).
- **010 (blocker)** - Caller-supplied `conversation_id` joined any existing
  conversation as owner member. `StartAgentConversation` now requires the
  source owner to already be an active member of a pre-existing conversation
  (`agent_conversation.go`, new `hasActiveConversationMembership` query;
  memory uses `canReadConversationLocked`).
- **011 (high)** - User-controlled artifact `contents[].bucket/object` were
  stored verbatim and signed by the manager's signing service account.
  `normalizeCreateSessionArtifactRequest` rejects GCS-backed contents (400);
  `handleGetArtifactContent` requires the stored bucket to equal the
  configured session-artifact bucket before signing (403)
  (`artifact_handlers.go`).
- **012 (medium)** - `UpsertRepresentativeAgent` accepted a caller-chosen
  `profile_id` (overwriting other users' profiles) and arbitrary
  `represents_type/represents_id`. Both stores now validate the represents
  subject (user = self; team = active membership in an active team) and
  refuse to update profiles owned by someone else (conflict)
  (`agent_conversation.go` `validateRepresentsSubject`,
  `upsertAgentProfile` owner guard).
- **013 (medium)** - `CreateNodeAgentSession` stamped caller-supplied
  `conversation_id`, `profile_id`, `representative_agent_id`, and
  `created_by_user_id` without validation. Both stores now validate
  references (`validateSessionReferences`): conversation membership,
  profile ownership, representative-agent ownership; `created_by_user_id` is
  coerced to the principal unless it names another active member of the same
  conversation (internal A2A flow), and first-writer-wins on re-upsert.

## Module boundaries and flows

- User-facing identity still comes from request headers
  (`auth.Service.Principal`); the `:user_id` path parameter is not part of
  authorization. Tenant isolation remains a storage-layer responsibility, so
  every fix landed in `internal/manager/storage` rather than handlers.
- The node-facing paxd API authenticates nodes via API key (`NodeAuth`) and
  only pins the top-level node identity; nested report payloads must be
  validated by the store (that is the 009 fix).
- The internal A2A flow (`StartAgentConversation` ->
  `createConversationSession` -> `CreateNodeAgentSession`) creates sessions
  for both participants with principal = each agent's owner. The new
  validations pass for this flow because both owners are conversation members
  before sessions are created and reference their own profiles/reps.

## Tests

New/updated regression tests:

- `internal/manager/storage/agent_status_test.go` - cross-owner and
  same-owner cross-node status reports cannot re-home agents; happy path
  still applies.
- `internal/manager/storage/memory_lifecycle_test.go` - foreign
  conversation ID rejected on start, member continuation works; foreign
  profile/rep references and created-by coercion on session create;
  representative profile conflict and represents spoofing.
- `internal/manager/storage/postgres_agent_conversation_test.go` - scripted
  query rows added for the new membership/ownership checks.
- `internal/manager/server_test.go` - artifact create rejects caller GCS
  fields; content URL refuses foreign buckets.

## Known risks and notes

- `UpsertNodeStatus` now skips foreign agents silently; a node that was
  legitimately re-registered (new `node_id`) and keeps reporting old agent
  IDs will no longer adopt them - agents are expected to be (re)created via
  the register flow instead.
- Direct session artifact creation with GCS-backed contents is now rejected;
  clients must use the upload -> complete flow.
- Representative agents can no longer be pointed at another user's profile
  ID or represents subject; existing bad rows (if any) are not migrated.
- Remaining lower-severity observations from the audit (not fixed here):
  device pairing codes are short and first-come-first-served; paxl device
  login stores a plaintext API key until consumed; team members have write
  access to team-shared agents (design question); ACP tunnel `connection_id`
  is client-chosen and not bound to the authenticated identity.

## Addendum: formatting, lint, and integration test repairs (2026-07-18)

Follow-up work on the same branch:

- `make fmt` was applied repo-wide (29 files). Pre-existing golines
  violations are resolved; `make fmt-check` passes.
- `make lint` now passes (0 issues). Removed five dead functions
  (`projectACPUserRawFrame`, `borrowAnyWait`, `isToolCallHistoryMessage`,
  the storage copy of `appendUniqueString`, `getReliableFrame`). Generated
  hertz handlers are excluded as a directory in `.golangci.yml` because the
  hertz marker is not recognized as generated code.
- `cmd/openapi-gen` now emits the generated marker as the first line, so
  `openapi_generated.go` is skipped by fmt/lint tooling; the file was
  regenerated. This intentionally changes generator + output together.
- `make integration-test`: the paxd image build was fixed by adding the
  `github_token` secret mount to `../paxd/Dockerfile.integration` (sibling
  repo, NOT part of this PR) and passing `--secret` from
  `integration/paxd_container_integration_test.go` when
  `PAX_BEEHIVE_READ_TOKEN` is set.
- ISSUE-014: ACP user tunnel claimed the agent tunnel before it registered
  (registration completes only after the reliablemq reconcile handshake).
  The handler now uses `claimAnyWait` (5s, 50ms), and the integration test
  agent client performs the reconcile handshake. Base commit `5821659`
  failed the same way - both were pre-existing.
- Verified: `make fmt-check`, `make lint`, `go test ./...` all pass;
  integration suite passes except `TestPaxdContainerMockHermesIntegration`,
  which also fails at base. paxd starts but never reports the API-created
  agent online (`agent_connection supervisor ... desired=0`), pointing at
  paxd-side configuration drift in the sibling repo; needs a paxd fix and
  is intentionally left out of this PR.
