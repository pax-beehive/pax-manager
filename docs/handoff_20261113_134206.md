# Secretary stall recovery

## Summary

Secretary tasks kept stopping in states that only an owner action could leave.
This change removes the three execution paths that produced most of those
states and adds a bounded automatic recovery as the safety net for the rest.
The summarizer still runs on the owner's own agent over ACP; no model, input
limit, execution deadline or output contract changed.

Issue 089 is new and partial. Issues 074 and 087 gained follow-up notes and
keep their status. Issue 064 is unrelated and remains open.

## What changed

1. **Failures before the prompt are retried, not unknown.**
   `conversationRunner.promptWritten` is set in `sendTurnPrompt` just before the
   session/prompt frame is handed to the transport. `secretaryNotDispatchedFailure`
   (`internal/manager/secretary_dispatch_retry.go`) wraps every failure before
   that point with `ErrSecretaryNotDispatched`: owner and agent lookup, internal
   session registration, tool registration, runner claim, session/new and the
   pre-prompt checks. These use the existing connection retry budget. Fencing
   is not wrapped. An explicitly unknown outcome stays unknown, because both
   the worker and storage test for it first. It replaces the two narrower
   helpers for tunnel claim and structured slot errors. session/new is bounded
   by `secretarySessionCreationTimeout` (two minutes), because it is now retried
   and the generic request timeout equals the whole execution deadline.

2. **The fence monitor no longer cancels on a failed lookup.**
   `Worker.monitorJob` cancels only for `ErrSecretaryFenced`. Other errors are
   reported once per execution through `OnError` and the execution continues.

3. **An unfinished dispatched turn is always canceled.**
   `promptOwnedSecretaryAgent` sends session/cancel whenever the prompt was
   written and the turn did not complete, not only when the context had ended.

4. **Stalled tasks recover automatically.**
   `Worker.Run` calls `Worker.RestartStalled` once a minute after the initial
   backfill. It uses the optional `domain.SecretaryAutoRestartStore`, implemented
   by both stores in `internal/manager/storage/secretary_auto_restart.go`.
   The decision is `secretaryAutoRecoveryDue`, shared by both stores and made
   under the task lock. A restart reuses `secretaryRestartJobSQL`, which the
   explicit task retry now also uses.

## Automatic recovery rules

A task is stalled when its current batch has an attempt and ordinary claims
skip the source for a reason that does not clear by itself: the job is
`execution_blocked`, the batch exhausted its connection retries, or a guided
operation needs attention. A new source message clears only the first flag,
so each reason counts on its own. Secretary must be enabled, the task not
paused, no lease active, and the task not blocked by the input size limit.

| Batch state | Recovery | Wait measured from |
| --- | --- | --- |
| `unknown`, or `running` behind a blocked job | restart | start of the attempt |
| `blocked`, or `pending` behind a blocked job | restart | last failure of the attempt |
| `output_received` behind a blocked job | release saved output for publishing | when the output was saved |

Restarts wait 15 minutes, then 1 hour, then 4 hours. A batch that already
dispatched two or three attempts gets one restart; a batch that dispatched at
most one gets three, whatever state it ended in. Saved output is released at
most once per attempt (`auto_resumed_attempt_id`). The count
applies only while the job is still in the epoch created by its last automatic
restart, has not published since, and its settings have not changed since. So
publishing, a settings change, every explicit retry and a superseding source
change start a new budget without any other write path resetting a counter.

`secretary_jobs` gains `auto_restart_count`, `auto_restart_epoch`,
`auto_restarted_at` and `auto_resumed_attempt_id`. They are added with `ADD COLUMN IF NOT EXISTS` in
`db/secretary.sql`, applied by `EnsureSchema` at startup like the existing
columns. No data is rewritten.

The PostgreSQL sweep walks every candidate by key. The candidate query mirrors
the decision closely, including source visibility and the per-task wait, so a
task that cannot be recovered right now neither fills the page nor keeps later
tasks waiting. The in-memory store applies pending source changes first, as a
claim does.

## Operational notes

- A restart spends model calls on the owner's own agent. One stalled task
  costs at most five extra calls (1 + 1 + 3 across three restarts) and usually
  one. Exhausted connection retries cost none.
- Each recovery is logged as `Secretary task recovered automatically` with
  `task_id`, `previous_state`, `restarts` and `resumed`. No source content is
  logged.
- Tasks already stalled in production become eligible after deployment under
  the same rules, starting with the first check after startup. The single
  sequential worker bounds how fast they run. Nothing is reset in bulk.
- Secretary does not wait for a tool approval. A turn that asks for one is
  stopped and the approval can no longer be granted for that turn.
- The Console does not yet show when the next automatic restart is due. A
  stalled task keeps its current state and reason until it restarts.
- Deploy Manager only. Console and paxd need no change.

## Review

Two rounds of independent review shaped this change.

The first round found that a task with exhausted connection retries was never
restarted once its source received another message, because the sweep required
the blocked flag that a new message clears. It also found that the candidate
page could starve later tasks, that the documented cost was understated, and
that two states left by a manual recheck were not covered.

The second round confirmed those fixes and found two more: releasing saved
output had no bound and could repeat every minute when a deterministic input
failure blocked the job again, and a batch could spend all three attempts yet
end unknown and so earn the full restart budget. Saved output is now released
at most once per attempt, and the budget is keyed on the attempts a batch
dispatched rather than on its final state.

Every fix has a contract test on both stores, and each guard was checked by
removing it and confirming that a test fails.

## Not covered

- Issue 064: sources whose upstream runtime snapshot stays running.
- Worker concurrency: one slow execution still delays other sources.
- A restart, like the explicit task retry, leaves the replaced batch in its old
  epoch as unknown. The bulk run command skips a source that has any unresolved
  batch in any epoch, so such a source is recovered per task, not in bulk.
- An attempt that is already older than its wait when first classified, for
  example after a long outage, restarts at the next check without a further
  wait for a terminal proof.
- The chat write path still runs Secretary triggers for every message part,
  and `secretary_jobs` has no index on `(source_agent_id, source_session_id)`.
- `EnsureSchema` still reapplies all DDL at startup without a lock timeout.
