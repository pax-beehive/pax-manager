# Secretary stall recovery

## Summary

Secretary tasks kept stopping in states that only an owner action could leave.
This change removes the three execution paths that produced most of those
states and adds a bounded automatic restart as the safety net for the rest.
The summarizer still runs on the owner's own agent over ACP; no model, input
limit, execution deadline or output contract changed.

Issue 089 is new and partial. Issues 074 and 087 gained follow-up notes and
keep their status. Issue 064 is unrelated and remains open.

## What changed

1. **Failures before the prompt are retried, not unknown.**
   `conversationRunner.promptWritten` is set in `sendTurnPrompt` just before the
   session/prompt frame is handed to the transport. `secretaryNotDispatchedFailure`
   (`internal/manager/secretary_dispatch_retry.go`) wraps every failure before
   that point with `ErrSecretaryNotDispatched`: owner and agent lookup, internal
   session registration, tool registration, runner claim, session/new and the
   pre-prompt checks. These use the existing connection retry budget. Fencing
   is not wrapped. An explicitly unknown outcome stays unknown, because both
   the worker and storage test for it first. It replaces the two narrower
   helpers for tunnel claim and structured slot errors.

2. **The fence monitor no longer cancels on a failed lookup.**
   `Worker.monitorJob` cancels only for `ErrSecretaryFenced`. Other errors are
   reported once per execution through `OnError` and the execution continues.

3. **An unfinished dispatched turn is always canceled.**
   `promptOwnedSecretaryAgent` sends session/cancel whenever the prompt was
   written and the turn did not complete, not only when the context had ended.

4. **Stalled tasks restart automatically.**
   `Worker.Run` calls `Worker.RestartStalled` once a minute after the initial
   backfill. It uses the optional `domain.SecretaryAutoRestartStore`, implemented
   by both stores in `internal/manager/storage/secretary_auto_restart.go`.
   The decision is `secretaryAutoRestartDue`, shared by both stores and made
   under the task lock. The transition reuses `secretaryRestartJobSQL`, which
   the explicit task retry now also uses.

## Automatic restart rules

A task qualifies when its job is `execution_blocked`, its current batch has an
attempt and is `unknown`, `blocked` or `pending`, Secretary is enabled, the
task is not paused, no lease is active, and it is not blocked by the input size
limit. A pending batch behind a blocked job is the state a manual recheck can
leave after a retryable failure.

| Restart | Wait | Measured from |
| --- | --- | --- |
| 1 | 15 minutes | start of an unknown attempt, otherwise the last failure of the batch |
| 2 | 1 hour | same |
| 3 | 4 hours | same |

After three consecutive restarts the task waits for the owner. The count
applies only while the job is still in the epoch created by its last automatic
restart and has not published since. So publishing and every explicit retry
start a new budget without any other write path resetting a counter.

`secretary_jobs` gains `auto_restart_count`, `auto_restart_epoch` and
`auto_restarted_at`. They are added with `ADD COLUMN IF NOT EXISTS` in
`db/secretary.sql`, applied by `EnsureSchema` at startup like the existing
columns. No data is rewritten.

## Operational notes

- A restart may spend another model call on the owner's own agent. Worst case
  is three extra runs per stalled task, spread over about five hours.
- Each restart is logged as `Secretary task restarted automatically` with
  `task_id`, `previous_state` and `restarts`. No source content is logged.
- Tasks already unknown or blocked in production become eligible after
  deployment under the same rules. The single sequential worker bounds how fast
  they run. Nothing is reset in bulk.
- The Console does not yet show when the next automatic restart is due. A
  stalled task keeps its current state and reason until it restarts.
- Deploy Manager only. Console and paxd need no change.

## Not covered

- Issue 064: sources whose upstream runtime snapshot stays running.
- Worker concurrency: one slow execution still delays other sources.
- A restart, like the explicit task retry, leaves the replaced batch in its old
  epoch as unknown. The bulk run command skips a source that has any unresolved
  batch in any epoch, so such a source is recovered per task, not in bulk.
- The chat write path still runs Secretary triggers for every message part,
  and `secretary_jobs` has no index on `(source_agent_id, source_session_id)`.
- `EnsureSchema` still reapplies all DDL at startup without a lock timeout.
