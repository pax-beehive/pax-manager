# Native A2A Prompt Delivery Handoff

## Summary

This change fixes native agent-to-agent prompt delivery and reply delivery.

- ACP session id rewriting is limited to the protocol envelope. Nested Pax
  sender and receiver session ids keep their durable Pax values.
- Native A2A delivery no longer sends `session/set_mode`. The runtime already
  creates the session in its configured mode, and the removed request used an
  invalid mode id.
- `POST /api/v1/node/conversation/deliver` now returns `202 Accepted` with the
  receipt immediately after the delivery is stored and scheduled. It no
  longer waits for `session/new` or `session/prompt` to complete.
- Retryable ACP delivery errors, including `session_busy`, are queued and
  retried with exponential backoff.
- Each injected turn has a stable `turn_id`, so a retry with a new JSON-RPC
  request id updates the same prompt and display projections instead of
  creating duplicate database rows.

## Module Boundaries

- `internal/manager/agent_conversation_handlers.go` owns A2A delivery
  orchestration, retry scheduling, and injected-turn metadata.
- `internal/manager/conversation.go` decodes ACP error data and exposes whether
  the runtime marked an error as retryable.
- `internal/manager/acp_history.go` projects ACP prompts into durable message
  history and applies retry idempotency.
- `internal/manager/a2a_invocation_display.go` defines the Pax invocation
  metadata stored in display messages.
- `internal/manager/acp_pipeline.go` translates ACP envelope session ids
  between Pax and native runtime values.
- `internal/manager/server_test.go` covers direct native delivery and the
  retryable busy reply flow end to end.

## Core Request And Data Flow

1. The node posts an ask or reply delivery.
2. The manager validates and stores the conversation delivery, including its
   receipt token and invocation state.
3. The endpoint schedules an in-memory background task and immediately returns
   `202 Accepted` with `delivery_status = queued`. The response does not depend
   on target model latency.
4. The background task claims the target ACP tunnel, initializes a native
   session when necessary, and sends `session/prompt`.
5. If ACP reports a retryable busy error, retries double from 100 milliseconds
   up to one second and stop after 30 seconds.
6. All attempts use the same Pax `turn_id`. The JSON-RPC request id may change,
   but prompt history and the `pax:invocation` display row are upserted under
   the stable turn identity.
7. When the native session becomes available, the delivery completes and the
   agent response is persisted.

## Risks And Operational Notes

- Delivery retry state is in memory and is lost if the manager process
  restarts.
- The retry window is bounded to 30 seconds. A session that remains busy longer
  logs the expiration; there is no durable retry job or final status update.
- ACP errors are retried only when the error data explicitly contains
  `retryable = true`. The existing local tunnel-conflict condition is also
  retryable.
- A `queued` HTTP delivery status means retry scheduling was accepted. It does
  not mean that a durable job exists or that delivery has already completed.
- Because the accepted job is currently in memory, a manager crash between the
  HTTP response and ACP delivery can lose the scheduled attempt. A durable
  outbox is still needed for crash-safe at-least-once delivery.
