# Session configuration catalog handoff

## Outcome

PAX Manager now records the complete session configuration advertised by a
plaintext ACP agent and exposes it to Console. The snapshot includes standard
select and boolean `configOptions`, plus the legacy read-only `models`
payload used by older agents. Model configuration is also projected into the
existing `agent_sessions.model` column.

The snapshot is observed from three protocol points:

1. the successful `session/new` response;
2. the successful `session/set_config_option` response;
3. `session/update` notifications whose nested
   `sessionUpdate` is `config_option_update`.

Observation runs after session lifecycle, manager/native ID translation, and
session request multiplexing. This ensures a new session row exists before the
first snapshot is written and a control response is associated with the right
manager session.

## Persistence

No migration is required. The normalized snapshot is stored under
`agent_sessions.metadata.acp_config` with its source and observation time.
The existing JSONB metadata column remains the durable source for the REST
response. Session status reports that omit a model no longer erase a model
projected from the observed ACP configuration.

## API contract

The endpoints authorize the exact user, node, agent, and session tuple:

```text
GET   /api/v1/user/{user_id}/nodes/{node_id}/agents/{agent_id}/sessions/{session_id}/configuration
PATCH /api/v1/user/{user_id}/nodes/{node_id}/agents/{agent_id}/sessions/{session_id}/configuration/options/{config_id}
POST  /api/v1/user/{user_id}/nodes/{node_id}/agents/{agent_id}/sessions/{session_id}/configuration/refresh
```

PATCH accepts a JSON `value` that must match the advertised option type and,
for select options, one of the advertised values. Permission-category mode is
rejected because the existing permission endpoint owns that policy.

ACP does not define a read-only model-list request. The refresh endpoint
re-applies the current model config value through
`session/set_config_option`; if no model option exists, it re-applies the
first non-permission config option. A successful response must include the
complete current `configOptions`, which replaces the stored snapshot. This is
a deliberate no-op write rather than a read-only query.

Session config controls use a separate per-session mux admission key. They may
run while a prompt turn is active, as allowed by ACP, but two config controls
for the same session are serialized. Legacy `models` has no standard setter or
refresh method and remains read-only. E2EE sessions are rejected because
Manager cannot observe or change their encrypted ACP payloads.

## Client capability

Paxd's persistent ACP initialize profile and Console's direct tunnel runtime
advertise:

```json
{"session":{"configOptions":{"boolean":{}}}}
```

Without this client capability, an ACP agent may omit boolean options such as
fast mode.

## Module boundaries

- `internal/manager/session_config.go` owns ACP parsing, authorization,
  control requests, and the HTTP response contract.
- `internal/manager/domain/session_config.go` defines the normalized domain
  and store interface.
- `internal/manager/storage/session_config.go` owns MemoryStore and
  PostgreSQL metadata persistence.
- `internal/manager/acp_tunnel.go` places observation in both ACP
  pipelines and owns the independent session-control admission key.
- Paxd owns the persistent ACP client initialize payload. Console owns display,
  cache polling, and user-initiated configuration calls.

## Generated artifacts

No generated file changed. These configuration routes follow the existing
custom Hertz route and runtime OpenAPI extension pattern used by agent fleet
and permission catalog endpoints. If the contract is later moved into
`api/pax_manager.thrift`, run `make generate` and commit all derived handler,
router, model, mock, and OpenAPI outputs together.

## Local operation and deployment

No database migration, service restart, or production rollout is required to
review this change. Local validation uses the standard commands from
`AGENTS.md`. A future rollout should deploy compatible paxd, Manager, and
Console builds together and follow `~/pax_workspace/DEPLOYMENT_RUNBOOK.md`.
The paxd update only changes future worker initialize profiles; existing
workers must be recreated by the normal daemon lifecycle before boolean options
can be advertised.

## Known risks and assumptions

- Manual refresh depends on an agent implementing the standard complete
  `session/set_config_option` response and accepting a repeated current value.
- A legacy `models` payload has no standard refresh or setter.
- Console may show a snapshot up to 10 seconds after Manager receives a pushed
  update.
- E2EE payloads remain opaque to Manager and are intentionally unsupported.
- This change is covered by protocol fixtures and unit tests, but has not been
  deployed or exercised against live production Codex, Claude, or Hermes
  adapters.
