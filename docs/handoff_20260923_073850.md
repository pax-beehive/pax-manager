# Cloudflare Access cross-account migration gate

## Summary

pax-manager can temporarily validate browser JWTs from two Cloudflare Access
accounts during a domain and account migration. Existing production behavior
is unchanged unless `CLOUDFLARE_ACCESS_MIGRATION_ENABLED=true`.

There are no database, API schema, generated-code, or paxd changes.

## Module boundaries

- `internal/manager/config` loads and validates the migration gate and the
  secondary issuer, audience, and JWKS URL.
- `internal/manager/auth` owns ordered verifier fallback behavior.
- `internal/manager/server.go` assembles one verifier normally and a two-entry
  verifier chain only while the migration gate is enabled.

## Authentication flow

1. Manager reads `Cf-Access-Jwt-Assertion` exactly as before.
2. The primary Cloudflare Access verifier checks issuer, audience, lifetime,
   signature, and normalized email.
3. If the primary returns `ErrInvalidAccessJWT`, the migration verifier checks
   the same token against the second account.
4. If the primary returns a JWKS transport or other operational error, the
   chain returns that error without trying the migration verifier.
5. Both paths resolve the authenticated email through the existing user and
   authorization flow.

The chain never infers identity from the request hostname or an unverified JWT.

## Configuration

The existing primary variables remain authoritative:

```text
CLOUDFLARE_ACCESS_ISSUER
CLOUDFLARE_ACCESS_AUD
CLOUDFLARE_ACCESS_JWKS_URL
```

Temporary migration variables:

```text
CLOUDFLARE_ACCESS_MIGRATION_ENABLED=true
CLOUDFLARE_ACCESS_MIGRATION_ISSUER
CLOUDFLARE_ACCESS_MIGRATION_AUD
CLOUDFLARE_ACCESS_MIGRATION_JWKS_URL
```

When the gate is enabled, startup rejects disabled Cloudflare Access,
incomplete primary configuration, or incomplete migration configuration.
Configuration errors name variables but never include their values.

## Deployment and removal

1. Deploy the compatible Manager build with the migration gate left disabled.
2. Prepare the protected production env candidate with the three migration
   account values and enable the gate.
3. Deploy Manager through the production runbook and verify authenticated HTTP
   and WebSocket requests through both old and new hostnames.
4. After the old hostnames are retired, promote the company account values to
   the primary variables, remove the migration variables, and deploy again.
5. Remove this temporary code in a later reviewed change.

Do not disable Cloudflare Access or enable local user headers for this
migration. The second cloudflared connector must also be listed explicitly in
`TRUSTED_CLOUDFLARE_PROXY_CIDRS`; that network setting is independent of JWT
verification.

## Verification

The following passed in a Go 1.25 BuildKit test image using an ephemeral SSH
mount for the private paxkit dependency:

```text
go test -count=1 ./internal/manager/config ./internal/manager/auth ./internal/manager
go build -o /tmp/pax-manager-build-check ./cmd/manager
```

No production deployment, restart, or environment change was performed.
