# Standard-session turn notifications and Android badge

## Result and scope

Issue 043 remains partial because encrypted-session terminal signaling and final
device acceptance are open. Standard Manager-owned sessions now create automatic
completion notifications. The companion Console change replaces the opaque app
image used as an Android status badge with a transparent monochrome PAX mark.

The owner confirmed that a manual test push reaches the device, but a real turn
did not notify. The deployed previous implementation had only a test trigger.
Its VAPID bundle is already configured in both regional Managers; this change
does not generate or rotate credentials and is not a production deployment.

## Completion boundary

- The reliable ACP inbound consumer projects terminal history without requiring
  a browser socket, SSE subscriber or in-memory response waiter.
- Only an `end_turn` response from the authenticated agent is eligible. Its RPC
  ID must match durable `session/prompt` history for the same owner, node, agent,
  session and business turn. Cancellation, permission replies, errors and
  uncorrelated responses do not generate completion alerts.
- Inbound journal receipt time becomes terminal history creation time. Retry or
  Manager restart cannot extend TTL or target a device registered afterward.
- `PostgresStore.UpsertMessage` commits terminal history, a stable completion
  ledger record and receiver delivery tasks in one transaction. Memory storage
  does the equivalent under its existing mutex. No push is called by an HTTP
  writer. The ordinary browser `turn_done` marker does not trigger another send.
- Receiver fanout and registration serialize on the owner row. The completion
  lock uses `FOR NO KEY UPDATE`, compatible with concurrent message foreign-key
  key-share locks. Concurrent completions are covered with actual PostgreSQL
  foreign keys and multiple connections.
- The unique notification ID deduplicates canonical turns even if their terminal
  frame is replayed under another message ID. A completion with zero receivers
  still enters the ledger, so later registration does not backfill that turn.
- Business persistence errors propagate to the reliable inbox instead of being
  swallowed as a browser write failure. Browser socket failures still do not
  prevent durable completion processing.

## Sending and API

The existing leased outbox, generic encrypted Web Push payload, bounded retry,
VAPID key checks, receiver revisions and subscription invalidation are reused.
Before sending a turn notification the worker also checks the current stored
session, node and agent ownership. Missing authorization suppresses that task;
an authorization-store error leaves it retryable. Manual tests remain independent
and are rate-limited only against other test notifications.

`turn_completion_enabled` becomes true when the sender and outbox are available.
Console explicitly describes automatic alerts as standard-session support and
states that encrypted sessions are unsupported. Manager never inspects encrypted
history or infers success from idle runtime snapshots. E2EE requires a separate
reviewed, authenticated terminal signal from paxd. No API schema, generated
transport source or paxd protocol changed in this PR.

## Schema and deployment

The additive `notification_completions` table stores only stable notification,
owner, node, agent, session and turn IDs plus completion time. Its primary key
deduplicates fanout. Existing history and delivery tables retain their contracts.

Deploy Manager with its ordinary schema initialization first, then Console.
Continue using the existing stable VAPID environment values. Reopen the Console
to update the root service worker, then complete a new standard-session turn
with the app page closed. Verify provider acceptance in Push subscriptions and
actual system display/click routing on the subscribed device. Old notifications
already displayed by the OS retain their prior icon.

An older Manager can ignore the additive ledger table; no data rollback is
required. If all sending must stop during rollback, disable the sender or revoke
the relevant receivers. Preserve history, subscription, outbox and ledger data.
No production configuration or service restart was performed for this PR.
