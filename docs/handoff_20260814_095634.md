# Session runtime disconnect grace

## Summary

Session runtime projection now distinguishes an authoritative idle turn from a
node-control connection whose last active snapshot has become stale. A
disconnect preserves `running` or `waiting_approval` for 60 seconds. If the
same connection fence is still authoritative after that grace period, active
sessions become `unknown` while retaining their runtime turn instance ID.

## Module boundaries

- `internal/manager/node_control_tunnel.go` schedules the disconnect grace.
- `internal/manager/domain/runtime_state.go` defines `unknown` and the fenced
  stale-marking store operation.
- `internal/manager/storage/runtime_snapshot.go` implements memory behavior.
- `internal/manager/storage/runtime_snapshot_postgres.go` implements the same
  fence check and update transaction for PostgreSQL.

## Runtime flow

1. A node-control connection activates a new opaque runtime fence.
2. On disconnect, Manager starts a 60-second timer for that fence.
3. A reconnect activates a different fence, making the old timer a no-op.
4. If no reconnect replaces the fence, active snapshot-owned sessions become
   `unknown`; their turn instance IDs remain available for compare-and-reset.
5. The reconnecting paxd sends an initial full snapshot. Active turns restore
   running states, while a complete empty snapshot changes omitted unknown
   sessions to idle.

## Generated artifacts

No generated files changed. `runtime_status` remains the existing string field;
`unknown` is an additional value.

## Operational notes

- `unknown` is intentionally not idle and must block new prompts.
- Runtime reset does not cancel the underlying ACP process.
- The fence comparison prevents a delayed timer from an old WebSocket from
  overwriting state reported by its replacement.
