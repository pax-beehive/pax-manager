# Pending approval notifications

## Result

Standard sessions now notify enabled devices when a request needs manual
approval, including when the Console is closed. Pax Auto Approve and reusable
grants do not generate manual approval alerts. Issue 043 remains partial for
the previously documented encrypted-session and device-validation gaps.

## Copy

- Title: `Approval needed`
- Body: `Your session is waiting for your approval. Tap to review the request.`
- Settings: `Get notified when a session needs your approval. Tap a notification
  to open the session and review the request. Requests handled by Pax Auto
  Approve or a saved approval do not trigger notifications.`

## Ownership and flow

`notifications/approval.go` builds a version-1 `approval.required` payload with
an opaque approval ID and the existing Home session URL. Identity is stable per
owner and approval, distinct from completion IDs. TTL is one hour, capped by
approval expiry. No command, approval title, or request description is copied
into the notification.

Both storage implementations enqueue from `CreateApproval` after canonical
session translation. PostgreSQL inserts the approval and receiver deliveries
in one transaction. The existing receiver eligibility, leases, retry policy,
and revision checks apply. No browser connection is required.

The worker uses `ApprovalDeliveryAuthorizer` immediately before sending. Storage
rechecks owner, session access, transport, pending status, expiry, and current
`pax_config.approval_mode`. Pax Auto Approve requests may still produce audit
records but never enqueue a push. Reusable grants are handled before pending
approval creation in the ACP pipeline.

The public configuration adds optional capability `approval_required_enabled`.
No Thrift or generated model change is needed: the existing configuration
handler owns its JSON response. No database or Android migration is required.
The companion Console worker recognizes the type, displays fixed copy, and
uses the existing authenticated Home navigation. Notification clicks only open
the request; approval remains an explicit in-session user action.

## Deployment and validation

Deploy the companion Console worker before the Manager. Existing VAPID keys
and device subscriptions apply. Old Managers omit the new flag and the Console
does not advertise approval reminders until that flag is true.

Validation uses BDD-style testify tests for payload identity, copy, manual and
automatic sessions, status/expiry/access changes, and transactional rollback.
The PostgreSQL tests use `PAX_NOTIFICATIONS_TEST_DATABASE_URL` with an isolated
schema per test. Frontend tests cover reminder display, session navigation,
settings text, and existing turn notifications. Final commands and results are recorded below.

Already delivered notifications cannot be retracted by the Manager. Opening a
stale alert still requires the normal session authorization and shows current
request state. Real push-provider and native OS display are outside local tests.
