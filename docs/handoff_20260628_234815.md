# Envelope Agent Team Access Handoff

## Summary

Envelope creation now supports optional `from_agent_id` and `to_agent_id`.
When both agent IDs are omitted, the existing accepted-friend requirement
continues to authorize the send. When agent IDs are present, both IDs must be
provided together and the send is authorized only if both agents are active in a
common active team where the sender is an active member.

## Module Boundaries

- `internal/manager/userapi`: owns request validation and chooses the friend or
  team-agent authorization path.
- `internal/manager/storage`: owns SQL and in-memory checks for common-team
  agent authorization.
- `internal/manager/domain`: carries the new envelope request and response
  fields.
- `db/init.sql`: adds persistent `from_agent_id` and `to_agent_id` envelope
  columns.

## Core Flow

1. `CreateEnvelope` normalizes `recipient_email`, `from_agent_id`, and
   `to_agent_id`.
2. If both agent IDs are empty, `GetAcceptedFriendByEmail` authorizes the send
   and resolves the recipient user.
3. If either agent ID is present, both are required.
4. `GetEnvelopeAgentRecipient` checks that both agents share an active team and
   that the sender is an active member of that team.
5. The target agent owner's user and email become the envelope recipient.
6. The envelope stores the resolved recipient plus `from_agent_id` and
   `to_agent_id`.

## Risks And Assumptions

- `recipient_email` is still required for the legacy friend path, but is
  optional for the agent path because `to_agent_id` resolves the target agent
  owner.
- If `recipient_email` is supplied on the agent path, it must match the target
  agent owner email.
- The team check is based on active `team_agents`, active `team_members`, and an
  active `teams` row. It does not require the sender to own `from_agent_id`.
- Existing envelopes are migrated with empty `from_agent_id` and `to_agent_id`.
