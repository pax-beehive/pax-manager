# E2EE short-code device authorization

## Change and boundaries

The Console's device flow uses eight decimal digits instead of copying a long
pairing secret. Manager implements an opaque relay and durable lifecycle, not a
short-code verifier. `domain/short_pairing.go` defines the optional store
interface; storage owns SQL, locking, capabilities, deadlines and budgets.
Manual E2EE handlers in `short_pairing.go` share existing owner authentication.
No generated handlers, Thrift contract or generated mocks were edited.

## Request flow

1. Create a pairing with `protocol_version: short-code-v2` and a random 32-byte
   base64 `recipient_capability`. Manager stores its SHA-256 hash; responses
   include protocol version and server time, never capabilities.
2. An authorized browser lists pending requests within the logged-in account
   and agent, then tries up to three requests/current and previous generations.
   `POST /pairings/:id/attempts` takes attempt ID, generation and OPAQUE client
   hello, with an approver capability in `X-Pax-Pairing-Capability`.
3. The recipient lists attempts with its capability. Both browsers perform
   OPAQUE locally. `POST /attempts/:id` advances stages 1 (recipient answer),
   2 (approver finish), and 3 (recipient encrypted pairing secret). Stage 3 sets
   the confirmation deadline. Exact retries preserve committed data/deadlines.
4. Explicit approval uses the existing `/package` route plus `attempt_id` and
   approver capability. Publishing the package, completing the request, and
   consuming the winning attempt (stage 4) are one transaction.
5. `/end` accepts recipient cancellation or rejection by a matched approver.
   Completed requests cannot become cancelled/rejected. Exact terminal retries
   are idempotent. Existing key-package reads work after approval expiry.

Manager cannot prove PAKE success or root-key possession: capabilities protect
relay roles from other logged-in clients; cryptographic verification stays in
browsers. No short code, seed, registration record, password-derived verifier,
or plaintext root key is sent to Manager. The Console pins a reviewed OPAQUE
library; the new application-level protocol has no independent security audit.

## Timing and persistence

Code generation changes every 60 seconds with 30 seconds of previous-generation
grace; new handshakes and messages must finish before that generation deadline.
A matched attempt can be confirmed for 30 seconds, capped by the request's
10-minute expiry. Deadlines are checked on reads/mutations; abandoned requests
reach logical expiry without a sweeper or a device remaining online.

`db/init.sql` is additive and repeatable: request protocol/capability/terminal
columns, `e2ee_pairing_attempts`, and `e2ee_pairing_rate_limits`. Existing requests
become `legacy-v1`. Delivered package storage and cryptography are unchanged.
Each account and account/agent gets 30 handshake attempts per fixed 10-minute
window, counting successes too. Device-scoped advisory locks serialize request
changes; account-scoped advisory locks and transactional UPSERTs serialize
budget reservations across Manager instances. Rotation and request regeneration
do not reset budgets. The browser also maintains a persistent local budget.

Expired attempts remain historical rows, but cannot advance or authorize.
No destructive backfill or retention deletion is included. Do not delete pairing
parents to clean up attempts: existing package foreign keys cascade on parent
deletion. A future retention job can remove expired nonwinning attempts, while
preserving winning attempts needed for idempotent completion and package parents.

## Rollout and validation

Deploy Manager and its normal startup schema migration before Console. Update all
Manager replicas before enabling the new Console. Old Console and paxd command
pairing remain supported; the command option creates a fresh legacy request.
No paxd upgrade, root-key rotation, or browser storage reset is required.

Use the repository's gvm-managed Go 1.26. In an isolated worktree set `GOWORK=off`.
Relevant checks:

- `make fmt-check` and `make lint`.
- `go test -count=1 ./...` and `go build ./cmd/manager`.
- With a disposable PostgreSQL database in
  `PAX_MANAGER_PAIRING_TEST_DATABASE_URL`, run
  `go test -race -count=1 ./internal/manager/storage -run 'TestShortPairing|TestPostgresE2EEPairing'`.
- HTTP tests enforce owner/role capabilities, malformed body rejection and
  terminal behavior. Shared memory/PostgreSQL lifecycle tests cover confirmation
  expiry, cancellation, rejection, idempotency and approved-package recovery.
- PostgreSQL tests run repeated migration over a legacy approved package and
  concurrent attempts on 36 store instances, accepting exactly 30.
- The companion Console PR includes BDD scenarios and real two-context browser
  checks for Worker/WASM, wrong codes, refresh, explicit approval and mobile width.

Issue 032 tracks the new relay and DB work. Existing deployment boundary issues
017 and other unrelated issues retain their current status.
