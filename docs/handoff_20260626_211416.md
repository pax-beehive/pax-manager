# Team Membership and Agent Sharing Handoff

## Summary

Added the first team feature slice for pax-manager. A user can create a team,
invite users with a role, accept or decline invites, list teams, list team
members, add owned agents to a team, remove team agents, leave a team, and have
a team owner remove members.

This change models teams as a trust and access layer. Agent ownership remains
user-owned through the existing `owner_user_id` fields.

## Module Boundaries

- `internal/manager/domain/team.go` defines team, member, invite, and team-agent
  domain types.
- `internal/manager/userapi/team.go` handles user-facing request validation,
  principal resolution, ID generation, and delegation.
- `internal/manager/storage/memory_team.go` implements team behavior for tests
  and local in-memory use.
- `internal/manager/storage/team.go` implements the Postgres adapter.
- `internal/manager/team_handlers.go` binds Hertz route data to `userapi`.
- `db/init.sql` owns the team schema.

Generated Hertz handlers were not modified. The routes follow the existing
hand-written user-facing friend/envelope pattern.

## Data Flow

Create team:

1. User calls `POST /api/v1/user/{user_id}/teams`.
2. `userapi` validates the name and creates a `team_*` ID.
3. Storage persists `teams` and the owner row in `team_members`.

Invite and accept:

1. Owner calls `POST /api/v1/user/{user_id}/teams/{team_id}/invites`.
2. Storage verifies the caller is an active owner member.
3. Recipient calls `POST /api/v1/user/{user_id}/team-invites/{invite_id}/accept`.
4. Storage verifies the pending invite belongs to the recipient and upserts an
   active `team_members` row.

Agent sharing:

1. Owner or operator calls `POST /api/v1/user/{user_id}/teams/{team_id}/agents`.
2. Storage verifies the caller is an active owner/operator member.
3. Storage verifies the agent exists and is owned by the caller.
4. Storage inserts or reactivates `team_agents`.

Member removal:

1. Owner calls `DELETE /api/v1/user/{user_id}/teams/{team_id}/members/{member_user_id}`.
2. Storage marks the member removed.
3. Storage marks that member's active team agents removed.

## Permission Rules

- Owner can invite users, remove non-owner members, add owned agents, and remove
  any team agent.
- Operator can add and remove only their own agents.
- Member can list teams, members, and agents, but cannot manage members or
  agents.
- No role can add another user's agent to a team.
- Owner cannot remove the owner membership in this slice.

## Routes

- `POST /api/v1/user/{user_id}/teams`
- `GET /api/v1/user/{user_id}/teams`
- `GET /api/v1/user/{user_id}/teams/{team_id}`
- `GET /api/v1/user/{user_id}/teams/{team_id}/members`
- `DELETE /api/v1/user/{user_id}/teams/{team_id}/members/{member_user_id}`
- `POST /api/v1/user/{user_id}/teams/{team_id}/leave`
- `POST /api/v1/user/{user_id}/teams/{team_id}/invites`
- `GET /api/v1/user/{user_id}/team-invites`
- `POST /api/v1/user/{user_id}/team-invites/{invite_id}/accept`
- `POST /api/v1/user/{user_id}/team-invites/{invite_id}/decline`
- `GET /api/v1/user/{user_id}/teams/{team_id}/agents`
- `POST /api/v1/user/{user_id}/teams/{team_id}/agents`
- `DELETE /api/v1/user/{user_id}/teams/{team_id}/agents/{agent_id}`

## Known Follow-Ups

- Team-scoped session/message access is not implemented yet.
- Team-scoped envelope/capsule sharing is not implemented yet.
- OpenAPI/thrift generated API descriptions do not include the hand-written team
  routes yet.
- If the frontend needs rich agent cards from `ListTeamAgents`, extend the
  Postgres adapter response to include selected `agents` fields.
