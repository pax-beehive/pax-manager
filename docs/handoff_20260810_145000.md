# Encrypted session identity race handoff

## Summary

Encrypted Console session creation no longer allows runtime discovery reports
to create a second Manager session while the ACP native session id is still
being bound.

## Root cause

The Console first creates a canonical Manager session without a native id and
then sends an encrypted ACP `session/new` command. The native runtime can appear
in paxd scans and active-turn snapshots before the successful ACP response binds
that native id to the canonical session.

Previously, an unknown native id in `session_runtime.snapshot` caused Manager
storage to insert a minimal session row. The paxd session inventory reporter
could also send the native id as its session id. Either path could race the
canonical binding and expose two sessions in the Console.

## Resolution

- paxd session inventory reports only native sessions with an existing ACP
  route whose Manager session id is non-empty.
- The inventory payload uses the Manager session id as `session_id` and retains
  the native id only in `native_id`.
- Manager runtime snapshot reconciliation skips unknown native session ids. A
  later complete snapshot updates the canonical row after inventory ingestion
  establishes the native binding.
- The Manager endpoint regression test covers the race, binding, active update,
  and later absent-to-idle transition while asserting that only one canonical
  session exists.

## Module boundaries

- `paxd/internal/sessionreporter` owns inventory filtering and route translation.
- `paxd/internal/daemon` adapts the daemon store ACP route into the reporter.
- `pax-manager/internal/manager/storage` owns snapshot reconciliation and never
  creates user-visible sessions from runtime-only observations.
- `pax-manager/internal/manager/node_control_tunnel_test.go` verifies the
  node-control report flow against the canonical session store.


No generated artifacts are changed by this fix.
