# Real-network search acceptance handoff

## Change

Added acceptance of the actual Manager process, including its normal startup,
PG schema loading and background search worker. The prior checks exercised the
real PG/ES business service and HTTP/MCP boundaries separately. This layer joins
those boundaries over the network without invoking a worker directly.

No product API, persistence behavior or generated files were changed by this
test-workflow work. There are no related local issue status changes.

## Files and boundaries

- `docker-compose.search-live.yml`: isolated PostgreSQL 16, private Elasticsearch
  9.5.5, and Manager built from the existing Dockerfile. It mounts all three SQL
  schema files and publishes only a dynamically assigned loopback Manager port.
- `tools/search_live_stack.sh`: unique project lifecycle, startup logs, guard
  tests, live runner, merged trace counts and cleanup. The `up` action keeps a
  seeded stack; the `test` action removes its containers and volumes even after
  failure or interruption.
- `tools/search_live_acceptance.py`: standard-library HTTP fixture and a genuine
  stdio MCP subprocess using the existing Secretary adapter. API keys are issued
  through HTTP and retained only in memory/process environment, never printed.
- `tools/test_search_live_acceptance.py`: guards for target validation, SQL
  boundaries, credentials in headers, denied responses, polling deadlines, MCP
  errors and subprocess cleanup.
- `Makefile`: adds `search-live-acceptance`, `search-live-up`, and
  `search-live-down`. Existing `search-acceptance` runs the old focused checks
  followed by the new full-network stage.
- `docs/search_acceptance.md`: updated commands, evidence and local-stack use.

The Manager still owns indexing, source authorization and summary publication.
Fixture SQL is sent only through `docker compose exec postgres` in the dedicated
project. Search, reads, user API-key creation and summary publication use HTTP.
MCP tools communicate through a real newline-delimited JSON-RPC child and the
actual Manager HTTP server. No remote service, normal development database,
Secretary board or stopped background pipeline is used.

## Limits

The local stack enables local header/default-user auth explicitly; production
defaults remain unchanged. ES and PG have no published host ports. Artifact
operations are outside this fixture, so no object-storage service is started.
An uncached Docker build may require `PAX_BEEHIVE_READ_TOKEN` through the existing
BuildKit secret. These checks establish behavior, not production latency or
corpus-scale capacity. No remote deployment or commit was performed.
