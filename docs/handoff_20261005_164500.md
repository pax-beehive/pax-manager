# KEV-90: regional paxl login with client commit

## Scope and boundaries

The CLI owns one durable login attempt in its existing private SQLite database.
The two Managers keep their existing PostgreSQL device-login sessions. The
region-directory Worker reads the existing identity assignment and signs approval
for exactly one region. No D1 schema, row, login record, or new write is added.
Existing signup/bootstrap provisioning is unchanged; this login endpoint never
creates a business account or merges existing regional data.

This is a cooperative client guarantee: simultaneous processes sharing one SQLite
database and attempt choose one region and identity. It is not a global lock across
copied databases, malicious clients, separate installations, or intentional new
login attempts. Such a guarantee would require a shared authoritative arbiter.

## Protocol and module boundaries

1. paxl starts US and HK requests with `protocol=client_commit_v1`, persists their
   poll secrets, and opens one Console link carrying regional approval codes.
2. Console authenticates through its existing AuthGate/RegionGate, then POSTs to
   `/api/v1/region/paxl-login/approve`. Worker reads the existing assignment and
   sends only its region's code to the corresponding fixed Manager origin.
3. Worker signs identity, assigned user ID, region, code and purpose with the
   existing regional provisioning secret. A separate HMAC domain separator and
   short timestamp window prevent reuse as a provisioning signature. Regional
   Manager approval requires that proof and independently authenticates the user.
4. Approval changes `pending` to `confirmed`; it creates neither key nor node.
   Another email cannot replace that session owner. Same-owner retries succeed.
5. paxl polls concurrently and atomically pins Manager URL, login ID, user ID and
   email in SQLite before sending `action=commit` with `expected_user_id`.
6. Manager locks the login row, creates key and node, and updates the login in
   one PostgreSQL transaction. Commit retries return the same credential.
7. paxl validates the returned identity and region and transactionally saves the
   credential with its receipt, then sends `action=ack`. ACK clears the replayable
   key and is idempotent until expiry. Only a consumed response finishes local
   cleanup. Unknown outcomes preserve the attempt for the next `paxl login`.
8. Losing requests are cancelled or expire. Cancel cannot undo an issued key.
   Unacknowledged keys stop authenticating at expiry even before cleanup; stale
   session cleanup revokes them. Acknowledged keys retain normal lifetime.

The new protocol is explicit: a new CLI refuses old Managers that do not echo
support. Legacy requests retain their protocol, with key/node creation now atomic.
They do not acquire the new multi-region guarantees.

`paxl login --admin --manager-url https://hk-api.paxworkspace.net` is an explicit
administrator destination override. Worker does not change the directory and the
HK Manager requires an already existing regional administrator account. Ordinary
login cannot override the assigned home region.

## Files and schema

- Manager domain exposes protocol/action fields. Service handles transport and
  identity; storage owns state transitions, row locks, issuance and expiry.
- `db/init.sql` adds a PostgreSQL `protocol` column and an index for unacknowledged
  credentials. Deployment must apply the normal idempotent database initialization.
- Worker `src/paxl-login.ts` owns read-only home routing and signed approval.
- paxl facade owns regional orchestration; model/store owns local conditional
  selection, candidates and atomic credential/receipt persistence.
- Console feature parses links and calls the same-origin Worker. The page displays
  the approving identity, destination for admin mode, and actionable failures.
- No Thrift endpoint was added. `go generate ./internal/manager` was run and
  generated OpenAPI artifacts were unchanged. Do not hand-edit generated handlers.

## BDD scenarios and TDD evidence

Behavior tests were introduced incrementally, observed failing, then implemented.
The major red-to-green checks were: failed approvals leaking credentials; approval
creating credentials before selection; lost commit response; identity switching;
local durable selection; Worker routing; signed proof; missing/invalid ACK; and
unacknowledged credentials remaining usable after expiry. Additional regression
checks cover the following matrix:

| Given / When | Then |
|---|---|
| Two regional approvals use different emails | One local selection remains pinned; the other region is never committed |
| Two processes race using the same local attempt | SQLite returns the same durable winner, including after reopen |
| Sixteen conflicting approvals race | A regional session has one owner; confirmation creates no credential |
| Sixteen commits race or a response is lost | One credential/node; retries recover the same result |
| Node insertion fails after key insertion | PostgreSQL rolls back both |
| Commit races cancellation | One terminal outcome; no orphan credential |
| Wrong owner, poll token, signature, region, code, or action | Reject without issuing credentials |
| Credential persisted, ACK response lost | Retry recognizes the saved receipt and completes idempotently |
| ACK returns an unexpected status | Preserve the attempt instead of reporting successful login |
| Unacknowledged credential expires | Authentication fails immediately; cleanup revokes the key |
| Home code/region is unavailable | Visible error; no fallback to the other region |
| Non-admin requests admin override | Target Manager denies it |
| Existing legacy client retries approval | Same key/node; failed requests create no orphan keys |

## Validation and operations

Tests use an isolated disposable PostgreSQL 17 database and separate schemas.
Set `PAX_MANAGER_LOGIN_TEST_DATABASE_URL` to an isolated database to run the real
PostgreSQL cases; without it those cases explicitly skip. No production test data
or deployment is required. Run:

```sh
GOWORK=off go test -count=1 ./...
GOWORK=off go test -race ./internal/manager/storage -run PaxlLogin
GOWORK=off make fmt-check lint
GOWORK=off go build -o /tmp/pax-manager-build-check ./cmd/manager
cd workers/region-directory
npm run typecheck
npm test
```

In paxl run `go test -count=1 ./...`, focused race tests, lint and build. In Console
run the auth/page Vitest tests, typecheck, ESLint and production build. Coverage is
measured for new/changed backend statement blocks, not the unrelated whole-repo
average. Final validation results are recorded below.

## Rollout and risks

These worktrees contain implementation only; no release or production deployment
has been performed. Install Worker routing and the new Console first, then both
Managers with the PostgreSQL migration, and the new CLI last. Worker signed
approval remains compatible with older Managers during staging. After regional
Managers enforce proofs, cached old Console code must be refreshed; a stale page
fails closed. Do not release the new CLI before both Managers support the protocol.
Rollback CLI first if necessary. Existing credentials remain valid.

Local issue 035 is partial pending coordinated release and live HK verification.
Other open regional provisioning/machine routing work remains out of scope.
