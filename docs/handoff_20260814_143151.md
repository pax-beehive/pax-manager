# ACP permission catalog handoff

## Summary

This change adds a manager-owned permission catalog for ACP agents. The user
API exposes one list containing the synthetic PAX auto-approve choice and the
agent-native permission choices. The browser does not match ACP adapter or
runtime versions itself.

The direct conversation endpoint now accepts `permission_choice_id`. Native
choices are validated against the actual `session/new` response and applied
with `session/set_config_option` (or legacy `session/set_mode`) before the first
prompt. Native choices always force PAX manual approval. The PAX synthetic
choice always forces `auto_approve_all`.

## Module boundaries

- `internal/manager/node_control_tunnel.go` parses sanitized paxd ACP pool
  capability report schema v1 and v2. Malformed, unsupported, or absent
  identity data becomes an `unknown` identity without rejecting the runtime
  status snapshot.
- `internal/manager/domain/permission_catalog.go` owns persisted and public
  permission catalog types and the built-in Codex profile seed.
- `internal/manager/storage/permission_catalog*.go` owns in-memory and
  PostgreSQL persistence.
- `internal/manager/permission_catalog.go` owns profile matching, observation
  projection, public catalog resolution, validation, and the user handler.
- `internal/manager/conversation.go` owns the create-session request behavior.

## Database schema

`db/init.sql` creates three independent tables:

- `agent_runtime_identities`: one current sanitized paxd identity per agent.
- `agent_permission_profiles`: append-only profile revisions keyed by
  `(profile_id, revision)`. Profiles may be global or owner-specific.
- `agent_permission_observations`: the latest session permission catalog per
  `(agent_id, identity_fingerprint)` with a TTL and content revision.

The global `codex-acp.permissions` revision 1 seed is inserted with
`ON CONFLICT DO NOTHING`, so startup never overwrites an existing revision.
Its native choices are read-only, agent, and agent-full-access. Its default is
agent. Full access requires confirmation and cannot be configured as a profile
default.

## Identity and matching flow

Paxd reports runtime identity through:

```text
runtime.snapshot
  -> agents[].acp_pool_capability_report
  -> implementation.acp_agent
  -> implementation.runtime (optional)
  -> implementation.identity_fingerprint
```

The adapter-declared allowlisted `_meta.pax.runtime` identity wins when it is
present. For the known Codex ACP launch forms only, paxd otherwise performs a
bounded `codex --version` probe and reports that sanitized CLI version as the
underlying runtime identity. The probe never interpolates ACP arguments or
initialize metadata into a command.

Schema v1 is accepted with a conservative derived fingerprint. Schema v2 may
omit ACP agent or runtime details; missing fields reduce confidence instead of
breaking status ingestion. `client_profile_hash`, command fingerprint, and
worker-result hash are folded into the observation discriminator so an ACP-only
implementation fingerprint cannot reuse a catalog across materially different
launch profiles. Known fields must match the profile constraints. Unknown
version fields are candidate matches and make profile and observed results
stale.

Every node-control connection supplies the existing runtime fence as a report
epoch. Storage rejects snapshots from an old fence, but accepts generation 1
from a new epoch even when paxd reuses a durable connection ID. Within an
accepted runtime snapshot, identity state is authoritative: a missing or bad
capability report replaces a prior consistent identity with an unknown
sentinel, so an old observation is no longer trusted.

Resolution order is:

```text
unexpired observation for a consistent current identity
  > owner-specific active profile
  > global active profile
  > PAX auto-approve only
```

`pool_consistency=mixed` or `inconsistent` returns PAX-only. Unknown pool
consistency does not consume a slot observation; it may use an agent-type
profile marked stale. Observations are best-effort cache writes and never block
ACP session creation. A successful `session/new` with no permission options is
stored as a negative observation, replacing any old native choices for that
identity. Live options not mapped by a validated profile are returned with
`risk=unknown`, require confirmation, and are never selected as the default.

## User API

```text
GET /api/v1/user/{user_id}/agents/{agent_id}/permission-catalog
```

The route requires the authenticated user to own the agent. Team visibility is
not sufficient. The response data is:

```json
{
  "catalog_revision": 1,
  "source": "observed",
  "stale": false,
  "default_choice_id": "agent:mode:agent",
  "choices": [
    {
      "choice_id": "pax:auto_approve",
      "label": "Auto approve (PAX)",
      "kind": "pax"
    }
  ]
}
```

Adapter/runtime identity and matching details are intentionally absent. The
path is added to the runtime-generated OpenAPI document.

## Conversation flow

The direct conversation JSON body accepts `permission_choice_id`. It may also
include the legacy `approval_mode` during migration, but the two must agree:

- `pax:auto_approve` requires `auto_approve_all`.
- Every `agent:*` choice requires `manual`.

For an agent-native choice, Manager performs:

```text
session/new
  -> parse live mode configOptions, falling back to legacy modes
  -> require the exact stable choice/value to exist
  -> session/set_config_option or session/set_mode
  -> persist PAX session policy and choice snapshot
  -> session/prompt
```

Missing live permission data returns 502. A cached/profile choice that is not
present in the live result returns 409. A failed set-config RPC aborts before
the prompt. Any failure after `session/new` triggers a bounded best-effort
`session/close` and removes the exact provisional manager binding while
preserving the original error response.

## Operational notes

- There is no admin profile mutation endpoint in this change. New revisions
  can be inserted through controlled database operations until an admin API is
  added.
- The ACP lifecycle persists the native session binding as soon as
  `session/new` succeeds. Until the permission choice is validated, configured,
  and persisted, that binding is treated as provisional and is cleaned up on
  failure as described above.
- The direct conversation path is integrated. A2A-created sessions retain
  their existing approval behavior because they do not yet accept a user
  permission choice. Any later legacy approval-mode override clears the stored
  creation choice while preserving unrelated session config such as cwd.
