# Notification subscription registry and administrator dashboard

## Result and scope

Delivery 2 of issue 042 is implemented. The Console exposes
`/admin/notifications`, adjacent to Customers in administrator navigation, with
a shared two-page switcher for desktop/mobile. It displays filtered regional
totals, paginated receivers, subscription status, the last client permission
report, registration/expiry dates, and receiver details. Customer links preserve
regional user references before the existing email merge. The page uses real
API data and truthful empty/unavailable states; browser QA fixtures exist only
in the test script.

The backend includes additive PostgreSQL schema, matching memory storage,
idempotent owner-derived registration, cross-owner rejection, a twenty-receiver
limit, key-erasing revocation, and an administrator-only metadata query. Registry
mutation locks the user first so registration/revocation cannot move revisions
backward. SQL summaries and pages use a read-only repeatable-read transaction.
Literal search escapes wildcard characters and pagination is by receiver ID.

This is a registry/dashboard release, not a working push sender. Actual turn
notifications, the delivery outbox/worker, permission/subscription UI, service
worker, and E2EE terminal signal remain deliveries 3-5. Latest delivery is null
until real attempts exist, and the UI shows `No delivery attempts`.

## Modules and API

- `notifications/registry.go`: registration validation, stable receiver identity,
  expiry, metadata-only DTOs, state projection and optional registry interface.
- `storage/notification_receivers*.go`: PostgreSQL and memory implementations;
  `db/init.sql` creates `notification_receivers` through normal schema startup.
- `userapi/notification_http.go`: authentication-dependent HTTP behavior, strict
  bounded registration input, admin/owner scoping, sanitized errors.
- `notification_routes.go`: bounded buffered JSON bridge into Hertz; no streaming
  connection is required. `idl_handlers.go` bridges generated handlers.
- `workers/region-directory/src/notification-subscriptions.ts`: guarded fixed
  US/HK reads, regional cursors, metadata allowlist and explicit partial failures.
- Console `features/analytics/subscription-*` and `use-subscriptions.ts`: typed
  snapshots, filter/identity-scoped TanStack keys, stale retention and focused
  polling. Each filter change remounts the result observer and cancels the prior
  request. `components/analytics/subscription-dashboard.tsx` owns the view.

Routes under `/api/v1/user/self`:

```text
GET    /notification-subscriptions                 administrator metadata
GET    /notifications/receivers                    current owner's metadata
GET    /notifications/config                       public registration config
PUT    /notifications/receivers/web-push            register current owner
DELETE /notifications/receivers/{receiver_id}       revoke current owner
```

The canonical Worker aggregates the admin endpoint as it does Customer analytics.
Any regional 401/403 denies the aggregate; outages may retain marked stale data.
The existing regional Node gateway continues its existing local-Manager read
behavior for metadata; adding cross-region administrative aggregation there is
outside this change. No routing/authentication protocol was replaced.

Server-side registration configuration is `PAX_WEB_PUSH_PUBLIC_KEY` and
`PAX_WEB_PUSH_KEY_ID` (default `default`). With no public key, registration is
unavailable but authorized registry reads remain usable. No private key or push
provider configuration was generated. The runtime has no hardcoded sample rows.
