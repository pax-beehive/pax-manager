# E2EE pairing lifecycle and browser recovery

## Behavior and boundaries

This change builds on the existing, uncommitted KEV-66 supersession changes.
No production database was cleaned, and no existing work was reverted.

The manually registered E2EE user API now includes:

GET /api/v1/user/{user_id}/agents/{agent_id}/e2ee/pairings/{pairing_id}

Only the owning user can inspect the request. It returns the existing request
metadata plus status: pending, approved, expired, or superseded. An approved
request remains approved after its approval deadline. No root key or pairing
secret is returned. The existing node read and both completion paths still
reject superseded requests. Storage returns the scoped request together with
the supersession error so only this read-only status handler can report it.
There is no new schema change beyond KEV-66's existing superseded_at migration.
These E2EE routes are manually registered; no generated Thrift files were edited.

Console first attempts to recover the matching encrypted package, including an
approved package retained while a newer request is pending. If a later approved
package replaced that slot, the old request is no longer a recoverable delivery.
Expired and superseded requests stop waiting; Create new request always creates
a fresh ID. Lost POST responses and 5xx preserve browser recovery material;
definitive rejections remove only the failed attempt's local pending record.
Network/auth failures do not imply expiration. Automatic recovery retries are
bounded by the stored deadline, while explicit checks, focus, and reload remain
available. Browser generation checks fence late results from previous requests
or agents. No automatic bulk deletion or root-key rotation is introduced.

## BDD and TDD

Console acceptance scenarios: docs/e2ee-pairing-lifecycle.feature in pax-console.
Tests were written first: the original four orphan/recovery cases failed;
new status GET tests failed before the route existed; an additional missing-
request deadline test failed before its terminal handling was implemented.
After implementation, the failing assertions pass without skipping them.

Relevant suites:

- Manager e2ee_pairing_status_test.go: owner scoping, pending, expired,
  superseded, and approved beyond the deadline.
- Storage e2ee_orphan_recovery_test.go and existing lifecycle/PostgreSQL tests:
  abandonment, replacement, late package retrieval, races, and migration.
- Console key-distribution-recovery, pairing-lifecycle, use-browser-pairing,
  and e2ee-pairing-page tests: lost responses, fresh IDs, expiry, recovery,
  stopped polling, and stale asynchronous operations.

## Validation and rollout

Use Go 1.26 via gvm. Required checks are make fmt-check, make lint, full go test
and manager build. Real PostgreSQL coverage uses an isolated temporary container
with PAX_MANAGER_PAIRING_TEST_DATABASE_URL; never set it to production.
Console validation uses TypeScript, targeted ESLint, and Vitest E2EE/Home suites.

Deploy Manager with KEV-66's schema and supersession behavior first, then Console.
Drain old Manager instances before relying on supersession fencing. New Console
cannot confirm pending state against an old Manager missing the status route;
it exposes Check again / Create new request rather than waiting indefinitely.
Existing paxd pairing and encrypted transport wire formats are unchanged.
This task implements and tests the changes; it does not deploy them.
