# Search summary source visibility cost

## Diagnosis

The search API groups ES matches by session, then revalidates current PG
visibility. Summary reads validate their dependencies through
`validateSearchMessageAccess`. Although that helper batches message reads,
the replacement predicate repeatedly scans and parses the same display rows
for every source message in a shared session.

Production read-only, owner-scoped probes measured 90 / 260 / 1451 ms on three
larger summaries before network transfer and Go canonicalization. The slow
409-source plan uses the existing display partial index 409 times, with 6953
JSON replacement validation calls. Four generic `port` / `search` probes showed
ES internal time of 99-139 ms; the node was healthy and had no queued search.
Docker-exec overhead is excluded from that ES internal metric. These are
component probes, not timings of the user's exact request or complete API.

No production body, title, evidence, query history, source ID list, credentials
or cursor was exported. Only timings, counts and safe plan-node metadata were
returned. There are no historical per-stage search latency logs to reconstruct
the reported request completely.

## Change and boundaries

The focused correction materializes relevant agent/session scopes and display
replacement classification once per batch, then checks target messages against
that prepared replacement set. The normal canonical message/parts validation
remains in Go; owner, node/session deletion and archival checks remain in SQL.
This is transaction-local query work, not a cache of permissions across requests.

Valid nonempty replacement arrays containing only strings/null override the
parent. Empty, missing, scalar or invalid-member arrays fall back to the parent.
Null and empty session IDs remain distinct; display checks remain scoped to
both agent and session. A display row's own role/hidden state does not change
the old replacement semantics. Null entries cannot hide unrelated messages.

Only the batched summary-source access path changes. Single-message lookup
keeps the existing predicate. Public APIs, ES query/ranking, storage schema and
indexes are unchanged. A Manager deployment is required to activate the fix.
No production deployment or data mutation is included.

## Verification

TDD first reproduced 3072 array-processing loops for 128 source messages and
24 display rows. With the correction the same plan performs 48 loops, bounded
by display classification and expansion rather than their product with source
count. The changed validator has 88.9% statement coverage. Real PG tests cover
63 replacement-shape/type cases, five session/agent scope variants and the
existing canonical visibility changes. Independent SQL semantics review found
no blocker.

A read-only repeatable-read production comparison returned these SQL-only
execution times. Old/new results are from the same snapshot and environment;
the second query may benefit from warmed buffers. They are not endpoint latency
guarantees:

| Source messages | Existing SQL (ms) | Optimized SQL (ms) |
|---:|---:|---:|
| 426 | 89.700 | 48.739 |
| 419 | 269.399 | 48.568 |
| 409 | 1561.589 | 58.319 |

An additional same-snapshot set comparison reported zero symmetric differences
for each of these samples. It returned only numeric counts, with no source IDs
or content. The runtime was not changed: these were read-only SELECT/EXPLAIN
probes, not a production deployment.

Final checks passed:

  both search and Secretary test DB URLs pointing to the task-owned PostgreSQL.

  case skipped because this worktree has no sibling Paxd repository.

- `git diff --check` and independent final SQL/permission semantics review.
