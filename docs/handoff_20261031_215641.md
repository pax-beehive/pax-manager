# Complete private VM Elasticsearch deployment

The US deployment had no SEARCH_URL or ES service, and its restored old Manager
binary also lacked workspace search routes, returning 404. In current Manager
source, search requires ES and returns 503 when its backend is unconfigured;
PG-backed chat and summary persistence remain independent of ES. There is no
PostgreSQL full-text fallback in the search API.

## Source changes and boundaries

deploy/vm/search.sh retains the pinned ES image, persistent volume, private
network, memory limit and restart policy. It now waits for bounded cluster
readiness before attaching Manager, repairs existing network membership, adds
a health command and supplies a Docker health check and file descriptor limit.
It does not expose a host port or delete data.

deploy/vm/configure_search.py performs one controlled same-image replacement
to set SEARCH_URL, SEARCH_INDEX and a persistent SEARCH_READ_RECEIPT_SECRET.
It holds the existing Release agent lock, rejects unresolved task state,
retains the original container and checkpoints credentials privately before
switching. It copies the immutable image, complete prior HostConfig and all
network endpoints including static IPAM and aliases. Local probes require both
200 health and 401 for unauthenticated user access. Failure restores the exact
previous identity; explicit rollback/recover handles interrupted operations and
refuses foreign replacements. No release journal is edited or deleted.

Current direct Release deployment already clones the active Manager environment
and networks, so subsequent application releases preserve search configuration.
The old GCloud deploy.sh remains unchanged and is not the US deployment path.
No application Go, API, schema, generated artifacts or pax-release engine change
is required. No tokenizer, model, embedding or board maintenance is added.

docs/search_deployment.md documents first activation, private state handling,
rollback, the actual US deployment paths and historical-launcher differences.
CI runs both new helper suites using its existing Python coverage dependency.

## US operations

The host already has vm.max_map_count=1048576 and sufficient available memory
for the existing 2 GiB ES limit. The image was pulled by the pinned repository
tag, resolving to docker.elastic.co/elasticsearch/elasticsearch@sha256:13b4a40bb095774f5fda635e45fd5677cc6a26565e42b24997b0c72b88e75984.
The supported recover-agent command reconciled the earlier failed rollback
against the healthy original Manager without restarting it; local active state
became empty. The deployment timer was paused for the controlled configuration
operation. Private operation artifacts are under
~/.local/share/pax-search-ops/20261101T045413Z; they contain credentials and must
not be committed or printed.

ES started as pax-search on pax-search-private with durable pax-search-data,
unless-stopped restart, a 2 GiB memory limit and no published host ports. Its
initial cluster health was green. Same-image Manager activation succeeded and
retained the original container. The protected host env source was updated,
the release agent's Manager health window became 240 seconds, and SEARCH_URL
and SEARCH_INDEX were added to its required_env guard. The deployment timer
was resumed. Installed helpers are under ~/.local/lib/pax-search.

This exposed a separate runtime-version problem: the restored old Manager binary
had none of the SEARCH_URL, search-worker or search-API strings, returned 404 for
POST /api/v1/user/self/search and had not created search_sync_state. The retained
previously attempted image did contain all three runtime features. Source/schema
file equality alone had concealed the different executable versions.

The same existing verified candidate digest
ghcr.io/pax-beehive/pax-manager@sha256:f710c45f6d1c174f123739f18baf6def9c66ac044072fde0327b0daf836e2105
was submitted as normal Release task dep_eb5c8135689d4df0904f1c461492dbea to prod-us.
The public operator CLI call received an edge 403; the controller's supported
localhost API at 127.0.0.1:18084 accepted the existing operator bearer and the
same new idempotency key. Application authorization, image validation, audit,
task queue, agent claim, heartbeat and reporting remain unchanged. Access policies
and operator credentials were unchanged. State transitions used the supported
recovery command and normal controller API, without manual release-state edits.

The normal Release task succeeded with rollback not needed. The requested
search-enabled Manager inherited all three networks, safe authentication flags,
SEARCH_URL, SEARCH_INDEX and the persistent receipt secret. Local health returned
200, unauthenticated user access returned 401, and unauthenticated POST search
also returned 401 rather than the old binary's 404. The release agent returned to
idle with no blocked state. ES stayed green with no published host ports.

Two read-only snapshots showed indexed documents increasing from 60 to 260.
At the latter snapshot search_sync_state contained 230031 total sources, 229771
pending, 260 indexed and zero errors. Historical backfill is asynchronous and
not complete at handoff; do not describe every old message as searchable yet.
No authenticated production search query was submitted because the existing
frontend lacks the search page and no suitable user credential was available.
Fixture tests cover authenticated search; this deployment evidence proves runtime
route presence, preserved authentication and live PG-to-ES synchronization.

The logged-in production Console currently returns 404 for /search. This source
change targets US backend search deployment; it does not deploy the separate
Console frontend. ISSUE-049 remains open for that release and browser validation.
Do not claim that the browser search page is commissioned.
