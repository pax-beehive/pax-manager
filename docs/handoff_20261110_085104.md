# Mobile runtime operator integration

## Change and boundaries

The owner of a node can operate its managed Android devices through
`POST /api/v1/user/:user_id/nodes/:node_id/daemon/mobile`. This follows the
existing browser operator path. The user API resolves the principal and checks
node ownership before sending a transient `mobile.control` query on the existing
authenticated node control WebSocket. It does not create mailbox/history events.

The request is `{operation, payload}` with `application/json` content type.
Simple cross-site content types, unknown envelope fields, trailing JSON and
envelopes larger than 32 KiB are rejected. Payloads must be JSON objects of at
most 16 KiB. The fixed operation set is `state`, `templates`, `create`, `start`, `stop`,
`destroy`, `takeover`, `release`, `screenshot`, `tap`, `swipe`, `text`, `key`,
`recording_start`, `recording_stop`, `recording_list`, and `recording_read`.
Responses retain the existing daemon-query envelope, with the operator result
under `data.mobile_control`.

The paxd adapter validates exact arguments and device/recording identifiers. It
resolves the local runtime configuration and private operator token on the node,
uses only a fixed loopback HTTP origin, strips credential paths and private
response fields, and returns recording files in bounded 256 KiB chunks. Screenshots
are bounded separately. Inputs require an explicit device, operator takeover,
and a fresh single-use screenshot frame ID. Ambiguous input is not retried.

This is the node operator UI path. It does not install an MCP server into an
agent harness or silently bind the last used phone to a Pax session. Local
WebRTC remains media-only and same-host; remote offers, arbitrary proxy URLs,
ADB/shell, APK filesystem paths, and login/credential operations are rejected.
Pax remote viewing uses screenshots and completed audio/video recordings.

## Sources and generation

- `api/pax_manager.thrift`: request and authenticated HTTP endpoint definition.
- `internal/manager/mobile_idl_handlers.go`: thin handwritten HTTP bridge.
- `internal/manager/userapi/mobile_control.go`: operation and payload policy,
  then existing principal/node ownership and node-control interfaces.
- `internal/manager/idl_handlers.go`: generated-handler dispatch registration.
- `internal/transport/http/**` and `internal/manager/openapi_generated.*`:
  generated from the IDL with `make generate`; do not hand edit.

No persistence schema, production auth defaults, browser endpoints or existing
issue statuses changed. Parallel changes live in separate mobile integration
worktrees for paxd and pax-console; the runtime is in agent-mobile-runtime.

## Local setup and verification

Use the installed Go toolchain managed by gvm. In this isolated worktree the
parent workspace's go.work names the main checkouts, so set `GOWORK=off` for
generation, checks and builds. Do not modify the shared go.work.

```sh
source /Users/gengcongkai/.gvm/scripts/gvm
gvm list
gvm use go1.26
export GOWORK=off
make generate
make fmt-check
make lint
GOCACHE=/tmp/pax-manager-go-cache go test -count=1 ./...
GOCACHE=/tmp/pax-manager-go-cache go build -o /tmp/pax-mobile-manager-build-check ./cmd/manager
```

The Android SDK, clean private AVD and media dependencies must be prepared on
the node using agent-mobile-runtime's setup instructions. Start that service
with its private configuration and set the same `AGENT_MOBILE_CONFIG` for the
isolated paxd process. Runtime credentials stay out of Manager and Console.
Do not publish its local control port or restart an unrelated running daemon.

The focused tests cover node ownership, forbidden network/credential/signaling
operations, malformed/oversized payloads, and an actual HTTP-to-node-WebSocket
round trip with a screenshot larger than 1 MiB. SDK capture and rendered Console
acceptance are separate tests; fake node results do not prove emulator capture.
Node queries use the existing per-node serialization, so a cold emulator boot
can temporarily delay other node control queries.

Generation, `make fmt-check`, both normal and integration-tag `make lint` passes,
the complete `go test -count=1 ./...` suite, and the manager binary build passed
in this worktree with Go 1.26. The Docker integration stack was not started;
this change does not alter Docker behavior or reset shared development volumes.
