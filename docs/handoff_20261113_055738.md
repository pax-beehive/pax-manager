# Secretary source-only summaries and historical execution recovery

## Final behavior

New Secretary work uses the frozen output policy summary-sources-v2. The model
returns summary titles, bodies and selected source message IDs, with one existing
processing outcome for each changed or removed message. It no longer copies
claims or quotation evidence. Baseline prompts omit old claim/evidence metadata;
compatibility echoes of claims are ignored by the new decoder. No quotation
alignment, semantic verifier, extra model call or embedding service is added.

Manager resolves selected IDs against supplied messages and the same node's
unchanged coverage. Optional outside sources retain exact references and verified
read receipts. Ownership, source visibility/completion, source versions, baseline
CAS, representative coverage and atomic progress remain enforced. Provenance is
traceability, not a guarantee that the summary's meaning is correct.

SummaryVersion, summary_sources, message_snapshots, immutable history and the
existing search/API/read structures are reused. Old revisions are not rewritten.
Fresh revisions contain body/title and provenance without model-generated claims.
There is no new table, database rewrite or frontend migration.
Legacy facts present only in old claim text are not synthesized into the new
baseline body; they remain available in immutable history and explicit reads.

## Versioning and module boundaries

- Domain defines the output policy separately from the existing input-view
  policy. SecretaryJob stores it as an optional frozen JSON field.
- Fresh storage preparation selects the new policy. Nonempty policies participate
  in run/batch identity; the omitted field preserves historical ID encodings.
  Restoring an unfinished legacy batch retains its original empty/legacy policy,
  original inputs and original instructions. Unknown policies are rejected.
- Secretary prompt/decoder/publication paths branch by that frozen policy.
  Legacy parsing and exact quote checks remain available for already frozen
  executions. General summary storage continues reading full and compact legacy
  claims. Receipt identity is checked separately from the immutable version.
- A structured retryable slot_unavailable response to session/new is classified
  as not dispatched. The existing exponential connection retry applies; failures
  after prompt dispatch are still uncertain.
- A persisted native end_turn can prove completion only when its prepared
  Manager dispatch, immutable binding, owner/agent/session/turn, exact RPC ID and
  successful response match. Known failures take precedence, and the reader
  excludes later notifications from the completed response.

Deploy a compatible Manager reader/writer together. An older binary does not
understand the new frozen output contract. Merging/deploying does not itself
reset jobs, adopt a new policy for old open batches, or replay unknown work.

## Production diagnosis and scoped operations

Production Manager was 6453907. A bounded owner-scoped audit found seven tasks
with errors; none currently reported the deterministic input-size limit. Frozen
JSON ranged from about 5 KiB to 131 KiB, including baselines and metadata. Actual
message-view text was about 0.4-16 KiB. Session length alone did not explain the
failures. No input limit, execution deadline or retry budget was increased.

- Release-session failures were model-copied U+202F/ASCII-space substitutions.
  A whitespace rebinding workaround was initially evaluated, then removed after
  the owner explicitly chose source-only summaries. It is not shipped here.
- Three older unknown attempts had exact persisted cancellation proofs. Existing
  store wake calls released only their blocked flags, preserving checkpoints,
  epoch, settings and attempt identity. Normal original-attempt recovery entered
  bounded retries; one source subsequently committed a batch.
- Another old attempt had a typed session/new slot rejection and zero prompt
  frames in the exact native reliable queue. Existing observed-revision task
  controls queued a targeted retry.
- A known failed source received a guided operation selecting its failed
  64-message range. Its one-operation requirements reinforced concise content and
  correct source selection; permanent guidance and previous results were retained.
- A separate answer had completed after about ten seconds and was already
  persisted as one complete JSON assistant row, followed by native end_turn.
  The reader only recognized an additional conversation marker. The new strict
  completion reader fixes original-result recovery without another model call.

Diagnostics used read-only transactions and bounded lookups with statement/lock
timeouts. Temporary operational helpers were removed and are not deliverables.
No raw source, quotations, capabilities or credentials are recorded here.

Successful late responses do not gain a new automatic queue wake in this PR.
An already blocked successful attempt can use existing per-task original-result
recovery after deployment. Legacy quote-blocked work requires an intentional new
retry to adopt the source-only policy. Do not bulk reset checkpoints or unknown
executions. Cross-message output concatenation is unchanged.
