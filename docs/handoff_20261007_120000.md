# Paxl version reporting and remote upgrade (KEV-93)

The authenticated user API now accepts `POST /api/v1/user/{user_id}/nodes/{node_id}/paxl/upgrade` with `command_id`, explicit semantic `version`, and optional `tag` (stable/latest). It authorizes the node through the existing user store, then forwards `paxl.upgrade` over node control. Query the existing daemon command endpoint for completion; an HTTP 202 or received ACK is not success. Paxl updates do not use daemon restart confirmation.

Heartbeat `paxl` observations are saved under node `metadata.paxl`: status, version, commit, actual executable path, checked_at, and optional error. Runtime snapshots preserve this last observation. Offline nodes retain it. No database migration is needed.

The Thrift IDL is the endpoint source of truth. Regenerate with `make generate`. Changes span the userapi service, HTTP adapter, heartbeat ingestion, and memory/PostgreSQL persistence. Paxd resolves the same executable used for session scanning, stages checksum-verified artifacts, atomically replaces the executable, verifies its actual reported version and restores the prior binary on verification failure. Console persists the command identity for refresh/retry recovery.

## Browser E2E

In the paxd checkout, build the production node-control runner fixture:

```sh
GOWORK=off go test -c -o /tmp/paxl-e2e-node ./internal/controlws
```

In this checkout, with Console dependencies installed:

```sh
PAXL_E2E_NODE_BINARY=/tmp/paxl-e2e-node \
PAXL_E2E_CONSOLE_DIR=/absolute/path/to/pax-console \
PAXL_E2E_BROWSER_CHANNEL=chrome \
GOWORK=off go test ./internal/manager -run '^TestPaxlBrowserUpgrade$' -count=1 -timeout=4m
```

The opt-in test starts a real Next Console and Manager API, and a subprocess using the production paxd WebSocket runner, SQLite store and installer. Only binary releases and local identity are fixtures. It does not run the full daemon supervisor or external PostgreSQL. It upgrades temporary v1/v2 binaries and checks browser reload recovery. Process groups are terminated during cleanup.

## Deployment and limits

Deploy compatible paxd and Manager before exposing the Console action. Updated paxl self-update and paxd cooperate through `<real executable>.update.lock`; older paxl versions do not honor this advisory lock, so avoid concurrent legacy self-update during rollout. Running processes retain their existing executable; subsequent launches use the new file. Windows remote updates and command wrappers are rejected. Interrupted received commands can be retried with the same ID; the daemon verifies an already-installed target rather than downloading again. The resolver must still return the explicitly requested target.

Validation results are recorded in the final task handoff; no production binaries or services were upgraded by this work.
