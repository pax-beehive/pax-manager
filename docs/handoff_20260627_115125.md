# VM Cloud Build Deployment Handoff

## Summary

Added a VM-targeted Cloud Build pipeline to replace the previous Cloud Run
deployment path. The new pipeline builds and pushes the pax-manager Docker image to
Artifact Registry, then SSHes to a single Compute Engine VM and runs a VM-local
deployment script.

The existing `cloudbuild.yaml` and `make cloud-build` target are deprecated and
kept only as a manual Cloud Run rollback path. Production CI/CD should use
`cloudbuild.vm.yaml` and `make cloud-build-vm`.

## Module Boundaries

- `cloudbuild.vm.yaml` owns the VM deployment pipeline only.
- `Makefile` exposes a convenience target for submitting the VM build.
- Runtime configuration and secrets stay outside the repository and Cloud Build
  command line.

## Request and Data Flow

```text
Cloud Build
  -> docker build with BuildKit github_token secret
  -> docker push Artifact Registry
  -> copy VM scripts from deploy/vm/
  -> bootstrap Docker and Cloud SQL Auth Proxy on the VM
  -> gcloud compute ssh pax-manager VM
  -> sudo /opt/pax-manager/deploy.sh <image>
  -> VM pulls image and restarts pax-manager container
```

The VM deploy script should retrieve `DATABASE_URL` from Secret Manager at
runtime and pass it to the container. Do not put database credentials in Cloud
Build substitutions, YAML, or SSH commands.

## VM Prerequisites

The VM should have:

- A service account with `roles/artifactregistry.reader`.
- Cloud SQL access for the VM service account, such as `roles/cloudsql.client`.
- Secret Manager access for the database URL secret, preferably scoped to only
  the required secret.
- `/etc/pax-manager/env` containing non-secret runtime configuration such as
  `PORT`, Cloudflare Access issuer/audience/JWKS URL, admin emails, and
  registration owner email.
- `/opt/pax-manager/deploy.sh` installed and executable. Cloud Build copies it
  from `deploy/vm/deploy.sh` on each deployment.

The VM Cloud Build pipeline bootstraps Docker and Cloud SQL Auth Proxy if they
are missing. Keeping Docker preinstalled on the VM still keeps deployments
faster and removes package manager availability from the deploy path.

The deploy script mounts `/cloudsql:/cloudsql` into the pax-manager container.
This is required while the Secret Manager `DATABASE_URL` uses the Cloud Run
Unix socket path under `/cloudsql`.

## Cloud Build IAM

The Cloud Build service account needs permission to SSH to the VM. If OS Login
is enabled, grant the appropriate OS Login role, such as
`roles/compute.osAdminLogin`. If SSH goes through IAP, also grant
`roles/iap.tunnelResourceAccessor` and allow IAP source range
`35.235.240.0/20` to TCP port 22 on the VM.

The Docker build uses BuildKit secret `github_token`, sourced from Secret
Manager secret `PAX_BEEHIVE_READ_TOKEN`, so private Go modules can be fetched
during `go mod download` without writing the token into the image layer. The
Cloud Build service account needs Secret Manager access to that secret.

## Deployment Commands

Default VM deployment:

```bash
make cloud-build-vm
```

This passes the local git short SHA as `SHORT_SHA` because manually submitted
Cloud Build jobs do not always populate `SHORT_SHA`.

Override the VM target:

```bash
gcloud builds submit \
  --config cloudbuild.vm.yaml \
  --substitutions SHORT_SHA=$(git rev-parse --short HEAD),_VM_NAME=pax-manager-monolithic,_VM_ZONE=us-west1-b
```

The deprecated Cloud Run rollback deployment remains:

```bash
make cloud-build
```

## CI/CD Trigger

The `pax-manager` Cloud Build trigger should use `cloudbuild.vm.yaml` instead
of autodetecting the default build. The trigger config is captured in:

```text
deploy/cloudbuild-trigger.vm.yaml
```

Apply it with:

```bash
gcloud builds triggers update github 679d5516-5c10-49a9-9ab5-705830f131b8 \
  --project pax-tech-499219 \
  --region global \
  --trigger-config deploy/cloudbuild-trigger.vm.yaml
```

After this, pushes to `main` build the Docker image and deploy it to
`pax-manager-monolithic` through the VM pipeline.

## Verification

After the VM deployment completes:

```bash
gcloud compute ssh pax-manager-monolithic --zone us-west1-b --command 'docker ps'
gcloud compute ssh pax-manager-monolithic --zone us-west1-b --command 'docker logs --tail=100 pax-manager'
gcloud compute ssh pax-manager-monolithic --zone us-west1-b --command 'curl -fsS http://127.0.0.1:9879/health'
```

Then verify the external route through the selected ingress path and confirm
that paxd agent tunnels and user ACP tunnels terminate on the single VM runtime.

## Risks and Gotchas

- This fixes the current in-memory ACP tunnel affinity issue only while the VM
  deployment remains single instance.
- Adding a second VM without durable tunnel routing will reintroduce the same
  class of failure.
- Secrets should be fetched by the VM deploy script or runtime, not passed
  through Cloud Build logs.
- The VM path assumes `/opt/pax-manager/deploy.sh` exists before the first
  Cloud Build deploy.
