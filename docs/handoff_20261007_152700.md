# Harness and ACP adapter upgrade forwarding

## Behavior and boundaries

The authenticated user API forwards harness.upgrade for Claude, Codex and Pi.
Requests contain command_id, harness, component (cli or acp), and an exact
version. ACP upgrades also require a running connection_id; CLI upgrades omit
it and select the native launcher on the daemon PATH. Remote callers cannot
supply package names, executable paths or shell commands.

Thrift remains the API source of truth. The original change regenerated models,
routes, handlers and OpenAPI with make generate. This restoration changes
validation, not the transport schema. userapi owns authorization and validation;
the existing node-control dispatcher and query API carry ACKs and results.

Console -> same-origin proxy -> Manager -> node-control WebSocket -> paxd's
durable received command -> paxl installer. Execution starts after ACK delivery.
Retries reuse the command ID. paxd drains work, installs, restarts affected ACP
processes, checks their new epochs and versions, and reports applied or failed.
Failure restores the previous launcher and restarts the previous runtime.

## Executable binding

Direct codex-acp and claude-agent-acp processes receive absolute CODEX_PATH and
CLAUDE_CODE_EXECUTABLE values. Nonempty explicit overrides take precedence;
otherwise paxd resolves codex or claude using the connection PATH and cwd.
Missing or invalid executables fail startup without falling back to adapter
bundled binaries. The launcher symlink is retained so atomic upgrades switch
its target for subsequent process starts. Probes follow this same binding.

CLI upgrades verify Runtime.Version on every affected new ACP process. Adapter
upgrades verify ACPAgent.Version. Shared launchers used by another remote block
remote upgrade. Unknown custom wrapper bindings block native updates. npx and
custom wrappers are not covered by the direct-launcher binding policy.

Pi ACP currently uses its own SDK. Pi CLI updates are separate and the Console
explains that distinction. A separate adapter task will add PI_ACP_SDK_ROOT;
paxd does not assume that interface exists yet. Pi ACP upgrades accept only the
scoped @ccgv2/pi-acp package. Its local staging checks JavaScript syntax because
it has no --version entrypoint; the daemon validates its ACP handshake version.

## Support and operational limits

The installer supports Unix npm global packages with direct symlink launchers.
Native installers, Homebrew, pnpm, bun, npx and Windows launcher replacement are
unsupported. Versions install into separate directories and old trees remain
available for rollback; garbage collection is deferred. Installing an adapter
alone is insufficient for managed Claude/Codex startup: install its native CLI
or configure an explicit native executable override as well.

Model visibility also depends on account/provider configuration and adapter
compatibility. Version verification does not guarantee a particular model is
available. New sessions obtain model lists from the restarted runtime.

These changes do not perform a workstation package upgrade or a production rollout.
No existing local issue describes this endpoint; legacy protocol issue statuses
remain unchanged.

## Validation

Run Manager full Go tests and build, make fmt-check and make lint (normal and
integration tags); paxl facade/CLI tests, lint and format-check; paxd control,
daemon, runtime and controlws tests; Console typecheck, scoped ESLint and resource
component tests. The runtime suite encountered one heartbeat timing failure
under concurrent load and passed on rerun without changing that test.

The browser test uses real Console/Manager transport, daemon command persistence,
paxl installation and ACP process supervision. npm downloads and packages are
fixtures. It exercises all six CLI/adapter upgrade combinations, refresh
recovery, native runtime version mismatch rollback and adapter version mismatch
rollback. Each affected connection has two ACP child processes. Fixture adapters
require absolute native bindings and observe the selected executable's version.
No model provider is called and no workstation package is updated.

```sh
# Select Go 1.26 using gvm before these commands.
# paxl worktree
GOWORK=off go build -o /tmp/kev64-paxl ./cmd/paxl
# paxd worktree
GOWORK=off go test -c -o /tmp/kev64-paxd-e2e ./internal/daemon
# Manager worktree, with Node 24 on PATH and Console dependencies installed
PAXL_E2E_BROWSER_CHANNEL=chrome \
PAXL_E2E_CONSOLE_DIR=/absolute/path/to/pax-console \
PAXL_E2E_NODE_BINARY=/tmp/kev64-paxd-e2e \
HARNESS_E2E_PAXL_BINARY=/tmp/kev64-paxl \
GOWORK=off go test ./internal/manager -run '^TestHarnessBrowserUpgrade$' -count=1 -timeout=6m
```

Final local validation passed: all six browser upgrade paths and both version
mismatch rollback paths (87 seconds); Manager full tests/build/fmt/lint; paxl
facade/CLI suites, build, lint and format-check; paxd affected suites and the
runtime rerun; Console typecheck, scoped ESLint, the resource suite and the
additional native CLI submission test. A first browser attempt completed its
native update but timed out waiting for page hydration after reload. The final
run included page error diagnostics and a longer reload wait and passed without
changing product behavior.
