# Runtime idle interruption grace period

## Summary

Runtime snapshots that move a session to `idle` no longer interrupt an active
conversation prompt immediately. The ACP session mux now waits for five seconds
of session-frame silence before interrupting the prompt and its SSE subscriber.

## Module boundaries

- `internal/manager/node_control_tunnel.go` converts an applied idle snapshot
  into a deferred interruption request.
- `internal/manager/acp_tunnel.go` locates the shared per-agent session muxes.
- `internal/manager/acp_session_mux.go` owns the grace timer, prompt-generation
  fence, frame activity reset, and atomic receiver interruption.

No generated artifacts or API schemas changed.

## Core flow

1. An applied runtime snapshot reports a previously active session as idle.
2. If the mux still owns a `session/prompt` response waiter, it starts a
   five-second idle interruption timer.
3. Any ACP frame for that session restarts the five-second quiet period.
4. A final prompt response, prompt cancellation, a newer prompt generation, or
   a snapshot that restores a non-idle status cancels the timer.
5. On expiry, the timer verifies the original prompt generation and atomically
   removes only that generation's waiter and subscribers before delivering the
   existing conflict error.

## Risks and operational notes

- A genuinely stopped runtime now takes up to five seconds longer to release
  its active conversation request.
- Any session ACP frame counts as activity and extends the grace period. This is
  intentional to avoid truncating output that is still in flight.
- The timer is fenced by the session's prompt generation so it cannot interrupt
  a prompt created after the idle snapshot.
