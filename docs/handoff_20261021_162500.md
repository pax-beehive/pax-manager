# Cron session registration handoff

## Change and boundaries

paxd now owns persistent cron jobs, triggers, prompt/workspace snapshots, and
new/reuse session bindings. ACP execution is local to paxd. paxl exposes CRUD via
the daemon socket. This Manager change registers node-created native sessions as
ordinary encrypted Pax sessions; Console displays their immutable cron origin.

The new endpoint is `POST /api/v1/node/agents/:agent_id/sessions/register` with
node authentication. Its request contains `native_id`, absolute node `cwd`, and
`origin` (`kind=cronjob`, `registration_id`, `cronjob_id`, `run_id`, `name`).
The response is the standard AgentSession data envelope with `session_id`.

Business validation lives in `internal/manager/paxd/node_session.go`; ownership,
idempotency, and persistence live in `storage/node_session.go`. The thin handler
is in `node_session_handler.go`. The canonical-session store wrapper forwards
registration to the underlying optional registrar interface. The machine-route
manifest includes the endpoint and enforces node credentials.

PostgreSQL locks the agent row before checking native ID or registration ID.
Identical retries return the same session. Different native/workspace/origin
bindings conflict. The agent must belong to both the authenticated node and its
owner. Sessions use transport `e2ee` from creation. Existing metadata stores the
origin and initial cwd; no new Manager table or schema migration is required.
Ordinary session updates must preserve this creation metadata.

## Cross-repository flow

paxd reserves a local binding before `session/new`, saves the native result, and
registers with Manager. It stores the returned Manager/native mapping before
publishing encrypted history. Local execution can proceed during Manager outages;
SQLite journals retain registration state, prompt/output frames, and encrypted
retry envelopes. Stable record IDs retain identical ciphertext across retries.
The standard ACP router retains prompt leases, resume routing, permissions, and
cancellation. New mode creates each run's session; reuse mode retains its first
creation run in origin metadata. Each run references its session separately.

Console reads `metadata.origin` through existing session queries and displays
`Cron: TASK_NAME` in recent sessions and the workbench, including cronjob/run IDs
in the tooltip. No separate browser scheduler is introduced.

## Operational limits

This is single-daemon scheduling, not a distributed scheduler. Daemon downtime
coalesces missed schedules; interrupted executions are not automatically retried.
An ambiguous native creation in reuse mode requires explicit binding reset.
Unanswered permissions time out without implicit approval. Existing E2EE key
provisioning is required. Local transcripts and retry envelopes are retained with
no automatic cleanup; monitor SQLite growth. There is no cron management page,
notification delivery, or import of native-agent schedules in this change.
