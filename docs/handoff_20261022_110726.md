# Durable node daemon command records

## Summary

The manager now persists paxd maintenance commands issued through the user API
so their progress survives browser reloads, other browsers, node disconnects,
and manager restarts. Before this change the only handle on a command was the
command_id held by the browser that sent it.

Recorded types: paxd.restart, paxd.upgrade, paxd.maintenance.cancel,
paxl.upgrade, harness.upgrade. Agent connection and secret channel commands
are not recorded.

## Ownership

- Intent (command_id, node, type, target, target version, requester, created
  time) is owned by the manager table `node_daemon_commands`.
- Execution state (status, phase, error, result) is owned by paxd, which
  persists its own command records. The manager row mirrors the last
  `command.get` observation and never invents execution state, except:
  - `dispatch_failed`: paxd never acknowledged the command.
  - `lost`: paxd answered `not_found` for a command it had acknowledged.
- paxd keeps restart and upgrade records at `received` after the new process
  starts. Completion for those comes from the heartbeat-based
  `maintenance_confirmation` (confirmed or version_mismatch), which is now
  persisted with the row.
- `state` folds both into `in_progress`, `succeeded`, or `failed`
  (`domain.NodeDaemonCommandState`).

## Flows

- Dispatch (`userapi.dispatchRecordedNodeDaemonCommand`): insert the row as
  `dispatching` before sending; reusing a command_id for a different type on
  the same node returns 409; after the ack the row takes the ack status, or
  `dispatch_failed`. A failed resend does not overwrite a status paxd already
  reported. The 202 response includes `daemon_command`.
- Read (`GET .../daemon/commands/:command_id`): still forwards `command.get`;
  the observation is written back and returned as `daemon_command`. When paxd
  is unreachable and a row exists, the stored row is returned in the
  command.get shape with `stale: true`. Unrecorded commands keep the old 503.
- Reconciliation: every heartbeat calls
  `userapi.TriggerNodeDaemonCommandSync`, which at most once per 10 s per node
  runs a background `command.get` sweep over up to 20 in-progress rows. This
  also re-tracks restart and upgrade confirmations after a manager restart.
- List (`GET .../daemon/commands?type=&state=&limit=`): stored rows only,
  newest first, default 20, max 100.
- Nodes (`ListNodes`, `GetNode`): each node carries `latest_daemon_commands`,
  the newest row per command type. A failure to load them only drops the
  field.

## Module boundaries

- `internal/manager/domain/node_daemon_command.go`: types, store interface,
  state folding.
- `internal/manager/storage/node_daemon_commands.go`: Postgres (raw SQL) and
  memory implementations.
- `internal/manager/userapi/node_daemon_commands.go`: recording, read-through,
  sync, list, node enrichment.
- `internal/manager/node_control_tunnel.go`: heartbeat trigger only.
- `internal/manager/node_idl_handlers.go`, `idl_handlers.go`: list handler.

## Schema and generated code

`db/init.sql` adds `node_daemon_commands` (primary key node_id, command_id;
cascades from nodes and users) plus two indexes. EnsureSchema applies it at
startup; the DDL is idempotent. No GORM model was generated for the table.

`api/pax_manager.thrift` adds `NodeDaemonCommand`,
`NodeDaemonMaintenanceConfirmation`, `Node.latest_daemon_commands`,
`NodeDaemonCommandData.daemon_command`, and `ListNodeDaemonCommands`.
Regenerated with `make hz-update`, `go generate ./internal/manager`, and
`make mocks` (needs `GOTOOLCHAIN=go1.25.8`; mockery built with go1.24 cannot
load this module).

## Risks and notes

- Rows created before this change do not exist; old browser-held command IDs
  still work through the live read path.
- A restart or upgrade whose node never reconnects stays `in_progress`.
- The sync sweep shares the per-node control connection, which serializes
  requests; the throttle and batch size keep it short.
- The console still uses its localStorage command IDs until the console change
  that reads `latest_daemon_commands` lands.
