# Search indexing queue priority

## Change and boundaries

ISSUE-050 fixes search indexing starvation while historical backfill is running.
Only PG queue metadata, source-trigger classification and the claim selection
change. Search APIs, matching, source visibility, owner checks, ES external
versions and worker acknowledgements retain their existing contracts. There are
no generated changes or regeneration steps.

`db/search.sql` adds `search_sync_state.is_backfill`. Missing backfill rows are
inserted with true by `BackfillSearch`; conflicts do nothing. The transactional
`pax_search_mark_dirty` function inserts false, including revision-one rows, and
promotes existing work to false when sources change. Promotion advances the
existing desired revision and preserves indexed revision and active leases.

`internal/manager/storage/search_postgres.go` claims live work first, then
history, then additional live work if history has unused slots. A production
batch of 20 uses 16 live slots and four reserved historical slots when both have
ready work. For other batch sizes of at least two, history reserves at least one
slot and otherwise integer one fifth. A batch of one prefers live work, falling
back to history; it cannot guarantee both classes a share under continuous load.
History orders session titles before summaries before messages. Both classes
honor retry availability and active leases, with row locks skipped. Each claim
remains bounded by the normalized batch limit of 100.

The unchanged lease-token acknowledgement fence prevents an old claim from
acknowledging a newly leased revision. Completing a historical claim never
reverts a concurrent live promotion or acknowledges its newer desired revision.
ES receives the existing durable revision and canonical source snapshot.

## Schema application and rollout

Existing rows receive the constant default true using PostgreSQL's
[metadata fast-default behavior](https://www.postgresql.org/docs/current/ddl-alter.html#DDL-ALTER-ADDING-A-COLUMN). Their original scheduling origin cannot be reconstructed
reliably; future source changes promote them. Startup runs no INSERT, UPDATE or
DELETE against the queue. Reapplying the schema does not reset existing false
classifications or any queue state.

One new partial composite index, `idx_search_sync_pending_priority`, matches the
class-dependent ordering and includes only desired revisions ahead of indexed
revisions. The first application builds that index and can briefly block source
writes while PostgreSQL creates it. Later applications use IF NOT EXISTS. The
existing availability index is retained. No per-batch full pending sort is
required by the verified claim plan.

Build and deploy through the normal Manager release path with the existing PG
and SEARCH_URL settings. The schema runs through existing EnsureSchema wiring;
no data export, reindex reset, manual blanket UPDATE or ES API change is needed.
Rolling back to an older Manager restores FIFO scheduling; its mark-dirty
function no longer promotes the new class flag. Canonical revisions remain intact.

A separate temporary production mitigation reprioritized eligible session-title
tasks using available_at only. The session-title backlog was observed drained
at 2026-11-01 06:13:12 UTC; this does not establish historical message-backfill
completion or deployment of this source fix. ISSUE-049 remains open.

## Verification

20 historical messages omitted both a waiting session title and a summary.
The new tests cover sustained live writes with reserved historical progress,
capacity borrowing, actual source-trigger revision-one insertion, promotion
under an active historical lease, stale acknowledgements, retry availability,
locked rows, unknown kinds and guarded legacy schema application. A 10,000-row
